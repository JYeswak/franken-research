## Hook

The repository describes itself as "semantic, transactional, replayable." In the code, "replayable" mostly means one concrete and well-tested thing: every effect family writes a private, hash-chained journal that is replayed on restart, and the tests flip every single byte of a journal and truncate it at every non-frame boundary to show replay refuses all of them [Code-verified, High]. The one component named for deterministic replay, the `dfmcp-lab` chaos harness, issues a `DeterminismCertificate` from a loop that draws random numbers and throws them away; its reproducibility test compares two untouched sessions [Code-verified, High]. The repo's own reality-check document already calls it "an RNG loop" [Maintainer claim, High].

## 4.2 Executive verdict

dwarf_fortress_mcp is an MCP server, written in safe Rust, that exposes a frozen eleven-tool `fortress.*` interface over a family of versioned, authenticated, loopback-only DFHack plugins the project writes itself, with every read published as a whole-or-nothing capsule and every effect run as prepare, durable `CommitStarted`, single dispatch, receipt-verified terminal record. **TRL 3** [Inference, Medium]: the lower library crates compile and the lab crate's 13 tests pass, but the `dfmcp-mcp` library that every server binary needs does not compile at the pin, several test targets do not compile (§4.5), no plugin has been built against a real DFHack generation in a recorded, qualified way, and the compatibility registry is empty [Reproduced, High; Maintainer claim, High; registry Verified, High]. **NODUS: Explore** [Inference, Medium]: substantive, unreleased, unvalidated. The single most important strength is the effect-journal discipline: durability before dispatch, no automatic retry of a mutating commit, restart replay that refuses any corrupted byte or torn prefix [Code-verified, High]. The single most important ceiling is that the whole apparatus has never been admitted against a live game, so every claim about Dwarf Fortress behavior is still target-state [Maintainer claim, High].

## 4.4 Architecture (reconstructed from the code)

**Crates and sizes** [Counted, High] (tracked `.rs` lines / files / `#[test]` annotations): `dfmcp-mcp` 78,549 / 197 / 703; `dfmcp-adapter` 77,221 / 181 / 751; `dfmcp-world` 14,379 / 45 / 137; `dfmcp-intent` 6,773 / 25 / 91; `dfmcp-core` 4,487 / 16 / 43; `dwarf-fortress-mcp` 2,273 / 8 / 16; `dfmcp-lab` 1,888 / 3 / 13. Total 185,570 lines, 1,754 `#[test]` annotations, 2 of them ignored; 59,807 lines sit in files named as tests (`tests/`, `*_tests.rs`, `tests.rs`), which undercounts inline test modules. The dependency graph is a strict layering: core ← world ← intent ← adapter ← lab ← mcp ← binary [Verified, High]. The repository's own reality-check addendum gives "~164k src LOC" [Maintainer claim, Medium]; the body of that same document, measured on an older checkout, says "~16.4k-LOC" and "The DFHack bridge does not exist" [Maintainer claim, High], which the pin contradicts.

**Native side.** 18 plugin directories under `bridge/` (plus `bridge/common/`): the original `dfhack-plugin` (protocols 1.0 and 1.1) and one directory per later generation from `jobs-v1_2` to `excavation-run-v1_18`, each with its own `.proto`, C++ source and `CMakeLists.txt` [Verified, High]. `tests/native/` holds C++ harnesses with DFHack stub headers and hex wire vectors [Verified, High]. The Rust side contains no FFI; it talks to the plugins over loopback RPC with bearer-token authentication [Maintainer claim, High; FFI absence Verified, High via the unsafe census].

**Binaries.** 16 `*-dev-server` binaries, one per development profile (for example `dfmcp-dig-control-dev-server`, `dfmcp-live-workforce-dev-server`), plus 2 probes and the main `dwarf-fortress-mcp` [Verified, High]. The dev servers are gated by environment switches such as `DFMCP_ALLOW_UNADMITTED_DIG_CONTROL_V1_16=1` [Maintainer claim, High].

**What "transactional" means in the code.** Three distinct mechanisms, none of them a database transaction:
1. *Read publication.* Multi-page citizen and announcement reads are assembled and published as one capsule only when every page agrees on the same observation identity; a failure leaves nothing published (`live_observation_publication_v1_1.rs`) [Code-verified, High]. The canonical capsule is independent of pagination and identified by SHA-256 [Maintainer claim, Medium; one related test, `capture_finishes_multiple_pages_and_is_idempotent_at_the_same_anchor`, seen by name].
2. *Effect journals.* For each effect family (pause/1.7, job suspension/1.9, work orders/1.10, bounded run/1.13, order run/1.14, dig/1.15-1.16, workforce/1.17), a private file journal under an exact `0700` directory with exact `0600` mode, opened with `O_NOFOLLOW`, synced with `sync_all`/`sync_data` before acknowledgement (`control_effect_journal.rs:1033-1143` and 8 other file-backed journal modules that call `sync_all`/`sync_data`) [Code-verified, High]. `CommitStarted` is written before the mutating RPC; unknown outcomes stay "reconciliation-required"; a new effect needs a new observation and a new idempotency key [Maintainer claim, High].
3. *Sealed plans.* Plans are digest-sealed; commit refuses a plan whose content changed after prepare and rechecks authorization even on idempotent replay (`dfmcp-lab/src/lib.rs:796-851`; test `commit_rejects_plan_content_changed_after_prepare` passed) [Reproduced, High].

**What "replayable" means in the code.** (a) Journal replay on restart, with integrity refusal: `every_byte_corruption_and_every_incomplete_frame_prefix_fails_replay` flips each byte of a prepared-and-committed journal and truncates it at every non-frame length, asserting `reopen` fails for all of them [Code-verified, High]. At least 40 `fn *replay*` tests exist in adapter, intent and mcp [Counted, High]. (b) Observation archives (operations/1.3, spatial/1.6 and 1.8) replayed to rebuild history and watches [Maintainer claim, High]. (c) Cross-language vectors: `independent_python_vectors_replay_through_real_rust_archive_and_book_codecs` and `independently_encoded_binary_fixture_replays` [Code-verified, Medium, names read]. (d) The lab determinism certificate, which is hollow (claim 5). No recorded game session, no trace of a real fort, and no determinism test over the game itself exists [Verified absence, High]; the project's docs treat Dwarf Fortress as nondeterministic and outside its transactional control [Maintainer claim, High].

**Doc layers.** 276 Markdown files, 32,690 lines, including a 171 KB comprehensive plan [Counted, High]; 127 JSON contracts and registries [Counted, High]; 100 `CHANGELOG.d/` fragments [Counted, High]; 124 beads in `.beads/issues.jsonl` (70 closed, 6 in progress, 48 open) [Counted, High].

**asupersync.** A direct runtime dependency of `dfmcp-mcp` only, pinned `=0.5.0` from crates.io: 27 `asupersync::` references in 13 files, used for `Cx`, `RuntimeBuilder`, the reactor, timeouts and cancellation (`dfmcp-mcp/src/lib.rs:62-194`) [Code-verified, High]. The crate named for asupersync's deterministic lab, `dfmcp-lab`, does not depend on asupersync [Verified, High].

## 4.6 Comparison: who owns the lane

The lane, "let an LLM agent read and act on a running Dwarf Fortress," is owned today by **DFHack** itself (2,044 stars, active 2026-09-23) [External, High]: its Lua scripting, `quickfort`, and remote RPC are what every agent project, this one included, builds on. For autonomous play, **BenLubar/df-ai** (279 stars, C++, last push 2022-10-10) is the long-standing DFHack plugin that plays a fort without an LLM [External, High]. For LLM access through MCP there are small, recent projects: `ryanbateman/vizier_mcp` (2 stars, read-only by design), `alexanderolvera/dfhack-mcp` (2 stars, "co-pilot … not an autopilot"), `oleksiy-korniychuk/dfhack-mcp` (0 stars), and the benchmark harness `lemoz/fort-gym` (0 stars) [External, High]. The incumbents win because they run against the real game now. The unoccupied lane is a control plane with typed authority, durable effect journals and fail-closed admission for unattended, long-horizon agent operation; none of the MCP projects above claims that, and this repository is the only one with journaled, receipt-verified effects [Inference, Medium].

## 4.7 Technical merit and adversarial review

**Strengths.**
1. Effect durability is built in the right order and tested adversarially: journal before dispatch, no automatic retry of a mutating commit, terminal evidence synced before acknowledgement, and replay that refuses every corrupted byte and torn prefix [Code-verified, High].
2. Safety posture at the language level is complete: zero unsafe code, no FFI, clippy denies `unwrap`/`expect`/`panic`/`todo` in the workspace [Verified, High]. The crates with the algorithmic content have no external dependencies [Verified, High].
3. The status file is unusually candid about what was not run, including "all 32 are UNCOMPILED AND UNEXECUTED" and "Four naming hazards" (`sqlite_ledger.rs` is not SQLite, `e2e_live_fortress_tests.rs` is not live) [Maintainer claim, High]. The compiled subset the analyst ran passed (§4.5).
4. Admission is designed as a chain of exact identities (registry, monotonic floor, server receipt, protocol-bound single-use ticket) with a doctor that holds no authority [Maintainer claim, High]; the compatibility-registry, resolution, floor, doctor and ticket checkers and their Python tests pass [Reproduced, High].

**Weaknesses.**
1. Documentation drift at three layers. README (last edited 2026-09-02) describes protocols 1.0-1.1 and "no live mutation RPC"; `AGENTS.md` still describes "an implemented but unadmitted Phase-1 announcement read slice"; `IMPLEMENTATION_STATUS.md` says "through spatial/1.8" and "no live dig … work-order … effect" while listing dig and work-order control under "Present now"; the tree reaches protocol 1.18 [Verified, High].
2. The project's own gate is red at the pin and has been since 2026-09-03: `verify.sh` stops at step 3, and 12 source-level static checks fail [Reproduced, High]. A repository whose README says "the standard is not 'the command ran'" cannot currently pass its own first gate.
3. The component named for determinism is hollow (claim 5), and its test is tautological: two untouched sessions produce equal hashes [Code-verified, High].
4. The pin does not build. `dfmcp-mcp` fails with 46 errors in the analyst's RCH run, including an import that no longer exists in the pinned `fastmcp_rust` rev, so no MCP server binary can be produced from this commit [Reproduced, High]. An independent review confirmed two blockers statically without rebuilding: the `fastmcp_rust::modern::ResourceTemplate` import and the private `authorize_entry` imported from `server` ([review 2](reviews/luna-review-2.md)); it did not re-count the 46; the analyst could not tell from the history how long the library has been broken [not checked at earlier commits].
5. Nothing has run against the game under qualification: the registry is empty, no receipts are checked in, and 16 development servers each extend the unqualified surface [Verified, High]. Velocity (224 commits in one day) outruns the evidence ladder the project defined for itself [Inference, Medium].
6. The README's substrate table names eight sibling projects as accretive roles; two are wired [Verified, High].

**Bear-case steelman.** This is 185,000 lines of Rust, 44,000 lines of Python contract checks and 33,000 lines of Markdown written in under a month for a game that none of the machinery has been qualified against. Value in this lane comes from actually running forts; the small MCP servers above already let an agent read a fort today, DFHack's own tools already mutate one, and df-ai played whole forts years ago. The project's distinctive part, the admission and journal apparatus, answers risks (power loss mid-dig, protocol confusion at launch, rollback of a compatibility registry) that no user of a single-player game has reported. Its own gates are red, its README is 17 protocol generations stale, and the part named for deterministic replay does nothing. If development pauses, it leaves a well-documented design and a large unqualified codebase.

## 4.8 License and governance

The repository's `LICENSE` first line: **"MIT License"**, followed by "Copyright (c) 2026 Jeffrey Emanuel" and the standard MIT grant, 21 lines in total, **with no rider** [License-verified, High]. `Cargo.toml` declares `license = "MIT"` [Verified, High]. On its face this is an OSI-approved license, which puts the repo with `franken_agent_detection` as the only plain-MIT Dicklesworthstone repositories assessed so far.

The binaries are a different matter. `dfmcp-mcp`, and so the `dwarf-fortress-mcp` binary and every dev server, depends on `fastmcp_rust` at rev `180a7c88890705217bb8e202d19555adabf24187`, whose `LICENSE` first line is **"MIT License (with OpenAI/Anthropic Rider)"**, and on `asupersync 0.5.0`, whose crates.io license field is `LicenseRef-MIT-OpenAI-Anthropic-Rider` and whose repository `LICENSE` has the same first line [License-verified, High; External, High]. The rider, quoted from `fastmcp_rust`: *"'Restricted Parties' means OpenAI, L.L.C.; Anthropic, PBC; any of their respective Affiliates; and any person or entity acting directly or indirectly on behalf of, for the benefit of, or under the direction of any of the foregoing … no rights are granted to any Restricted Party."* Its definition of use includes *"benchmarking, testing, analyzing, indexing, or incorporating the Software or any Derivative Works into any dataset, training corpus, evaluation harness, or pipeline for machine learning or other automated systems."* So the rider bars OpenAI, Anthropic, their affiliates and anyone acting for them, including their ML training and evaluation use. It does not bar people who use those labs' models. The effect here: the five dependency-free crates (`dfmcp-core`, `-world`, `-intent`, `-adapter`, `-lab`) are usable by anyone under plain MIT; the MCP server as built is not usable by a Restricted Party without breaching its dependencies' licenses [Inference, High]. This packet does not speculate on why the repository's own file omits the rider.

**Governance.** Bus factor 1, a judgment from maintainer concentration [Inference, Medium]: 1,127 of 1,136 commits are under the maintainer's names; the remaining nine are eight `Autonomous Agent` commits and one `TopazBarn` author label [Git-observed, High] (not linked to a public GitHub account; identity unverified) [External, Medium; reviewer's lookup]. No explicit refusal of outside contributions was found; `CONTRIBUTING.md` sets a pull-request standard ("Leave the tree in a coherent, locally qualifiable state") [Verified, High]. One external issue exists, closed; one fork exists with no visible divergence checked [External, Medium]. Review depth is not observable: there are no pull requests, and commits land directly on `main` [External, High].

## 4.10 Wardley placement

- **Commodity:** DFHack's remote RPC and data model, and the MCP protocol. The project clones neither; it pins DFHack generations and a modern-only MCP profile. Movement: a DFHack release changes the plugin build matrix.
- **Custom-built:** the per-generation DFHack plugins, the Rust adapters, the eleven-tool MCP waist and its Agent Turn envelope. Movement: a first admitted tuple (R1-R5 receipts in the registry) would move the read path toward product.
- **Genesis:** the effect-journal protocol (durable `CommitStarted`, receipt-verified terminal states, never-redispatch recovery) and the exact-identity admission chain for agent-facing servers. Movement: reuse in a second project, or a published crash campaign at every durability boundary, would move them to custom.

## 4.11 Trajectory (12 / 24 / 60 months) [Inference]

**Base case (12 months):** development continues in bursts; more protocol generations and dev servers appear; the static gate is repaired and broken again; the registry stays empty or gets one read-only tuple. Documentation drift continues because the README is edited weeks apart from the code. **24 months:** either one read profile and pause are admitted against a named DFHack generation, or the project goes quiet with a large, well-described, unqualified tree. **60 months:** the journal and admission ideas outlive the game integration if they are extracted.

**Upside:** a published disposable-fort campaign (R1-R5 receipts for one exact tuple) and a tagged release; an outside agent benchmark such as fort-gym adopting it as an action adapter. **Decay:** DFHack moves, each of the 18 plugin directories needs rebuilding, and the unqualified surface becomes a maintenance liability.

## The eight deepening questions

1. **Provenance.** The project records who and what produced each artifact in fine detail: Agent Turn packets carry bridge protocol, ticket, compatibility entry, registry, floor, server receipt and executable identity; journals are hash-chained; capsules are SHA-256 identified; source bundles come from one exact clean commit [Maintainer claim, High; journal chaining Code-verified, High]. It is not portable yet: no receipt has been published, nothing is signed ("no signed cross-platform release provenance" is in the status file's absent list), and the chain ends at local custody. Portability would need signed receipts and at least one published, re-checkable qualification run.

2. **The embeddable unit.** The smallest useful unit is `dfmcp-core` plus `dfmcp-world` and `dfmcp-intent`: canonical digests, Merkle proofs, witnessed plans, obligation state machines, with no external dependencies and plain MIT [Verified, High]. The more distinctive unit, a durable effect journal with never-redispatch recovery, sits inside `dfmcp-adapter` and is specialized per effect family (9 file-backed journal modules), so extracting it means writing the generic crate the repo does not have. Cost is low legally and moderate in engineering.

3. **Unexercised option value.** The asupersync lab (deterministic scheduling) is available through the dependency but unused by the crate named after it; wiring the chaos harness to the real adapter and a simulated bridge would give the determinism certificate content. The in-memory `sqlite_ledger` and `franken_fs` prototypes mark where a durable MVCC store would go. The 16 dev servers already cover most effect families; one admitted tuple would convert that option into a product.

4. **Benchmark honesty.** No performance number is claimed, and the SLOs are disclaimed as targets [Maintainer claim, High]. The numbers load-bearing for the thesis are test counts: 1,754 Rust test annotations, 786+786 mock-native checks, 35 Python tests. The analyst reproduced 34 of 35 Python tests on macOS and 13 of 13 lab tests; the full workspace, and so the 1,754-test figure, does not compile at the pin (§4.5). None of these reaches the game, which is where the thesis lives.

5. **The governance path.** One maintainer plus agents, commits straight to `main`, no reviews, no releases. The project already wrote its own institutional machinery (receipts, registry, floor, doctor), which is the right scaffolding for a second maintainer or an operator. What breaks first if velocity drops is DFHack compatibility: 18 plugin directories covering 19 protocol generations, each pinned to a DFHack build.

6. **The license as strategy.** The repository itself excludes no one. The rider enters only through `fastmcp_rust` and `asupersync`, and excludes OpenAI, Anthropic, their affiliates and anyone acting for them from using, testing, benchmarking or evaluating the MCP server binary; it does not stop anyone else, including people driving it with those labs' models. For an agent control plane whose natural evaluators include frontier labs, this puts the barrier at the presentation layer and leaves the core crates open [Inference, Medium]. Whether that split is intended is not documented.

7. **Agent-era fit.** The workload is an unattended agent running a fort for hours: it needs complete reads, bounded outputs, no double-applied effects after a crash, and a way to explain why the fort is in its current state. A benchmark such as fort-gym would pick this over the small MCP servers if two things became true: one admitted live tuple with a working external MCP handshake, and effect families beyond pause qualified against a real game.

8. **The kill test.** Build the protocol-1.0 plugin for one current DFHack, run R1-R5 on a disposable fort, and run the pause/1.7 crash campaign at every durability boundary the status file lists. If the reads or the journal fail against the real game, the apparatus is ceremony; if they pass, the project gets its first admitted tuple and the ring should be revisited. A cheaper test: make the workspace compile and `verify.sh` pass at a pin.

## Cross-cutting lenses

- **Decoupling.** The project separates authority from cognition (derived graphs, search and recommendations can never authorize an effect) and separates observed history from game effects, stating that the first is transactional and the second is not [Maintainer claim, High; enforced in part by capability checks in code, Code-verified, Medium].
- **Methodology export.** If the game integration never ships, the parts that survive are the effect-journal protocol and the exact-identity admission chain, plus the byte-flip and truncation replay tests as a pattern [Inference, Medium].
- **The asupersync question.** Runtime dependency of `dfmcp-mcp` only, `=0.5.0` from crates.io; used for `Cx`, runtime construction, reactor, timeouts and cancellation; not used by `dfmcp-lab` despite that crate's "asupersync Deterministic Lab" doc line [Verified, High]. The repo's own dependency-policy checker rejects the crates.io pin [Reproduced, High].
- **The rider question.** Covered in §4.8 and question 6.
