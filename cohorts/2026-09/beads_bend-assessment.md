## Hook

A port of the issue tracker `br` into Bend 2, a language whose type checker is a proof checker, advertised in its GitHub description as "law-proved." What the proofs are, concretely: 73 laws in `port/LAWS.bend`, of which 72 are closed equations on one concrete input each and every one of the 73 is proved by `{==}`, that is, the checker evaluates both sides and finds the same normal form [Counted, High]. The one quantified law relates two identity functions left over from the project template [Code-verified, High]. The README says as much in its own table ("no quantified one"). The port's real claim to fidelity rests elsewhere: 1,094 captured outputs of the pinned `br 0.6.0`, and I reproduced 804 of the 813 read-only ones byte for byte with a separately built `br` of the same commit, all nine differences explained [Reproduced, High].

## TL;DR

**Verdict.** beads_bend is a five-day-old, agent-written, single-maintainer experiment: re-implement the JSONL-only mode of `br` (`br --no-db`) in Bend 2 and hold it to two separately named equivalences, "original == spec" by captured goldens and "spec == fast" by laws the Bend checker verifies. The golden half is unusually disciplined: the oracle is a hash-pinned release binary [Verified, High], outputs are captured inside a hermetic sandbox and never typed [Maintainer claim, High], every golden digest matches its manifest (3,282 of 3,282) [Reproduced, High], and the goldens are real `br` behavior (804 of 813 re-derived independently) [Reproduced, High]. The port is reported to pass all 1,094 cases on three of its four executors [Maintainer claim, Medium; not re-run]. The law half is thinner than the word "law-proved" suggests: every law is a closed example checked by evaluation, so each is a compile-time unit test with the expected bytes pasted from a golden; 17 of them compare a fast implementation with its spec implementation on one fixture each [Counted, Medium]. No quantified property of the port is proved, and the two beads that would add one (`bb-0au`, `bb-7bm`) are open [Verified, High]. No CI, no release, no tag. **TRL 4. NODUS: Explore-with-a-ceiling.** Strongest asset: the oracle-capture discipline. Ceiling: the product has no reason to exist beside `br` (the README says "When to use `br`: always, today"), and the "law" layer, as built, proves examples rather than properties.

## 4.4 Architecture (reconstructed from the code)

**Topology.** One Bend program: a pure core of 31 modules under `port/core/` (20,564 lines, 2,177 `def`s) [Counted, High] and an IO shell, `port/main.bend` (310 lines), that reads argv, the environment, the store and the clock, calls `Run.outcome` once, and applies its `Outcome` (stdout, stderr, exit code, a list of file writes) [Code-verified, High]. The shell defines five custom effects, `Sys.exit`, `Clock.wall`, `Sys.stdin`, `Sys.cwd`, `Sys.remove`, each with a C and a JavaScript twin in `port/effs/` (125 lines in all) because Bend's base library lacks them [Code-verified, High]. The largest modules are `help.bend` (3,347 lines of carried `clap` help texts, generated by `scripts/gen-help-bend.py`), `run.bend` (1,858), `decode.bend` (1,554) and `cli.bend` (1,495) [Counted, High]. The split exists so that `PROOF.bend` imports only the core: under Bend 2.0.20 a proof book that reaches a foreign effect gets a different verdict and checks 5 to 9 times slower [Maintainer claim, Medium].

**Data flow.** argv and env → workspace probe → store bytes → `Store.load` (or `Store.load_fast`, a 16-way fork tree over lines, then the same sequential fold) → command → render Plain, JSON or Quiet → on mutation, `Store.text` rewrites every record ordered by id [Code-verified, Medium; read at the law and header level]. The clock enters once, as `BEADS_BEND_NOW` (the test seam, DISC-001) or `Clock.wall` [Code-verified, High].

**Twins and the kill switch.** Fast twins run by default; `BEADS_RUST_SPEC=1` selects the spec twins (`Store.load`, the list scans of the BLOCKED relation) [Maintainer claim, High]. So the goldens exercise the fast twins on every lane, and the last recorded golden run of the spec twins is one JS-lane run at commit `fd0a945` over the 1,009-case corpus of that commit (1,007 pass, 2 fail, "the same two failures as without the switch") [Maintainer claim, Medium]. The README's picture, where goldens vouch for simple code and laws carry that trust to fast code, is inverted in practice: the lanes test the fast code directly.

**The law layer, concretely.** `LAWS.bend` declares 73 `law`s and `PROOF.bend` fills each with `def Laws.<name>(): {==}` [Counted, High]. `{==}` asks the checker to normalize both sides of the stated equation and compare. By kind (classified from each law's own comment): 32 closed goldens (the expected side pasted from a golden file), 16 closed facts, 17 closed `fast == spec` comparisons, 6 other closed checks (time-grammar refusals, an offset suffix, an agent-context reprint), 1 refutation (`lead_tenths_odd_tie_refused`), and the template law [Counted, Medium]. I compared the expected side of 21 laws with the goldens they cite: 20 are byte-identical to the cited golden (or its store line, or its stdout before the harness's store dump), and `run_list_two` is two lines that occur in `list_plain.out`, as its comment says [Reproduced, High]. No law was ever deleted from `LAWS.bend` in its 25 commits; two commits on 2026-09-20 changed law bodies, and the one I diffed only added an empty write list to the expected `Outcome` when the type gained that field [Git-observed, High]. `LAWS.bend` is "HUMAN-OWNED" by its header and by `.github/CODEOWNERS`, but 24 of its 25 commits carry a Claude co-author trailer [Git-observed, High]; the header allows agents to add laws.

**What the law layer does not cover.** The checker's evaluator is not any of the four executors, so a law says nothing about the C or JS builds (the README says the same). The repository's `PLAN §7` and the header of `LAWS.bend` promise a round-trip law `decode(encode(x)) == x`; none exists, and bead `bb-7bm` ("Flagship law: the store codec round trip and Store.text idempotence, quantified") is open, as is `bb-0au` ("Quantified laws the spec names") and `bb-9eh` (`law-mutation.sh` STRONG for the two fast twins, i.e. checking that the laws fail when a twin is broken) [Verified, High].

**Dependencies and safety.** No Rust, no `Cargo.toml`, no crates [Verified absence, High]. Zero `@unsafe` in `port/` [Verified absence, High]. The C effects use Bend runtime internals with "no ABI promise" (`PLAN §8`) [Maintainer claim, High]. The harness scripts are copies from a `porting-to-bend2` skill (`scripts/ORIGIN.md`) [Verified, High].

**Scale.** 3,759 tracked files, of which 3,572 are under `goldens/` (1,094 `.out`/`.err`/`.exit` triples, 195 fixtures, 74 scenarios) [Counted, High]. Building the native binary takes 19.0 to 23.6 GB and about 5 minutes for C emission plus 5.7 to 6.0 GB and about 6 minutes for clang; the JS bundle 13.8 to 16.5 GB [Maintainer claim, Medium].

## 4.6 Comparison: who owns the lane

The lane, a local-first JSONL issue tracker that agents drive, is owned by **`br` itself** (beads_rust, 1,107 stars, releases through v0.7.0 on 2026-09-24) and upstream by Steve Yegge's **beads** (now `gastownhall/beads`, 27,405 stars, Go) [External, High]. `br` wins today for every reason the README lists: it is the working tool, it has the SQLite store, locks, atomic publication, TOON and Rich output, and the maintainer uses it daily. beads_bend concedes this directly ("When to use `br`: always, today") [Maintainer claim, High]. The lane beads_bend actually occupies is a different one: **a worked, public example of porting a real stateful CLI into a proof-checked language under an oracle-and-goldens discipline**. Adjacent work in that lane exists but is smaller: Bend 2 projects that state laws on single examples (the `rootagi/bend-json` issue "Laws are single examples, not general properties", 2026-09-19, makes the same observation about that project), a SHA-256-in-Bend repository with a functional-correctness proof against a separate FIPS spec (`Giulio2002/bend-sha256`), and the maintainer's own sibling port `toon_bend` [External, Medium; from search results, not audited]. I found no other public port of a real multi-command CLI to Bend 2 with a comparable golden corpus; with search recall this thin, that absence is weak evidence [Inference, Low].

## 4.7 Technical merit and adversarial review

**Strengths.** (1) The oracle discipline is real and checkable. The oracle is a hash-pinned release binary rather than a source build that moves under concurrent edits (the README notes the live `beads_rust` tree is 271 commits past the pin); I confirmed the hash and tag [Reproduced, High]; every golden's digest matches [Reproduced, High]; and the goldens are `br`'s actual bytes on 804 of 813 cases I could re-derive, with every difference already registered or clock-bound [Reproduced, High]. (2) Nondeterminism in the original is handled by measurement, not assumption: a repeat-3 "floor" run of the original over every batch, one-of-a-kind canonicalizers that touch only the registered leaks (DISC-005 for the ambiguous-id order, DISC-006 for version metadata), and OPEN entries for the draws still unhandled (DISC-010, -011, -012) [Code-verified for the canonicalizers, High; floor results Maintainer claim, Medium]. (3) The claims vocabulary is disciplined and mostly honored in the README body: "proved", "golden-tested" and "measured" have fixed meanings, the parity-claim template is stated and left unfilled because nothing qualifies yet, and the performance section is an honest zero [Verified, High]. (4) The spec is large and machine-linked: 909 clauses, each citing cases, with a blind self-containment review that predicted 10 of 10 sampled cases byte for byte from the spec alone [Reproduced for the lint, High; review result Maintainer claim, Medium].

**Weaknesses.** (1) "Law-proved" is the headline and the weakest layer. All 73 proofs are `{==}` by evaluation; 72 laws are single examples and the one universally quantified law binds two identity functions [Counted, High]. That is a set of compile-time regression tests evaluated by the checker, useful but no stronger in kind than the goldens, and weaker in coverage (73 examples against 1,094 cases). The word appears in the GitHub description and in the README's framing, while the README's own table concedes "no quantified one". (2) The evidence is maintainer-local. There is no CI of any kind (no workflow files; `.github/` holds only `CODEOWNERS`; the Actions API reports 0 runs) [Verified absence, High], so every lane verdict is a pasted line from a 30 GB shared Linux host. (3) Documentation drifts inside a single day's work: law count (73 vs 68), rounds (13 vs 11), fixtures (195 vs 163), exit-code counts (1,094-case vs 1,009-case corpus), arch-lint (FAIL on 774 clauses vs "PASS" on 764), and a parity board whose header is a day old and whose coverage tables are unfilled template rows, one of them reading `PASS` [Verified, High]. (4) Governance roles are nominal. CODEOWNERS assigns every role to one account; DISC acceptances were decided by the porting agent under the owner's blanket delegation; "non-author" find-fix rounds are fresh agent sessions [Verified, High]. (5) Cost: the proof book needs about 12 GB and 9 minutes, the native build about 24 GB, and the interpreter lane about 90 hours, so the full gate has never run on the current code [Maintainer claim, Medium].

**Bear-case steelman.** beads_bend does not matter. It re-implements a subset of a tool that already works, excludes the parts that make `br` safe under a swarm (locks, atomic writes, the database), and tells its own readers not to use it. Its proof layer, the thing that distinguishes it from any other golden-tested port, proves nothing general: 72 examples and a placeholder. Everything that carries weight (the golden corpus, the sandbox, the floor, the discrepancy register) is ordinary differential testing that could have been done in Rust against `br` with no new language, and the Bend-specific costs (24 GB builds, a 90-hour lane, a runtime with no rename or fsync) are paid for a proof story not yet told. Five days in, with no CI, no release and a single maintainer directing agents, it is a lab notebook.

## 4.10 Wardley placement

- **Commodity surface:** the `br --no-db` contract itself: `.beads/issues.jsonl`, the `--json` envelopes, exit codes. Standardized by `br`; the port copies it byte for byte. Moves only when `br` changes (v0.7.0 already has).
- **Custom-built reimplementation:** the Bend core and shell, and the harness (sandbox, capture, floor, conform, lanes). Custom, pre-product. What would move it: a release artifact, CI running the lanes, and a second user.
- **Genesis-stage elements:** (a) quantified `fast == spec` laws over a real CLI's data structures, which do not exist yet; (b) the pairing of hash-pinned oracle capture with a proof-checked target, which exists as method. Moving (a) from genesis to custom needs the first quantified law over the store codec (bead `bb-7bm`); moving (b) needs a port by someone other than this maintainer that reuses the harness.

## 4.11 Trajectory (12 / 24 / 60 months) [Inference]

**Base case.** The port reaches its own parity gate within weeks (the remaining work is owner decisions and one long lane run), stays unreleased, and its lessons keep flowing into the `porting-to-bend2` skill, as the README says happened on 2026-09-22. The pin ages: `br` moved to v0.7.0 four days after the port started, and each re-pin means a re-capture and a re-run of every lane. At 12 months the repository is most likely a finished case study referenced by the skill; at 24 to 60 months its value depends on whether Bend 2 becomes a language anyone ships in.

**Upside.** A quantified round-trip law over the store codec and quantified `fast == spec` laws for the BLOCKED relation land and check in reasonable time; the law layer then earns the word "proved", and the project becomes the reference example for proof-carrying ports. A second, independent party reruns the lanes from the published harness.

**Decay.** The laws stay closed examples, the proof book's cost grows with each one (it went from 11.4 GB at 61 laws to 12.5 GB at 73 [Maintainer claim, Medium]), the interpreter lane is never run in full, and the documents keep drifting from the gate lines. The repository then reads as a thorough golden-testing harness wrapped in proof vocabulary.

**Revisit triggers.** (1) The first law with a `for` binder over port data (bead `bb-7bm` or `bb-0au` closed). (2) `lanes.sh` PASS once, end to end, including the interpreter (bead `bb-wjk`). (3) Any CI workflow that runs a lane. (4) `converge.sh` `CONVERGED`. (5) A tagged release. (6) A re-pin to `br` v0.7.0 or later. (7) Anyone other than the maintainer's agents reproducing a lane.

## 4.12 Limitations and open questions

**Not done.** Bend was not installed, so `PROOF.bend` was not checked and no lane was run; every port-side pass count here is the maintainer's. The sandbox was not run (bubblewrap is Linux-only); 281 goldens were not re-derived: 187 that change the store (they need the pinned clock) and 94 that use scenarios, a pinned `@time`, or the harness's file, env, cwd, listing or no-workspace modes. The re-derivation used a different platform build of `br` than the pinned oracle (same commit), outside the sandbox. `claims-lint.sh` did not finish in 300 s. The spec was read only at its head and through lint; its `file:line` provenance against `br`'s v0.6.0 source was not checked. `port/core/` was read at the level of the laws, the shell, and the modules they name, not line by line. `perf/` numbers were not reproduced (none are claimed). The license was not diffed against `br`'s. Search recall for third-party coverage of a five-day-old, 5-star repository is thin; the only outside mentions found were a listing in `777genius/awesome-bend` and one fork.

**Open questions that would most change the verdict.** (1) Does `bend port/PROOF.bend` print `All terms check.` at the pin on bend 2.0.20, and in what time? (2) Can a quantified law over the store codec or the BLOCKED relation be proved in this code base at all, at a checking cost the host can bear? (3) Would `law-mutation.sh` show the 17 closed `fast == spec` laws fail when a fast twin is deliberately broken (bead `bb-9eh`)? If not, they are weak even as examples. (4) Does the full interpreter lane pass? (5) Does the spec twin build (`BEADS_RUST_SPEC=1`) still pass the current 1,094-case corpus?

## The eight deepening questions

1. **Provenance.** The repository records provenance for the oracle side with care: `goldens/MANIFEST.txt` carries the capture time, the exact argv, the wrapper's sha256, the case-table sha256 and a sha256 per golden file, and re-captures need a stated `--repin` reason or a DISC id [Verified, High]. The weak link is the host: the manifest names paths on the maintainer's Linux machine, the oracle binary's hash lives in PLAN §2 rather than in the manifest, and no gate line is signed or produced by a third-party runner. Portable attestation would need the capture and lane runs executed in CI, or a signed evidence bundle; `scripts/evidence-bundle.sh` and `assets/templates/evidence-pack/` exist as templates for exactly that, and no bundle is committed [Verified absence, High]; the oracle's sha256 does not appear in `MANIFEST.txt` [Verified absence, High].

2. **The embeddable unit.** The smallest useful piece is the harness, not the Bend code: `scripts/ws-run.sh` and `ws_inner.py` (bubblewrap, tmpfs, cleared environment, libfaketime-pinned instant, canonicalizers limited to registered leaks), `golden-capture.sh`, `floor.sh` and `conform.sh`. They are language-agnostic and would test any port of any stateful CLI against a pinned binary. Adoption cost is low in engineering terms and high in license terms (the rider travels with them). Of the Bend code, `core/sha256.bend` with its three FIPS vectors is the most self-contained piece.

3. **Unexercised option value.** Three options sit unused. First, the checker could prove quantified properties; the laws file already names the kinds (round trip, conservation) and none is stated beyond examples. Second, Bend's GPU lane: the harness has a gpu lane recorded `MISSING` for lack of a device, and the port has no GPU construct yet ("no device, no bang", `docs/FEATURE_PARITY.md`) [Maintainer claim, Medium]. Third, the parallel store load (`Store.load_fast`) exists behind a kill switch with no measurement of whether 8 threads help (EXP-002 is `RUNNING` with no capture).

4. **Benchmark honesty.** No performance number is claimed, and the exploratory timings are labeled as such in every card; that would survive any rerun because there is nothing to refute. The load-bearing numbers are conformance counts. 1,092 of the 1,094 passes are plausibly stable; the other two pass on the original's coin flip, which the README says. The goldens themselves survived an independent rerun in this packet (804 of 813 read-only cases, every difference explained). The proof-book figures (12.5 GB, 529 s) are load-bearing for feasibility and were not rerun.

5. **The governance path.** There is none beyond the maintainer. Every CODEOWNERS role is one account, contributions are refused, and "owner approval" of a discrepancy is a standing delegation to the agent doing the work. If velocity decays, the first thing to break is the pin: `br` v0.7.0 already exists, and a re-pin means re-capturing 1,094 cases and re-running three lanes at about 24 GB each; the second is the documentation, which already lags the gates by hours.

6. **The license as strategy.** The rider withholds rights from Restricted Parties (OpenAI, Anthropic, their affiliates and those acting for them), including their use of the software in ML training or evaluation pipelines. It is not a blanket ML-use ban on anyone else, and it does not bar people who use those companies' models, which matters here because 122 of 129 commits name a Claude model as co-author. The exclusion costs this project little as a product (it tells users to run `br`), but it cuts against the project's stated purpose, an experiment about agent-built, law-checked software: the evaluation-harness clause keeps the corpus out of exactly the kind of benchmark where a 1,094-case, oracle-pinned porting task would be most useful to others [Inference, Medium].

7. **Agent-era fit.** The workload that would pick beads_bend over `br` is not issue tracking; it is porting. An agent asked to move a stateful CLI into a language with a proof checker could reuse the sandbox, the capture discipline, the DISC and OQ registers and the claims vocabulary as a ready procedure. For that to be true, the harness would need to run without the maintainer's host paths and memory budget, and the method would need at least one quantified law to show the proof half works at this scale.

8. **The kill test.** Try to state and prove a quantified law of the form "for every store value, loading its written text gives back the same value" (the codec round trip `PLAN §7` promises, bead `bb-7bm`) under bend 2.0.20 within the host's memory. If it cannot be proved, or checks only at a cost the 30 GB host cannot pay, the "law-proved" thesis fails for real-tool ports in Bend at this version, and what remains is a well-run golden-testing harness. If it proves, the thesis stands for the first time.

## Cross-cutting lenses

- **Decoupling.** The project decouples a tool's contract from its implementation language: `br --no-db`'s bytes are captured once and any executor is judged against them. It also separates the two kinds of evidence (empirical goldens, checked laws) and names which one each claim rests on [Verified, High].
- **Methodology export.** If the port fails, the harness and the vocabulary survive, and have already been exported to the `porting-to-bend2` skill (README, "What This Port Fed Back into the Method") [Maintainer claim, Medium]. This is the most likely survivor [Inference, Medium].
- **The asupersync question.** Not applicable: there is no Rust in the repository and no dependency manifest of any kind besides the Bend imports [Verified absence, High].
- **The rider question.** Covered in §4.8 and question 6.
