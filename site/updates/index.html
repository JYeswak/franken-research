Since the pin

Every one of the 44 assessments was pinned September 22, 2026 (the assessed commit), and says nothing about what happened next. The suite kept moving. This page records the movement without rewriting a single verdict: a read-only census of every repository two days later, and a dated re-check wherever a verdict cell could change.

Six definitions. The pin is the exact commit an assessment froze on; every claim is evaluated at the pin, not at a later HEAD (the newest commit). TRL is technology readiness level, scored 1 to 9. NODUS is the program's four-ring verdict scale (Invest, Pilot, Explore, Monitor). CI is continuous integration: automated checks that run on every push. The rider is the license clause withholding all rights, including benchmarking and testing, from OpenAI, Anthropic, their affiliates, and anyone acting for them. Bus factor is how many people would have to leave before a project stalls.

Live watchChecked every day, filed as issues

Watched daily by a GitHub Action: see the latest census and the changes open for triage.

Every day at 11:23 UTC a scheduled workflow reads all 44 repositories through the GitHub API and compares each with its pin and with the previous day. It writes a census, and opens an issue labelled watch for any change that could move a matrix cell: a new release or tag, a license edit, workflow files removed or appearing where there were none, archiving, a rename, a deletion, a rewritten pin, or a new franken or Rust repository. New commits and added workflow files are counted in the census but never filed.

Each issue then goes through the same loop: triage (could this move a cell?), a dated re-check under updates/ if it could, a review of that re-check by a separate agent session, any new practice added to the rigor table, and a close that links all of it. The watch reports and never edits a verdict. The rules are in updates/METHOD.md, and what the watch reads is in watch/README.md.

Why pinsA verdict needs a fixed object

Some of these repositories take dozens of commits a day. A finding about "the repo" with no commit attached is out of date before anyone reads it, and nobody can check it. So every packet names one commit and its date, and every claim in it is about that commit. When the code moves, the packet stays true about what it read; it just stops being the newest reading.

The response to movement is a new, dated file beside the old one, never an edit to the old one. A re-check pins its own commit, uses the same evidence tiers, and says for each matrix cell whether it would change and why. The published suite counts stay as they were on September 22; if a re-check would move one, it says so in its own text and leaves the count alone. The full rules are in updates/METHOD.md.

Dated re-checkfranken_code_browser shipped a notarized developer preview

At the pin, franken_code_browser was ten days old, had no release, no CI, and a README that disavowed any application. The next day, 2026-09-23, its maintainer published v0.1.0, an Apple Silicon disk image containing a signed, Apple-notarized Mac app, alongside a checksum-verifying install script and a Homebrew cask. He reports submitting a sandboxed Mac App Store build for review the same evening. Shipping a notarized app eleven days after creating the repository is a real event, and it is the first revisit trigger the packet named. The app source was not written after the pin, though: it was imported in one commit from a private history, which the packet had noted was missing.

We re-checked it at the release commit, c7c5310, with the release artifact itself: download, hash, signature, Gatekeeper, and notarization ticket, all read-only. We did not launch the app.

Dated re-checkfrankengit deleted 71 of its 78 workflow files

At the pin, frankengit had 78 workflow files and no pass or fail on record for the pinned commit. Four hours later, commit 53776f9b deleted 71 of them and set the 7 it kept to run only when someone starts them by hand. Their check steps call the repository's own scripts/verify.sh; the other steps install the pinned toolchain, record the revision and compiler, or archive the source. An hour after that, a merge brought back one old single-use job that applies a patch to main, which makes 8. GitHub has recorded no workflow run of any kind since 2026-09-22 18:11 UTC.

The checks did not move somewhere new. Since 2026-08-20 the repository's own rules have said that workflow files are hand-started adapters and that the project "MUST NOT rely on GitHub-hosted Actions". At the pin all 78 files broke that rule. Nine could not even be parsed, and 6,828 of the repository's 7,204 Actions runs were instant failures from files like those; the 18 runs on the pinned commit were all of that kind, so no test ran against it. The repository has its own checker for the rule. We compiled it and ran it: 238 workflow errors at the pin, none at the removal commit, and 3 today, all in the file the merge brought back.
