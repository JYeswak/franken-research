Web search API layers

Adopt and wrap Confidence Medium Group Tools and environment Evidence as of 2026-09-23

Written by VerdictsTools Reviewed by ReviewTools on 2026-09-23

Bracketed tags are evidence tiers from RULEBOOK.md §1: [Verified] means checked directly, [CI-observed] read from a project’s CI pages, [Maintainer claim] asserted by the project, [External] a dated third-party source, [Inference] our judgment. A gold path:line link opens the cited line. TRL is technology readiness level, scored 1 to 9. CI is continuous integration: automated checks that run on every push. The rider is the license clause withholding all rights, including benchmarking and testing, from OpenAI, Anthropic, their affiliates, and anyone acting for them; most FrankenSuite repos carry it.

Bottom line

Inference, medium confidence: adopt an existing web search and extraction layer, either Firecrawl self-hosted (AGPL-3.0) or a commercial API (Tavily, Exa, SerpApi) through its official SDK, and wrap it with your own quality and latency checks. The ranking machinery in this category is closed, and no repository in the evidence publishes a relevance benchmark or a latency budget, so "the search is good" is something you have to measure yourself. Keep a frozen, hashed set of recorded queries and responses as your test oracle, and keep live vendor API tests in a separate lane behind secrets rather than in the required build.

Copy these practices

  • A labeled quality run on every merge, against what shipped: Firecrawl triggers an evaluation against production after each deploy, labeled with the commit and an experiment ID. Copy the plumbing and write your own ground truth. Starter kit: Receipts carry provenance; generation binding. [Verified] (ecosystem/pickup/_evidence/web-search-apis.md:22 Post-deploy quality-eval benchmark against production, labeled per commit)
  • On-demand evaluation from a review comment: a maintainer comment dispatches a quality eval, gated by organisation membership. Starter kit: none. [Verified] (ecosystem/pickup/_evidence/web-search-apis.md:23 Comment-triggered on-demand eval for PRs)
  • The search backend as a CI matrix axis: Firecrawl's self-hosted suite already makes the search backend a matrix axis, with one value today (SearXNG; Google disabled); add a second backend so a provider swap is proven, not assumed. Starter kit: none. [Verified] (ecosystem/pickup/_evidence/web-search-apis.md:24 parameterize the search backend as a matrix axis so a clean-room implementation proves provider-swap correctness in CI; ecosystem/pickup/_evidence/web-search-apis.md:24 search backend searxng (google disabled))
  • Unit tests with HTTP interception, live tests separate: split unit and integration directories and mock transport at the HTTP layer for unit tests. Starter kit: none. [Verified] (ecosystem/pickup/_evidence/web-search-apis.md:26 new project should mock transport at the HTTP layer for unit tests)
  • Every example executes in CI: Exa runs all its example scripts in CI, against live APIs with keys, so documentation cannot rot unnoticed; keep that lane out of the required build. Starter kit: Claim discipline enforced: README claims cross-checked against proofs. [Verified] (ecosystem/pickup/_evidence/web-search-apis.md:27 Docs-as-tests: every example executes in CI; ecosystem/pickup/_evidence/web-search-apis.md:27 run with EXA_API_KEY/OPENAI_API_KEY secrets against live APIs; ecosystem/pickup/pickup-web-search-apis.md:35 as oracles and never required for a green build)
  • Per-option end-to-end fixture files for extraction: Jina Reader boots its server and tests content fidelity, chunking, token budgets, error handling and option interactions one file each. Starter kit: none. [Verified] (ecosystem/pickup/_evidence/web-search-apis.md:28 For any extraction endpoint, this is the file-level template.)

Build only if

  • You need control of the index and ranking: that machinery is closed in every vendor, so no incumbent offers it; but an internet-scale index is a different project type, not a web search API layer. [Verified] (ecosystem/pickup/_evidence/web-search-apis.md:36 lives inside Tavily/Exa/SerpApi/Brave/Perplexity and is not open; ecosystem/pickup/pickup-web-search-apis.md:25 Building a web index or crawler at internet scale)
  • A key-free, self-hosted requirement alone does not justify building, because Firecrawl ships a self-host path. Firecrawl and SearXNG are both AGPL-3.0 (fresh read 2026-09-23, gh api repos/<owner>/<repo> --jq .license.spdx_id); a builder who cannot accept AGPL source obligations for a modified network service still has AGPL-free adoption paths to try first: the commercial APIs through their MIT SDKs, Jina Reader (Apache-2.0) for extraction, Firecrawl's own SDKs, which are MIT, and running Firecrawl unmodified as a separate service. Only if none of those fits does the AGPL constraint justify building, and a clean-room verdict would still have to quote the clause. The other adopted repositories read MIT or Apache-2.0 in the same read. Revisit when

  • A vendor-independent relevance benchmark for agent search is published, or Firecrawl documents its scoring method.
  • Any incumbent publishes and gates a latency budget.
  • Firecrawl's self-host footprint turns out to block a real deployment, or Firecrawl or SearXNG changes license.
