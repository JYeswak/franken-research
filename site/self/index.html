Graded by our own method

Franken Research assessed 44 repositories from Jeffrey Emanuel's FrankenSuite and reported, among other things, how few of them could show a passing automated build, a release, a license without restrictions, or a second maintainer. A project that publishes those findings should pass the same checks, in public, or say where it does not. This page scores this repository on the same columns as the master matrix in synthesis/00-overview.md, with the same evidence tiers.

Six definitions. TRL is technology readiness level, scored 1 to 9. NODUS is the program's four-ring verdict scale (Invest, Pilot, Explore, Monitor). CI is continuous integration: automated checks that run on every push. The pin is the exact commit an assessment froze on; every claim is evaluated at the pin, not at a later HEAD. The rider is the license clause withholding all rights, including benchmarking and testing, from OpenAI, Anthropic, their affiliates, and anyone acting for them; most of the assessed repos carry it. Bus factor is how many people would have to leave before a project stalls.

ReproduceRun the gate chain yourself

You need git, Bun, python3, node, and Google Chrome or Chromium. The render gate finds Chrome in the usual install locations; set CHROME_PATH if yours lives elsewhere. No network access is used after the install.

git clone https://github.com/JYeswak/franken-research.git
cd franken-research
bun install --frozen-lockfile
bun run verify
# optional: prove the committed 3D map bundle is what its source builds
bun run build:map
git diff --exit-code site/assets/app.bundle.js

The chain prints PASS or FAIL for eleven gates and exits nonzero on any failure. They check that the shipped packets and Rulebook are byte-identical to the canonical copies; that every method-page citation resolves to a real claim-table line; that every suite number on the site is computed from the data rather than typed in; that the six terms above are defined before first use on every page; that every brief pairs with exactly one packet; that every internal link and anchor resolves offline; that every referenced file ships; that pages stay keyboard-operable with no-JS fallbacks; that copy passes a slop scan; that five representative pages, this one included, render in headless Chrome at desktop and phone widths with zero console errors and zero horizontal overflow; and that no removed scaffolding is referenced. The full list, with the reason for each gate, is in BUILD-GATES.md; the script is scripts/verify-site.sh.

What the gates do not proveThey prove the site says what the packets say, consistently and reachably. They do not prove the packets are right. A verdict is only as good as the reading behind it; to test one, follow Reproduce a verdict against a real repository at its pin.

Known gapsWhat we got wrong, or cannot prove

  • Our own mechanism ran ahead of execution, for a while. The second headline finding says the suite's checks often exist without running where it matters. When this page was first written, the verify workflow existed but had never run on GitHub, because the repository had not yet been pushed. Its first run, on commit 527c227, passed every step: the secret scan of the tree and its history, the check that the map bundle equals what its source builds, and all eleven gates (run 35944707134). Commit hashes in this repository changed in a history rewrite on 2026-09-23 that removed email addresses; CI runs from before it show the old hashes, and the old-to-new map links them. One green run is a start, not a track record. [CI-observed, High]
  • Two gate summary lines printed a blank count. The statistics gate and the link gate reported "( data-stat slots checked)" and "( links)" on macOS, because the count was extracted with a GNU-only grep flag. Both gates were still checking; only the summary lied by omission. Fixed in this release, and an empty scan set now fails instead of passing.
  • Readiness and ring are judgment calls. Every TRL and NODUS placement in the corpus is labeled [Inference, Medium], ours included. Reasonable readers will place some repos a ring differently.
  • Only one verdict rests on re-executed tests. For the other repos the evidence is reading the code at the pin, CI pages, and release APIs. That is stated in each packet's method section, but it bounds how strong any single verdict can be.
  • Two CI taxonomies disagree by one repo. The site's data files frankenjax as private-only CI, while the synthesis matrix files it as having no test CI. The reclassification is disclosed on the method page; it moves no headline number.
  • The corpus is a snapshot. Everything was assessed on 2026-09-22 at each repo's pin. The FrankenSuite moves fast, and some findings will be stale by the time you read them. Staleness is a finding, not an error, but check the pin date before quoting a verdict.
  • We changed the as-shipped packets once. Maintainer commit email addresses quoted from public git metadata were redacted from the packets, their site copies, and one synthesis brief before publication. No other evidence text was edited.
