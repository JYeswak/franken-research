## 2. Execution-readiness gates (verbatim)

The clearest gate ritual lives in `docs/planning/PHASE2C_EXTRACTION_PACKET.md` §6 "Per-Ticket Extraction Schema (Mandatory Fields)" and §10 "Packet Readiness Rubric":

- §6: [Verified] Every `FJ-P2C-*` packet MUST include: 1. `packet_id` 2. `legacy_paths` 3. `legacy_symbols` 4. `ir_contract` 5. `transform_contract` 6. `dispatch_effect_contract` 7. `cache_backend_contract` 8. `error_contract` 9. `strict_mode_policy` 10. `hardened_mode_policy` 11. `excluded_scope` 12. `oracle_tests` 13. `performance_sentinels` 14. `compatibility_risks` 15. `raptorq_artifacts`. **"Missing fields => packet state `NOT READY`."**
- §10: [Verified] "Packet is `READY_FOR_IMPL` only when: 1. extraction schema complete, 2. fixture manifest includes happy/edge/adversarial paths, 3. strict/hardened gates are machine-checkable, 4. risk note includes compatibility + security mitigations, 5. parity report has RaptorQ sidecar + decode proof."
- §7 risk tiering: [Verified] Critical tickets "must pass strict drift `0`" (e.g. `FJ-P2C-001` Jaxpr/Tracer invariants, gate: "jaxpr invariant replay").
- §2 packet template: [Verified] each ticket must deliver "all artifacts in the same PR": `legacy_anchor_map.md`, `contract_table.md`, `fixture_manifest.json`, `parity_gate.yaml`, `risk_note.md` — a "definition of done" baked into the handoff format.
- `PLAN_TO_PORT_JAX_TO_RUST.md` §5: [Verified] every phase (A–E) has explicit "Exit criteria" (e.g. Phase B: "End-to-end deterministic dispatch for scoped scalar programs. Cache key is deterministic and strict-mode fail-closed behavior enforced. Conformance harness emits machine-readable parity report skeleton.").
- `TODO_SUPER_DETAILED_PORT_AND_PARITY.md` RCB11 "Validation checklist for this planning/bead phase": [Verified] re-run `br dep cycles --json` (result: no cycles), `br ready --json`, `bv --robot-triage`, `git diff --check`, commit + push + mirror to `master`. RC9 adds per-session landing gates: `cargo fmt --check`, `cargo check --workspace --all-targets`, `cargo clippy --all-targets -- -D warnings`, targeted tests, `cargo test --workspace`, close beads, leave unfinished beads "open with exact next steps".
- Beads Workflow Integration (AGENTS.md): [Verified] "Before ending any session, run this checklist:" `git status`, `br sync --flush-only`, `git add .beads/`, commit, push.

**Distinctive:** the gates are *machine-checkable artifacts*, not human sign-offs. No human-in-the-loop approval step, no named second reviewer, no two-model adversarial review of plans appears anywhere; readiness is determined by artifact completeness checks (`READY_FOR_IMPL` / `NOT READY` packet states).

## 3. Honesty guardrails

- **Negative-evidence ledgers — present and central.** [Verified] `docs/NEGATIVE_EVIDENCE.md` (15,840 lines) with entries like "2026-07-09 - WIN 1.44x vs ORIG: DRAM-scale dense-f32 reciprocal donation (BlackThrush)" — each entry records the agent name, which *closed/rejected* lanes it consulted first ("Consulted this ledger first and avoided the closed/rejected `fj-lax` maxpool, softmax/log-softmax, cumsum/AD chain-cumsum..."), measured bench rows with worker IDs, and validation results. Canonical version: `evidence/perf/negative_evidence_ledger.md`, whose header states: "This ledger records code-first performance attempts and retry predicates so dead ends are not rediscovered without new evidence." Entries record "MEASURED NO-SHIP / SOURCE REVERTED" with retry predicates (e.g. "do not attempt SIMD-prefix or force-inline scan changes; resume only after..."). **[Inference]** Installed from very early on: perf evidence files date from 2026-02–06, i.e. present since the method-stack setup (M0 2026-02-13); the retry-predicate discipline is a planning rule, not an afterthought.
- **Claim matrix — [Absent] as a named artifact; present in functional form.** No file named claim-matrix exists, but the vision-evidence map is its machine-checked equivalent: [Verified] `scripts/bootstrap_vision_evidence_map.sh` "Scans FEATURE_PARITY.md and README.md, extracts claims, links to evidence artifacts and tests, emits JSON map with red/yellow/green status per claim"; the preview lists 22 claims, 19 green / 3 yellow / 0 red, with yellow claims annotated "Claimed green but no machine-verifiable evidence paths found". Exit code 1 if gaps found. **[Inference]** This is the claim-promotion/demotion machinery: claims degrade from `parity_green` to yellow when evidence paths go missing.
- **Auto-demotion rules — present, adversarial, maintainer-driven.** [Verified] The 2026-05-01 reality-check (TODO doc RCB0–RCB11, owned by a "Codex session") applied a `reality-check-for-project` skill "instead of jumping directly to implementation", ran "Ambition Round 1: make claims machine-checkable", "Ambition Round 2: promote parity claims only after oracle or fail-closed evidence", and produced a "reality-check gap tracker". Verbatim demotions in the follow-up program `frankenjax-fcxy.1` (all now closed): "Replace stale 846 fixture claims with live 848 fixture count", "Clarify TTL as auditable evidence/provenance rather than a formal semantic proof", "Downgrade TTL, dispatch composition, `vmap`, control flow, and RaptorQ rows where the next artifact is a real parity gap rather than routine expansion", "Keep declared V1 successes marked green only where live evidence supports them". **[Inference]** Demotion is ad-hoc maintainer judgment enforced through reality-check campaigns, not a codified auto-rule.
- **Reward-hacking guardrails — present by reference (suite-level), not duplicated.** [Verified] AGENTS.md RULE 0.5 binds this repo to suite-wide `/data/projects/AGENTS.md` "Named Reward-Hacking Patterns (ALL FORBIDDEN)" — 12 named patterns, "several already observed in this suite": "gate self-weakening (and the exact price of a legitimate gate fix), proof-class inflation, golden regeneration reflex, commit-stream pumping, tautological tests, easy-lever cherry-picking, close-pump abuse, scope-splitting, spec-editing as progress, conformance metastasis, dependency smuggling, bench-path hardcoding". - **Claim/promotion discipline in perf work:** [Verified] release_readiness_scorecard entries keep a running scorecard "0 wins / 2 losses / 0 neutral; 0 kept / 0 reverted" per pass, and AGENTS.md Perf Doctrine mandates the loop: baseline p50/p95/p99 + memory → profile → one optimization lever per change → behavior-isomorphism proof → rebaseline + delta artifact.

## 8. Maturity verdict

**Mature.** FrankenJAX has the most complete and most *executed* planning apparatus seen in this program so far: a normative master spec with acceptance gates, phase-gated execution plan with exit criteria, a ticket-packet system whose readiness rubric (15-field schema → `READY_FOR_IMPL`/`NOT READY`) was actually run across 8 extraction packets with all artifacts on disk, a 2,047-issue dependency-checked task graph that is 99% closed, an agent-operations manual (AGENTS.md, 866 lines) encoding deletion/irreversibility/multi-agent coordination discipline, and — most unusually — an institutionalized honesty infrastructure (negative-evidence ledgers with retry predicates, BOLD-VERIFY loss scorecards, machine-checked vision-evidence maps, adversarial DOC-PASS red-teams, reality-check recalibration campaigns that *downgrade* claims, stub/dead-claim audits, 12 named reward-hacking patterns). The one structural gap is externalization risk: the suite-wide rulebook that binds the repo (RULE 0.5, Work-Graph Discipline, 12 reward-hacking patterns) lives at `/data/projects/AGENTS.md` and the legacy oracle at `/dp/frankenjax/...`, neither of which is in the repo — the planning method is portable as documents, but its hard constraints partially live on the maintainer's host.
