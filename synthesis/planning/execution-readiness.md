# Execution-Readiness Gate Catalog (44 repos)

**Source:** all 44 per-repo planning profiles in this directory, read in full 2026-09-22.
**Tier key:** [Verified] = read in a repo file by the profile author. [Maintainer claim] = Emanuel's prose, quoted verbatim. [Inference] = analyst reasoning. [Absent] = searched for, not found.
**Counting rule:** a repo is listed only if its profile records the gate as present (functional equivalents explicitly identified by the profile count). Profiles marking a gate [Absent] or never mentioning it are excluded, so prevalences are floors over documented mechanisms, not guesses. Two repos — beads-for-frankentui and beads_for_franken_engine — are publish mirrors of bead graphs, not in-repo execution systems; they are excluded from executable-gate counts and noted where relevant. "The website trio" below always means frankensqlite_website, frankentui_website, and frankensim_website (franken_markdown_website is named separately). A full 44 × 23 repo × gate adjudication matrix is published as `.gate-matrix.md` (hidden working file); every prevalence figure in this catalog is recounted from it.
**Enforcement legend:** [M] = mechanically enforced (a script/hook/linter/CI rejects on violation). [D] = documented doctrine (prose rule; enforcement is agent obedience). [A] = aspirational (documented as not yet real).
**Tier scope:** tier tags mark verbatim quoted material and profile-author verdicts. Unquoted summaries elsewhere are analyst characterizations ([Inference] by default).

Missing any file => packet status `NOT_READY`."* Machine check: *"Non-zero exit means at least one packet is `NOT_READY`"*
(`validate_phase2c_artifacts`).
**PREVALENCE: 6/44** — franken_numpy, frankenjax, frankenpandas, frankenscipy, frankentorch, frankenredis.

## Gate 6 — Pre-commit / pre-edit executable gate

## Gate 7 — Oracle / differential / incumbent-comparison gate
**Definition:** the pinned incumbent (or spec oracle) is executed head-to-head; a self-speedup without the incumbent live in the same invocation is not a win.
**Example** (franken_lean, plan §3 D5/D8 + `AGENTS.md` Rule D8, [D][Verified]): *"Vendored Reference as oracle"* — upstream sources held byte-identical at the pin, used as differential oracle, fixture/census mine, and native input. Example (frankengit, `VERIFY_SPEC.md` §11, [D][Verified]): Git 2.54.0 sandboxed differential lane. Suite-wide honesty rule ([Maintainer claim], recurring): *"a **self-speedup is MAINTENANCE, not a win** — a win needs the incumbent live in the SAME invocation."*
**PREVALENCE: 21/44** — franken_engine, franken_lean, franken_markdown, franken_networkx, franken_nlp, franken_node, franken_numpy, franken_ocr, franken_overlap, franken_whisper, frankenfs, frankengit, frankenmermaid, frankenpandas, frankenredis, frankenscipy, frankensqlite, frankensympy, frankenterm, frankentorch, frankensearch.
**Absent/notable variants:** franken_snowflake (empirical goldens instead of differential), franken_surveillance_system (admission gates instead), franken_remote (verification lanes, no oracle), frankentui (self-audit against own math; no competitor comparison, [Absent]), frankensqlite_website and frankentui_website (removed from this gate in round 2: their only oracle-related evidence is a quoted AGENTS.md honesty *principle*, not an executed incumbent — a principle quoted in a website repo with no incumbent to run is doctrine, not a differential gate).
**Enforcement:** [M] in frankentorch (G3 gate), frankenmermaid (`.ci/quality-gates.toml`), frankentorch h2h benches; [D] elsewhere.

## Strongest-observed composite checklist (not a floor)

This is the composite of the strongest mechanisms observed anywhere in the suite — what a plan must pass before agents are set free *if it uses the suite's best-demonstrated machinery*. It is a composite maximum, not a floor: its items cite mechanisms present in 4/44 to 38/44 of repos, and a floor cannot consist of mechanisms absent in most of the population. For each item the prevalence is stated and the absent/inapplicable condition noted. The actual empirical common floor — mechanisms present in a majority of repos — follows separately.

1. **Pinned oracle.** The incumbent (or pinned spec/census) is fixed at a commit/SHA before work starts; behavior is extracted into executable artifacts, not summarized from memory. (Gate 7 — 21/44. Absent where there is no incumbent to run: websites, satellites; frankensnowflake uses empirical goldens, frankensurveillance admission gates, frankenremote verification lanes, frankentui self-audit instead.)
2. **Executable task graph.** All work is beads with typed dependencies; the graph is the plan of record; prose plans are rationale. (Gate 1 — 38/44. Absent in the four websites, franken_native_capsule, franken_overlap.)
3. **Ticket completeness.** Every ticket carries the mandatory schema; missing fields ⇒ `NOT READY`, checked by a script, not a reviewer. (Gate 2 — 6/44; machine-checked in 5/44, documented-but-unverified in frankenredis.)
4. **Phase exit criteria.** Named phases/workstreams with exit gates defined before agents start; a gate cannot pass on an unresolved blocker. (Gate 3 — 25/44, all [D].)
5. **Per-change gates.** Named toolchain commands (fmt, lint, tests, build) plus executable commit-time checks (hooks/preflight) that reject bad evidence rows. (Gate 5 — 21/44; Gate 6 — 10/44, of which 7 verify a rejecting hook/script/CI path, 2 are documented-but-unverified, 1 is advisory-by-default.)
6. **Receipt-bound evidence.** Every evidence artifact carries provenance (hash, worker, generation); a receipt from a different generation is not evidence. (Gate 8 — 31/44.)
7. **Claim discipline.** Public wording is bound to named proofs; prose cannot exceed evidence; approximation terms are banned or flagged. (Gate 9 — 22/44 documented; 7/44 mechanically enforced.)
8. **Negative-evidence ledger.** Losses and rejections are banked with retry predicates; reporting a loss is a success. (Gate 10 — 31/44 including 3 functional equivalents.)
9. **Demotion path.** Every claim has a defined downgrade. The strongest observed forms: automatic on SHA mismatch (frankengit), ratchet Block/Quarantine on bound regression (franken_ocr — designed/tested, contract TOMLs not yet live), expiry on staleness (frankentui 90-day `manual:`, franken_surveillance_system generation-change expiry), quarantine on contradiction (frankensympy — demotion-by-policy, reviewer-triggered). 30/44 have some demotion machinery; 5/44 verify a judgment-free mechanical path. (Gate 19 — absent in 14/44 including frankentorch.)
10. **Release gate.** Publication is blocked on incomplete producer evidence; certification clauses that cannot be waived are named. (Gate 4 — 26/44; [M] in 3.)
11. **Anti-reward-hacking law.** The 12 forbidden patterns are binding; gates are never weakened to land a change; gate changes require evidence in both directions. (Gate 18 — 29/44; bound by reference to the off-repo suite file, so enforcement is mostly agent obedience.)
12. **Meta-audit.** The honesty machinery audits itself: resurrection audits of ledgers, claim-coverage fractions, planted negatives, gate self-tests. (Gates 11+12+13+17 — 11/44, 8/44, 4/44, 7/44; the rarest layer and the suite's real differentiator.)

### The empirical common floor

Mechanisms present in a majority of repos, i.e. what the suite *typically* demonstrates rather than its best case: executable bead graph (38/44), receipt-bound evidence (31/44), negative-evidence ledger (31/44), demotion/expiry machinery (30/44), anti-reward-hacking doctrine (29/44), release gate (26/44), phase exit criteria (25/44). Everything else — packet schemas, pre-commit hooks, claim linters, resurrection audits, planted negatives, anti-ceremony doctrine — is minority practice: load-bearing where it exists, absent more often than not. In particular, mechanically *enforced* gates are the exception in every family; the documented doctrine is the floor, the machine is the ceiling.

## What contradicts the patterns

Every cross-suite pattern in this catalog has named counterexamples; the full list is in `planning-methodology.md` §5. The load-bearing ones: **plan-first is not universal** (6 repos run no prose plan); **dialectical review is a minority practice** (16/44); **demotion is absent** in 14/44 including frankentorch; **mechanical enforcement is the exception, not the rule** — most gates are documented doctrine, and frankentui_website's drifted AGENTS.md proves even the anti-drift rule can drift; **planning maturity does not predict execution honesty** (franken_node's bead-completion illusion, franken_networkx's corrected first audit, frankensim's false closes). A recurring pattern — not a universal law — is that repos instrument the failure mode and route the correction through the bead machinery that caused it (franken_node's 739 debt beads, frankentui's close-audit after the thin-close discovery, frankenscipy's rewritten bootstrap gate); frankentui_website's drifted AGENTS.md is the case where that answer demonstrably did not hold.
