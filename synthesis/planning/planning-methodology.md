# Planning Methodology — Consolidated Suite Pipeline (44 repos)

**Source:** all 44 per-repo planning profiles in this directory, read in full 2026-09-22.
**Tier key:** [Verified] = read in a repo file by the profile author. [Maintainer claim] = Emanuel's prose, quoted verbatim. [Inference] = analyst reasoning from artifacts. [Absent] = searched for, not found.
**Prevalence method:** counts below are repos where the profile records the mechanism as present (including functional equivalents explicitly identified). A profile that marks a mechanism [Absent] or never mentions it is not counted. Counts are therefore floors for documented mechanisms, not estimates of unmentioned practice. Every substantive claim carries repo + file path. A full 44 × 23 repo × gate adjudication matrix is published as `.gate-matrix.md` (hidden working file); every prevalence figure in this document is recounted from it.
**Tier scope:** tier tags mark verbatim quoted material and profile-author verdicts. Unquoted §2 summaries are analyst characterizations ([Inference] by default). "The website trio" means frankensqlite_website, frankentui_website, and frankensim_website (franken_markdown_website is named separately).

## 1. The consolidated capability stack

No single repo runs every stage. The stack below is the union of mechanism families observed across the suite — the maximal idea-to-execution-ready method the 44 repos collectively define. It is a taxonomy of observed mechanisms, not a sequence any single repo runs: stage ordering is not universal. Counter-evidence per profile: frankengit's research-provenance layer is retrospective-by-design (`RESEARCH_PROVENANCE.md`, 2026-08-20 — research documentation *follows* planning, frankengit.md §5); frankenredis's negative-evidence Policies 1–2 were installed 2026-07-27, mid-program, after ~a month of perf campaign (frankenredis.md §3); frankentui's close-audit machinery was installed *after* 188 no-reason closes and 859 very thin closes (frankentui.md §3) — reactive, not staged. frankensympy does install governance first (WS00), which is exactly why a universal layered pipeline is false as a cross-suite claim: the ordering holds for *some* repos.

**Stage 0 — Oracle anchoring.** Pin the incumbent as the source of truth before writing code. 21/44 repos run an oracle/differential/incumbent-comparison gate (franken_lean: *"Vendored Reference as oracle… differential oracle"*, `AGENTS.md` Rule D8, franken_lean profile; frankentorch: *"Differential parity green for full drop-in target surface"*, `docs/planning/PLAN_TO_PORT_PYTORCH_TO_RUST.md` §6; frankengit: Git 2.54.0 sandboxed differential lane, `VERIFY_SPEC.md` §11). Pinned-source censuses exist where oracles can't be executed (franken_ocr, `docs/truth-pack/CENSUS.md`: census self-corrected 2,229 → 2,244 modules).

**Stage 1 — Normative plan/spec.** A written, versioned plan or spec is the execution prerequisite. Phase/workstream exit gates documented in 25/44 (franken_overlap removed in round 2: its profile marks "Definition of done for plan phases" [Absent], franken_overlap.md:129). Examples: franken_nlp v5.0 plan §11 (*"No phase gate may claim a result whose transitive dependency closure contains an unresolved [OPEN]"*); frankensqlite's 18,208-line comprehensive spec, which explicitly declares itself a *"target specification, not an execution receipt"* (`docs/planning/COMPREHENSIVE_SPEC_FOR_FRANKENSQLITE_V1.md`). Counter-pattern: the four website repos (franken_markdown_website, frankensim_website, frankentui_website, frankensqlite_website), the externally-governed satellite franken_native_capsule, and franken_agent_detection run no prose plan at all (§5). franken_overlap is the adjacent case: it *does* have a prose plan — the 15 KB master design document `COMPREHENSIVE_PLAN_FOR_FRANKEN_OVERLAP.md` ([Verified], franken_overlap.md artifact inventory) — but no plan-readiness gate and no beads/trackers: evidence-first planning with ungated waves.

**Stage 2 — Packetization.** Research is converted into machine-checkable tickets. 6/44 document a mandatory packet schema where missing fields mean `NOT READY`: franken_numpy, frankenjax, frankenpandas, frankenscipy, frankentorch, frankenredis — of which 5 verify a machine enforcer; frankenredis is [D] (normative prose in `PHASE2C_EXTRACTION_PACKET.md` §6, no enforcer verified). Verbatim (frankentorch, `artifacts/phase2c/SCHEMA_LOCK_V1.md`, [Verified]): *"Missing any file => packet status `NOT_READY`"* and *"Machine-check command: `cargo run -p ft-conformance --bin validate_phase2c_artifacts`. Non-zero exit means at least one packet is `NOT_READY`."* frankensympy adds a mandatory plan-to-Beads conversion schema, CI-linted by `tools/validate_planning.py`.

**Stage 3 — Executable task graph.** The Beads dependency graph is the plan of record in 38/44 (`.beads/issues.jsonl` or `beads.sqlite3`; JSONL is truth, sqlite disposable). Scale ranges from 16 issues (franken_agent_detection) to 12,745 (asupersync). Two repos — beads-for-frankentui (2,590 nodes) and beads_for_franken_engine (1,180 nodes) — are publish mirrors of graphs, not in-repo execution systems. Absent in: franken_markdown_website, franken_native_capsule, franken_overlap, frankensim_website ([Absent] — its `public/beads/` is a display export of frankensim's graph, frankensim_website.md:126).

**Stage 4 — Per-change gates.** Toolchain gates (fmt/lint/test/build) documented in 21/44; executable commit-time gates (pre-commit hooks, pre-edit blocks) in 10/44 — of which 7 verify a rejecting hook/script/CI path ([M]), 2 are documented-but-unverified ([D]: franken_lean, franken_tts), and frankensim is advisory-by-default (frankensqlite_website and frankentui_website excluded in round 3: their AGENTS.md `ubs` instruction is a security bug-scan, not an evidence-condition gate per the Gate 6 definition). Verbatim (franken_whisper, `examples/ledger_preflight.rs` + `.githooks/pre-commit`, [Verified]): invalid evidence rows are blocked at pre-commit with exit 2. Verbatim (frankensim, `scripts/hooks/pre-commit`, [Verified]): *"pure shell — no cargo, no build"* — deliberately advisory by default (warns and lets the commit through) because *"a hook that builds the workspace is a hook that gets bypassed with `--no-verify` on its second use"*; `FRANKENSIM_HOOK_STRICT=1` makes it refuse.

**Stage 5 — Evidence and claim discipline.** 22/44 run a *documented* claim/evidence-discipline mechanism (matrix, ledger, guard, linter, or policy); 7/44 verify mechanical enforcement (frankensympy CI claims linter, frankentui `check_readme_claims.py --proof-refs`, franken_markdown self-proving gate script, frankengit SHA-bound rows, frankensqlite gate code, franken_manim claim token, frankenterm taxonomy line + hedge test). 31/44 bind evidence to receipts with provenance (hashes, worker identity, generation binding). 31/44 keep a negative-evidence ledger (including 3 profile-identified functional equivalents: franken_remote, frankensim, frankentui); 11/44 then audit the ledger itself (ledger resurrection); 8/44 run claim-coverage audits measuring how many claims are actually attested. Verbatim (frankenterm, `docs/reality-check-bridge-plan-2026-09-01.md` §4b, [Verified]): *"Generation binding. Every receipt records `commit`, `cli_version`, `mux_version`/`app_version`, `codec_version`, `host`, and the worker for remote lanes. A receipt from a different generation than the release under test is not evidence for that release."*

**Stage 6 — Independent review.** 16/44 run a dialectical or independent-review mechanism (rival plans, duels, adversarial reviews, named-agent separation of powers, external reviews). The majority (28/44) have no two-model dialectic; where "adversarial" appears it usually means adversarial *fixtures*, not reviewers (frankentorch, [Verified]).

**Stage 7 — Release gate.** 26/44 have a release/publication/sign-off gate. Strongest forms are machine-enforced: frankenterm's attestation build *"fails loudly"* on missing artifacts (`docs/release/attestation-checklist.md`, [Verified]: *"Incomplete producer evidence MUST block publication"*); frankentui's `docs/pane-release-gate-policy.md` ([Verified]): *"The pane workspace ships only on an **objective, automated** verdict — never on subjective confidence"*; frankentorch's G8 readiness sign-off with residual-risk register (`artifacts/phase2c/READINESS_DRILL_SIGNOFF_V1.md`).

**Stage 8 — Post-release drift/demotion.** 30/44 have some demotion/expiry/drift machinery (5/44 verify a judgment-free mechanical path; the rest are procedural); 4/44 plant negatives in acceptance criteria; 7/44 self-attack their gates (mutation batteries, deliberately broken gates, fabricated-proof fixtures); 4/44 run anti-ceremony doctrine (franken_engine, franken_threed, franken_tts, frankentui).

## 3. Mechanically enforced vs documented/aspirational

## 4. What the capability stack guarantees — and what it does not

**What it guarantees (when the mechanical subset is actually wired):**
- **Traceability.** Every public claim can be chased to a named proof artifact (test, receipt, hash, bead). The suite's strongest form: frankenterm's generation-bound receipts, frankentui's proof grammar, frankengit's SHA-bound claims.
- **Falsification is first-class.** Losses, rejections, and retractions are banked as permanent artifacts (31/44 keep negative-evidence ledgers; the norm *"reporting a loss is a success — one line, revert, next lever, no retraction narrative"* is one of the three load-bearing Rule 0.5 rules bound in 29/44 — Gate 18 — though whether agents live the norm is [Inference], not measured).
- **Drift is detectable.** Expiry (frankentui 90-day `manual:`, franken_nlp revalidation triggers, franken_surveillance generation-change expiry), resurrection audits (11/44 re-adjudicate their own ledgers), and claim-coverage audits (8/44 measure attested fraction) make staleness visible.
- **Gates resist weakening.** The 12-pattern taxonomy names gate self-weakening as forbidden (29/44); frankenfs requires evidence for gate changes *in both directions* (newly admitted and still-rejected cases); frankenredis requires deliberately breaking a new gate in a scratch copy.
- **Closure requires evidence.** Close-time policies (frankentui, frankenlibc, franken_agent_detection) make "done" a checkable state, not a belief. frankentui's rationale, verbatim: *"A step you can satisfy by believing you did it is not a step."*
- **False-closure repair.** A distinct mechanism family the gates do not separately name: post-hoc revalidation and reopening of thin closures. franken_node reopened 739 completion-debt beads (*"bead-completion illusion"*, `docs/progress/REALITY_CHECK_AND_BRIDGE_PLAN.md`); franken_nlp reopened eleven falsely closed beads with receipts preserved (`REALITY_BRIDGE_PLAN.md` §0); frankentui installed close-audit machinery after 188 no-reason closes and 859 very thin closes. It is filed here under Gate 1's close-evidence family rather than as a 24th gate because it is a *corrective* to close-time evidence, not a separate gate type — but it is more than close-time evidence and more general than Gate 11's ledger resurrection (which audits ledgers, not closures).

**What it does NOT guarantee:**
- **Execution coupling.** Elaborate planning maturity does not imply the plan drives the work. frankengraphdb, frankensim, frankenfs, and frankensqlite explicitly report tracker drift, false closes, inert gates, or an evidence apparatus outrunning delivery. franken_node names the *"bead-completion illusion"* and reopened 739 thin closures. A mature ledger can coexist with an immature build.
- **Implementation maturity.** franken_nlp's planning system is the most elaborated observed, while the plan itself states implementation is *"a substantial code-first reference/artifact scaffold, not yet a usable or proved product."* Planning maturity and product maturity are independent variables.
- **Independence of the doctrine.** 29/44 bind themselves to the suite-wide `/data/projects/AGENTS.md`, which is referenced by absolute local path and vendored in almost no repo — the anti-reward-hacking spine is external to the repositories it governs. bus factor and single-maintainer control are suite-wide givens.
- **Universality.** Websites and satellites (franken_markdown_website, frankensim_website, frankentui_website, frankensqlite_website, franken_native_capsule) run thin, inherited, or no planning machinery. Agent-only planning (franken_agent_detection) and evidence-first planning without beads (franken_overlap) are working alternatives, not degeneracies.
- **Dialectical review.** Only 16/44 have any second-eyes/dialectical mechanism; the suite default is single-agent execution with machine gates. "Adversarial" usually means adversarial *fixtures* (frankentorch), not adversarial *reviewers*.
- **That the honesty machinery is itself honest.** The suite's own answer is the meta-audit layer: ledger resurrection (11/44), claim-coverage audits (8/44), gate-validity catalogs (frankenredis), mutation batteries (frankensympy), planted negatives (4/44), and anti-ceremony doctrine (franken_tts Doctrine #0, franken_engine, frankentui, franken_threed RULE 0.1). But these are opt-in: 33/44 have never resurrection-audited their ledgers, and 36/44 have never measured their claim-coverage fraction.
