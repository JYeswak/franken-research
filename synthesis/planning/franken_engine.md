## 2. Execution-readiness gates (what must a plan pass before agents are set free?)

[Verified] The repo is gate-heavy; plans are executable only after layered pre-merge and pre-close gates. Key gates, quoted verbatim:

1. **Change acceptance gate** (`docs/RUNTIME_CHARTER.md` §8 — binding): "A runtime-facing change is acceptable only if it: 1. Preserves native-only execution ownership. 2. Preserves deterministic replay guarantees on relevant paths. 3. Preserves decision/evidence linkage for high-impact actions. 4. Respects repository split and sibling-reuse contracts. 5. Uses claim language consistent with evidence policy and artifact availability. 6. Ships tests and artifacts proportional to risk and claim scope. If any gate fails, the change is rejected or explicitly scoped as non-runtime/prototype work."

2. **Evidence and decision contracts** (`docs/plans/PLAN_TO_CREATE_FRANKEN_ENGINE.md` §11 — mandatory): "Every major subsystem proposal must include: change summary; hotspot/threat evidence; EV score and tier; expected-loss model; fallback trigger; rollout wedge; rollback command; benchmark and correctness artifacts. No contract, no merge."

3. **Bead closure gate** (`CONTRIBUTING.md`): "Do not mark a bead complete from code shape alone. A security, performance, replay, or evidence task is complete only when its adversarial/failure path and preserved proof surface are also correct." Close form: `br close <bead-id> --reason "implemented and verified: <concise evidence>"`.

4. **Bridge closeout gate** (`docs/BRIDGE_CLOSEOUT_POLICY.md`): all `-> closed` transitions for `bridge-manifest`-labeled beads require native gate `bridge_closeout` (`.beads/policy.yaml` has `allow_bypass: false`). Verbatim: closing requires "`scripts/run_bridge_closeout_gate.sh <bead-id>` (verify + record pass), then `br close <bead-id> --reason "<evidence-cited reason>"` — now accepted. Any status change after the pass stales it; re-run the reporter." Break-glass exists but is "flagged `breakglass_not_normal_completion` forever by the verifier."

5. **Claim promotion gate** (`docs/operator-gates/FE_CLAIM_010_PROMOTION_DECISION.md`): the matrix entry for the >=3x claim "may only read `observed` when a FRESH, re-runnable Node/Bun denominator artifact demonstrates: 1. `score_vs_node >= 3.0` and `score_vs_bun >= 3.0` …; 2. `publish_allowed == true` …; 3. a `repro.lock` accompanies the score artifact … If any condition fails, the honest outcome is that FE-CLAIM-010 stays `target`." Current decision: STAY_TARGET.

6. **Claim publication gate** (`docs/CLAIM_LANGUAGE_POLICY.md`): "A claim is publishable only if all checks pass: 1. Claim class is declared. 2. Evidence bundle exists and is linked from the claim context. 3. Artifact hashes in `manifest.json` match stored files. 4. Reproduction commands run successfully from `commands.txt`. 5. Reviewer sign-off is recorded (maintainer or delegated owner). If any check fails, statement must be downgraded to intent-language."

7. **Docs accuracy release gate** (`docs/DOCS_ACCURACY_GATE_CONTRACT_V1.md`): "Any documentation that contradicts shipped behavior blocks release until manual review and explicit override." Config: `max_aspirational_claims: 0`, `fail_on_contradictory: true`, `min_alignment_rate_millionths: 950_000` (95% alignment required).

8. **DW capability verification standard** (`docs/dueling_wizards/DW_TESTING_AND_VERIFICATION_STANDARD.md`): every capability must ship unit + integration tests, an e2e gate script `scripts/run_dw_<cap>.sh ci`, a replay wrapper, golden coverage, and fuzz targets; exit codes "0 = pass, non-zero = fail-closed, 3 = degraded … never a silent pass." Gate hygiene: "`cargo check --all-targets`, `cargo clippy --all-targets -- -D warnings`, `cargo fmt --check` all green."

9. **Process-artifact creation gate** (`AGENTS.md`): "A process artifact (certificate, ledger, dashboard, matrix, meta-report, speculative check) may be created only if it names a concrete consumer, the named feature it gates, the observed defect class justifying it, and its deletion condition. Otherwise it does not get created." [Maintainer claim] This is the anti-bureaucracy gate: process is only built when it names its consumer and its death condition.

## 3. Honesty guardrails (negative-evidence / claim-matrix / demotion)

[Verified] The honesty machinery is the most distinctive feature of this repo's planning, and it is installed in the founding documents, not bolted on later:

- **Claim states** (`docs/RUNTIME_CHARTER.md` §7.1): "`observed`: use when results were measured in a declared environment and artifact bundle is attached. `target`: use for design goals or SLOs not yet proven by released artifacts. `hypothesis`: use for projected outcomes that are not yet validated."
- **Forbidden language** (`docs/CLAIM_LANGUAGE_POLICY.md`): "Forbidden unless evidence is linked inline: 'guaranteed', 'always', 'unbreakable', 'bulletproof', 'zero risk', 'category-defining' (when used as a factual present-tense claim)."
- **Mandatory evidence bundle** (`docs/CLAIM_LANGUAGE_POLICY.md`): every SECURITY/PERFORMANCE/COMPATIBILITY/DETERMINISM claim must link `manifest.json`, `env.json`, `repro.lock`, `commands.txt`, `results.json`, `README.md`. Recommended: `attestation.json`, `waivers.json`.
- **Auto-demotion rule** (`docs/RUNTIME_CHARTER.md` §7.4): "If an artifact cannot reproduce a published claim, claim language must be downgraded immediately (`observed` -> `target`/`hypothesis`) and corrected in the same change set that records the discrepancy." [Verified in charter text; enforced mechanically by the claim-matrix gate.]
- **Claim-to-proof matrix gate** (`docs/CLAIM_TO_PROOF_MATRIX_V1.md`): "The gate fails when `actual_wording_state` is stronger than `allowed_state`, when source spans drift, when observed rows lack artifact handles, or when missing proof lacks exact downgrade text." The matrix is honest in practice: FE-CLAIM-010 (the >=3x headline) remains `target`, with the operator record documenting a preserved 2026 historical bundle measuring `0.000920x` vs Node and `0.000791x` vs Bun — i.e. the machine's own receipts contradict the claim, so the claim stays demoted. [Maintainer claim, quoted from operator record] "If engineering doesn't deliver that number, the matrix stays TARGETED — that's the honest outcome and is preferable to fudging."
- **Execution-vs-scaffold truth ledger** (`docs/EXECUTION_TRUTH_LEDGER_V1.md`): "Bind the historical JIT, AOT, tiering, Test262, performance, and claim records to the code paths and artifacts that actually exist. The ledger preserves useful scaffolding while preventing planning records, input-only hashes, synthetic timings, test-only paths, or observed failures from being promoted into production-success claims." [Verified] This is a per-bead, per-claim classification of what kind of reality each record is.
- **Refusal ledger / negative evidence** (`docs/E8_ANALYZED_SUBSET_REFUSAL_LEDGER.md`): "The refusal ledger is not a non-use certificate. It is the artifact that prevents an unanalyzed run from being promoted into one." [Verified] Covert channels, timing channels, implicit flows, and CPU side channels are out of scope and "must be named as out-of-scope refusals rather than silently approved" — each with a refusal code (e.g. `out_of_scope_covert_channel`). A denominator defines when a run is *inside* the analyzed subset; "If any item is missing, the result is not a successful non-[use certificate]."
- **Runtime demotion controllers** (artifacts + code): `frx_online_regret_change_point_demotion_controller_v1.json`, `optimization_demotion_replay_receipts_contract_v1.json`, `crates/franken-engine/src/demotion_rollback.rs`, `pre_signed_demotion_fallback.rs`, and tests (`self_replacement_demotion_required.rs`, `demotion_rollback_integration.rs`) — rollback is a first-class, receipt-bearing operation, not an undo. [Inference] The plan's section 18.14 codifies this at program level: "It does not fabricate completion, widen waivers, or change the benchmark after measurement."
- **No self-certification** (`AGENTS.md`): "work is closed by an independent verifier citing evidence at an exact revision. Solo sessions re-verify by re-execution and state what was not independently verified." Also: "A typed refusal beats a fabricated result and is less valuable than the real capability; refusal-only work stays open and says so." and "Truthful null results ('checked X, found no material increment') are successful outcomes. Unsupported claims are worse than silence."

Lifecycle position: the claim machinery is installed at the charter/plan level (section 7 of the Runtime Charter and the founding plan itself), meaning it governs the repo from inception; wave-specific refinements (E8 refusal ledger, demotion controllers, execution truth ledger) arrive with the waves that need them.

## 6. Anti-satisficing (red-team / falsification / campaign mechanisms)

- **Continuous adversarial campaign** [Verified] (`artifacts/adversarial_campaign/README.md`): deterministic run manifests for `bd-2onl`; "Each run writes: `commands.txt` … `run_manifest.json`: mode, seed, git commit, command list, outcome, and verification commands" plus operator verification steps and replay. The plan's §9F.7 prescribes an "Autonomous Red-Team Generator": "perpetual adversarial campaign generation that evolves faster than static malicious corpora … Failures auto-minimize into deterministic repros and are promoted into permanent regression corpora."
- **Negative tests as gates** [Verified]: `signed_decision_receipt_negative.rs`, `conformal_split_independence_negative.rs`, `counterfactual_incompatible_policy_negative.rs`, `convergence_slo_gate_negative_integration.rs`, `fleet_privacy_budget_refusal_integration.rs` — refusal paths are tested, not just documented.
- **Anti-ceremony doctrine** [Maintainer claim, AGENTS.md]: "The purpose of agent work here is working, deployable capability. Process serves that outcome and never becomes the product." Twelve named reward-hacking patterns are forbidden (gate self-weakening, proof-class inflation, golden regeneration reflex, commit-stream pumping, tautological tests, easy-lever cherry-picking, close-pump abuse, scope-splitting, spec-editing as progress, conformance metastasis, dependency smuggling, bench-path hardcoding), with the instruction "Name these pathologies when they occur … the names are the deterrent."
- **Ambition floor** [Maintainer claim, plan §3 "Category-creating disruptive floor"]: "If outcomes are parity-only or incremental, the program is considered off-charter." Out-of-charter behavior includes "Scope trimming framed as 'practicality' when it weakens disruptive potential" and "Ambition reduction without explicit owner request."
