## 2. Shared negative patterns

### Pattern A — README drift (present-tense/spec marketing vs pinned reality)
franken_alignment shares the suite's signature defect: a README that describes a target state as if built, with version drift against the tree. Packet quote: "All five registered SLOs (and all component targets) are unmeasured proposals" and the README itself admits "No number below has been measured" [Code-verified, High]; separately the README cites qualified compiler `nightly-2026-09-07` in one place and `nightly-2026-09-08` in another [Code-verified, High]. **Other projects:** franken_networkx ("The README is a drift source (13-variant tie-break → 12 counted; 33 fuzz targets → 34 counted…) [Counted, High]"), franken_jax ("The README contradicts itself and the code on the most basic facts (118 vs 162 primitives, 15 vs 17 crates, 162,733 vs 459,703 lines) [Counted, High]"), franken_sympy ("the README's 'green workspace tests' line is stale-by-a-month [Code-verified + CI-observed, High]"), franken_redis/franken_node/franken_pandas/franken_search/franken_term (each packet carries explicit drift callouts). The twist: franken_alignment and franken_manim *both* disclaim the tense — franken_manim's packet: "the README is written in present tense as if the 1.0 design were fully realized; it is a spec of the target, not a description of the present [Verified, High]" — making the disclaimer itself a shared pattern, and both admit it leaks (franken_alignment: the asupersync badge "reads as a fact about the tree" that the disclaimer "fails to protect" [Code-verified, High]).

### Pattern B — Evidence stale or unverifiable at the pin
The suite-wide version of franken_alignment's 14-day/416-commit gap. **Other projects:** franken_ocr ("the CI workflows were deleted from the tree at HEAD and the last runs (2026-09-03) failed, while the docs still describe CI as the release gate" [TL;DR]), franken_sympy ("the build-and-test gate has failed 786 consecutive CI runs (last green 2026-08-23; pin fails at the fmt gate, unit tests never run) [CI-observed, High]"), franken_node ("CI is red at the pin — all 8 push-triggered runs observed against the pin's head SHA concluded failure… the broader recent window is predominantly red [CI-observed, High]"), franken_lean ("CI red at the pin"), franken_redis ("conformance run #7679 failed at the `cargo fmt` gate… and the Tcl lane's verdict step failed"), asupersync ("zero workflow runs exist at the pinned commit and the most recent runs (2026-09-07, older commits) show failures [CI-observed, High]"), franken_jax ("No third party can observe any test passing — zero GitHub Actions workflows exist, so every 'green' claim executes on the maintainer's local RCH fleet and is attested only by checked-in artifact JSON [External + Inference, High]"). franken_alignment sits inside this pattern but at its honest extreme: it is the only one to *open its status ledger* with the disqualification.

### Pattern C — Non-OSI license rider excluding the most capable evaluators
The MIT + OpenAI/Anthropic rider (barring use *including* "benchmarking, testing, analyzing, indexing") appears across essentially the whole suite. **Other projects:** franken_node ("the license rider bars OpenAI/Anthropic and anyone acting for them from use including benchmarking, testing, and analyzing [Code-verified (license text), High]"), franken_manim ("a non-OSI MIT+OpenAI/Anthropic-rider license that withholds even benchmarking rights from the two leading AI labs"), franken_ocr ("excludes the frontier AI labs from even benchmarking it"), franken_networkx, franken_jax ("the same labs whose models co-authored 53% of recent commits"), franken_search, franken_snowflake, franken_torch, franken_tui, frankenscipy, frankenfs, frankengit, frankenterm, franken_numpy, franken_pandas, franken_redis, franken_engine, franken_lean, franken_threed, franken_nlp, franken_sympy, frankensqlite, franken_tts, franken_whisper, franken_drone_geometry_reconstruction, franken_code_browser, franken_surveillance_system, franken_overlap, franken_remote, franken_markdown(+_website), franken_tui_website, franken_sim, asupersync. **Exceptions (no rider):** franken_agent_detection ("License:** MIT, 21 lines, **no rider** — read verbatim [Code-verified, High]"), frankensim_website ("no rider at all"), beads_for_franken_engine ("none — no LICENSE file in the tree"), frankensqlite_website ("none — no LICENSE file; README declares default copyright"). franken_alignment's packet makes the strategic cost explicit in a way others only note in passing: "the buyers with the problem are the labs the license excludes [Inference, Medium]."

### Pattern D — Bus factor 1 by design, not accident
franken_alignment: "All 458 commits authored by Jeff Emanuel; one co-authored-by trailer in the entire history [Git-observed, High]" with "no succession plan, no second committer, no foundation" [External, High]. **Other projects:** franken_term ("bus factor 1 by **explicit, deliberate policy** (no outside contributions accepted)"), franken_ocr ("a single maintainer who explicitly accepts no outside contributions"), franken_manim ("outside contributions explicitly refused"), franken_snowflake ("contributions explicitly refused"), franken_node ("bus factor 1 [External, High]"), franken_jax ("One human maintainer with an explicit no-outside-contributions policy [Maintainer claim, High]"), franken_search ("bus factor 1 with an agent-swarm maintenance model"), frankenscipy ("bus factor 1 (6,395 commits by a `claude` contributor…"), asupersync ("bus factor 1 with outside contributions explicitly refused (README L2620 verbatim policy)"). The suite-wide variant is single-maintainer + stated refusal of outside contributions; franken_alignment shares it with the explicit-policy subgroup (term, ocr, manim, snowflake, jax, asupersync, node).

### Pattern E — Extreme commit velocity concentrated in process/test/docs rather than shipped capability
franken_alignment: 458 commits in 16 days, with the claim inventory's verified items all being *process and honesty* claims ("the repo's documentation of its own limits is its most verified feature") and all capability claims aspirational. **Other projects:** franken_networkx ("Bus factor 1 (single GitHub contributor, 8,808 contributions [External, High])"), franken_scipy ("6,395 commits by a `claude` contributor"), franken_node ("~20 commits/day in the sampled window [External, High]"), franken_manim ("a 642-record issue tracker" on a pre-1.0 reimplementation), franken_alignment's own packet notes the suite-wide opportunity-cost framing: "458 commits in 16 days to this repo is attention not spent on the other 42 FrankenSuite repos [Inference, Medium]".

### Pattern F — Operator-local gates, no (or deliberately disabled) GitHub Actions
franken_alignment: "No GitHub Actions: quality gates run operator-local via Cargo + DSR by design" [Code-verified, High], gates requiring "the maintainer's private RCH fleet" so "no independent party can reproduce them" [Maintainer claim, High]. **Other projects:** franken_jax ("every 'green' claim executes on the maintainer's local RCH fleet and is attested only by checked-in artifact JSON [External + Inference, High]"), franken_term ("no public CI (verification runs on maintainer-controlled RCH hosts that are not independently inspectable)"), franken_networkx ("GitHub Actions 'permanently non-authoritative… must stay disabled'"), franken_markdown ("GitHub Actions workflow is explicitly DISABLED"), franken_nlp ("GitHub Actions is disabled… CI workflow inert (`on: {}`)"), franken_ocr ("the CI workflows were deleted from the tree at HEAD"), franken_overlap ("GitHub Actions is deliberately disabled, so no third party can [observe]"). The DSR-vs-Actions split is itself a suite motif; franken_alignment is the extreme case because its *only* execution path is the private fleet.

## 3. CI/evidence bar — what franken_alignment demonstrates that others lack

1. **Machine-checked documentation concordance.** `xtask` dispatches `concordance-check`, `system-map-check`, `prose-check` (docs↔code mappings) and `inventory` (admission checks, source snapshots) [Code-verified, High]. A grep for "concordance" across all 44 packets hits only the franken_alignment packet. Others check docs drift with scripts (franken_node's `scripts/check_claims_manifest.py --check-honesty` "9 checks ok, 0 drifted" [Verified, High]; franken_lean's claim-matrix documentation CI) but none machine-check prose↔code mapping via a gate driver. franken_jax, franken_networkx, franken_pandas, franken_redis, franken_search, franken_sympy — the drift-laden READMEs of §2 Pattern A — all lack this.
2. **Source-hash-bound execution receipts with retained failed attempts.** Per-batch receipts in `artifacts/execution/` bind source hashes, job id, and raw logs, "failed attempts retained" (the 2026-09-08 batch record) [Code-verified/Counted, High]. franken_search has committed machine-readable latency receipts ("corroborate the README's numbers to the decimal [Verified, High]") but no failed-attempt retention; franken_term publishes held-out *failed* runs (RC53) but as curated examples, not as standing per-batch records; franken_networkx's negative-evidence ledger records losing rows but not per-batch execution receipts. The retained-failure-batch convention is franken_alignment's.
3. **Standing "unqualified source addition" self-disqualification.** Not a one-off audit but a *rule*: any code landing after the last executed gate must open the status ledger with a self-disqualification until the gate re-runs [Code-verified, High]. Closest analogues are one-shot events: franken_sympy's "Sept-8 revised reality-check audit that reads like a red-team report against its own author [Code-verified, High]", franken_ocr's negative-evidence and performance ledgers, franken_search's "documented public correction (v1.6.0…)", franken_term's "`skipped_not_proven` qualification gates the maintainer refuses to sign off prematurely" — none is a standing per-commit rule.
4. **Machine-readable self-labeled-unmeasured SLOs.** `registry/slo.json`: `"all_values_are_unmeasured_proposals": true`, every target `"status": "unmeasured"` [Code-verified, High]. Others disclaim in prose only (franken_lean README "0 bench targets"; franken_engine pins throughput at TARGETED via a claim-to-proof gate; franken_search's ledger records losing rows). The JSON self-label is unique.
5. **Hardcoded release refusal + machine-readable release readiness.** `xtask release-check` returns `Err("Release blocked: no qualified production broker, frozen release toolchain, foundation closure, target matrix or signed proof closure exists yet.")` [Code-verified, High]; `registry/release_readiness.json` has `"production_release_enabled": false` [Code-verified, High]. Closest: franken_ocr's "three-pillar release-certification gauntlet whose finalizer refuses to claim a three-party OpenPGP certificate the release process cannot produce" and franken_manim's "release notes that reject their own bad artifacts" — neither is a machine-readable readiness registry plus a hard error.
6. **Planted-mutation testing with per-batch intended-failure assertions.** "deliberately introduced defects must fail after controls pass (documented per batch, e.g. 'Two planted defects fail after controls')" [Code-verified, High]. This is *partially* shared — frankensympy has "mutation-tested certificate families [Code-verified, High]", franken_node has "mutation-adequacy floors", franken_native_capsule has "mutations run in CI with zero admissions and the ledger is committed", frankengraphdb has "mutations that now guard them [Maintainer claim, High]", franken_manim has "mutation controls + 2 negative controls on its self-test", frankenfs/frankengit mention mutations — but only franken_alignment documents planted defects *per qualification batch* with explicit intended-failure assertions inside the receipt-bound record, which is the form that makes mutation a standing evidence practice rather than a one-off campaign.
7. **Closed dependency universe demonstrated by lockfile.** `Cargo.lock` contains zero external packages — "the entire workspace (936 `.rs` files, 194,256 lines [Counted, High]) compiles against `core`/`alloc`/`std` only" [Code-verified, High]. franken_lean also has "a zero-external-dependency 731k-line workspace [Counted, High]", and zero-unsafe/closed-universe claims appear in franken_manim, franken_markdown_website, franken_nlp, franken_surveillance_system, franken_term, franken_drone_geometry_reconstruction, frankengraphdb, beads-for-frankentui — so call this shared-with-lean at the top end, not unique; franken_alignment's distinctness is combining it with zero `unsafe` (workspace `forbid` + per-crate `#![forbid(unsafe_code)]` gates, 18 gate lines counted [Counted, High]) in a *design-program* repo rather than a reimplementation.

## 4. Shared hurdles (structural issues with evidence)

- **Bus factor 1 + no succession.** All 458 commits by Jeff Emanuel [Git-observed, High]; "No succession plan, no second committer, no foundation, no release artifact to fork from cleanly (0 releases, 0 tags)" [External, High]. Shared with essentially every packet (see §2 Pattern D).
- **License rider as advancement blocker.** The rider "makes the license **non-OSI** (it discriminates against named persons/groups, violating OSD §5/§6) [Code-verified (license text), High]" and is "incoherent with the mission: an *alignment-control* project whose theory of change requires adoption by frontier labs bars two of the frontier labs doing the most relevant work [Inference, Medium]." The franken_node packet makes the same structural point ("the rider is an advancement blocker (Explore-with-a-ceiling), not a ring qualifier"), and the same wording family appears across packets — the rider is the suite's single largest structural hurdle, and franken_alignment is the case where it bites hardest because its thesis *requires* evaluation by frontier labs.
- **README drift / present-tense marketing.** The README's present-tense spec of a non-existent system, with only a paragraph-level disclaimer; the asupersync badge as the leak the disclaimer doesn't cover [Code-verified, High]. Shared across the suite (§2 Pattern A); franken_alignment and franken_manim both carry explicit tense disclaimers.
- **Velocity vs review depth.** 458 commits in 16 days concentrated in docs/reference/tests, with G1–G6 (all production gates) `not_implemented`; the packet's own skeptic take: "143 packets and 337 bead issues for a G0 project is process overhead that can mask missing substance… Process output receives no capability credit — the project's own AGENTS.md says so [Code-verified, High; Inference, Medium]." Echoes: franken_networkx's 8,808 single-author contributions, franken_scipy's 6,395 claude-authored commits, franken_node's ~20 commits/day.
- **Private-environment evidence.** Receipt-bound evidence whose execution environment is the maintainer's RCH fleet — "receipt-bound evidence you cannot re-run is audit theater's respectable cousin" [Maintainer claim + Inference]. Shared with franken_jax (RCH fleet + checked-in artifact JSON) and franken_term (RCH hosts "not independently inspectable"); the inverse pattern is CI-observable-but-red (node, redis, lean, sympy, asupersync).
- **Suite-internal attention competition.** "The maintainer's own attention… 458 commits in 16 days to this repo is attention not spent on the other 42 FrankenSuite repos" [Inference, Medium]. No other packet quantifies the opportunity-cost frontier this directly, but several packets (franken_redis's dated revisit triggers, franken_ocr's governance-decay signal) document the same one-maintainer-44-repos decay pressure.

## 5. Genuine uniqueness (vs the other 43 — "also does X" flagged honestly)

1. **Docs↔code concordance as an executed gate** (`concordance-check`, `system-map-check`, `prose-check` in `xtask`) — no other packet's repo has it ("concordance" appears in no other packet). *Note:* franken_lean's B8 documentation CI is adjacent but different — it rejects wording stronger than the claim matrix permits, whereas franken_alignment checks prose↔code/source mappings.
2. **The "unqualified source addition" standing disclosure** — no other repo has a per-commit self-disqualification rule; franken_sympy's red-team reality check, franken_ocr's negative-evidence ledgers, franken_search's public correction, and franken_term's refused sign-offs are all one-off audits or curated examples, not standing rules.
3. **Preregistered hypotheses with kill criteria.** 21 falsifiable hypotheses H1–H21 "with kill criteria" in a preregistration ledger [Code-verified, High], plus the plan's "publish negative results" rule (plan §G4). franken_nlp and franken_overlap have preregistration-adjacent machinery ("preregister" grep hits), and several repos have hypothesis ledgers — but only franken_alignment's packet shows kill criteria attached to each hypothesis.
4. **Self-labeling-unmeasured SLOs in machine-readable JSON** (`"all_values_are_unmeasured_proposals": true` in `registry/slo.json`) — unique as a machine-readable mechanism; the practice of disclaiming unmeasured numbers is shared (lean, engine, search, node).
5. **A design-first, non-reimplementation governance program.** Unlike the reimplementation repos (franken_redis et al.), this is "original design work, and the only suite repo whose primary artifact is a *governance methodology* rather than software [Inference, Medium]" — 251,689-byte plan, 257 docs, 15 registries, 143 work packets, 40 invariants, 21 hypotheses. franken_nlp has a claims-annotation scheme and hypothesis ledger (partial overlap); franken_surveillance_system and franken_drone_geometry_reconstruction have plans; but none is a methodology-first program at this scale.
6. **Hardcoded release refusal + machine-readable release-readiness registry** (`xtask release-check` hard `Err`, `release_readiness.json` with `"production_release_enabled": false`) — unique in the *hard-coded plus registry* combination. *Also-does-X flag:* franken_ocr's gauntlet finalizer refuses an unproducible certificate, franken_manim's release notes reject bad artifacts, franken_node's close-condition oracle "currently reads RED on its own corpus numbers" — the refusing-to-ship culture is shared; the machine-readable hard gate is franken_alignment's alone.
7. **Planted-mutation discipline documented per qualification batch** — *also-does-X flag:* frankensympy (mutation-tested certificate families), franken_node (mutation-adequacy floors), franken_native_capsule (mutations in CI with ledger), franken_manim (mutation controls + negative controls), frankengraphdb ("mutations that now guard them") all do mutation testing; franken_alignment's version is unique only in being bound into the receipt ledger per batch with intended-failure assertions.
8. **Epistemic MVCC with negative range witnesses; rights conservation with checkable authority-graph coverage (dominators, minimum cuts); salted commit–reveal helper congress with credibility ledgers** — the actual control-plane semantics. No other packet describes anything in this space (the suite is reimplementation work; franken_agent_detection is detection-adjacent but not control-plane). This is unique by construction — but all of it sits at reference-model level, not production.

## 6. Cross-pollination IN (other packets → franken_alignment)

1. **Documentation CI that rejects wording stronger than the claim matrix permits → franken_alignment.**
   - *Origin:* franken_lean B8 — "a claim matrix with evidence states and documentation CI that rejects wording stronger than the matrix permits" and "anchor-bound kernel contracts" with "`expect=` tokens that fail CI on drift" [Verified, High].
   - *Why it fits:* franken_alignment already ships `concordance-check`/`prose-check`; its open leak is *wording strength* — the README's present-tense comparison table "fights strawmen" [Inference, Medium] and the asupersync badge escapes the tense disclaimer [Code-verified, High]. franken_lean's mechanism checks strength, not just mapping.
   - *Expected payoff:* the tense disclaimer becomes machine-enforced; a badge or table row asserting more than the evidence matrix permits fails the gate. Directly closes the packet's "badge reads as fact" finding.

2. **Public, non-RCH execution lane for the reference model → franken_alignment.**
   - *Origin:* franken_redis / franken_node — both run conformance suites on public GitHub Actions even when red ("conformance run #7679 failed at the `cargo fmt` gate" at the pin; franken_node "all 8 push-triggered runs observed against the pin's head SHA concluded failure [CI-observed, High]") — observably failing but observably *runnable*.
   - *Why it fits:* franken_alignment's fatal reproducibility finding is that "the evidence is receipt-bound and tamper-evident, but the *execution environment* is private" — the 511-test gate needs the maintainer's RCH fleet [Maintainer claim, High], and the workspace "was never compiled" by the analyst. A public Actions lane running `cargo xtask check` over `fa-reference` needs no RCH (it's pure safe Rust, zero external deps).
   - *Expected payoff:* outsiders can re-execute and re-verify receipts; converts the "audit theater's respectable cousin" weakness into checkable evidence; does not require dropping the RCH fleet for heavier gates.

3. **Phase −1 truth pack (pinned model commit + fixture hashes) → franken_alignment's first hypothesis run.**
   - *Origin:* franken_ocr — "a Phase −1 'truth pack' pinning the exact model source commit and fixture hashes" [TL;DR], plus the L0–L5 parity ladder with skip-honest no-weights mode.
   - *Why it fits:* franken_alignment's own next step 3 proposes running H15 (the manifold premise) on "a small open model" — an experiment whose reproducibility lives or dies on exact model/fixture pinning. The truth pack is the mechanism for it, and using open-weights models dodges the license rider's lab-exclusion problem.
   - *Expected payoff:* the first real-hypothesis execution arrives pre-registered *and* reproducible by non-excluded outsiders — the packet's cleanest path to a published positive-or-negative result.

4. **Claim-coverage audit with a ledger contract forbidding unsupported claims → franken_alignment's 143-packet program.**
   - *Origin:* franken_networkx — the CLAIM_COVERAGE_AUDIT "found 579 of 591 KEEP rows carry no vs-incumbent ratio — the headline speedups are overwhelmingly self-speedups, which the project's own ledger contract says 'must not support a competitive claim' [Code-verified, High]"; plus five auto-generated ledgers "that fail CI on drift [Code-verified, High]".
   - *Why it fits:* franken_alignment's 143 work packets + 337 bead issues are exactly the "process overhead that can mask missing substance" risk [Code-verified, High; Inference, Medium]. A per-packet evidence-coverage state (executed / stale / absent) with a contract like "a packet with no executed gate must not support a capability claim" would make the overhead auditable.
   - *Expected payoff:* machine-checkable answer to "which of the 143 packets has any executed evidence" — the program becomes self-auditing at the granularity it already tracks.

5. **Sigstore-signed, content-addressed release attestation bundles + per-work-item provenance → franken_alignment's DecisionClosure.**
   - *Origin:* franken_term — "content-addressed, sigstore-signed release attestation bundles, per-category producing-bead provenance" [TL;DR]; plus "a hash-chained ledger" binding mutation to "(origin identity, policy version, input hash)".
   - *Why it fits:* franken_alignment's DecisionClosure (frozen effect digest, policy epoch, evidence closure, round, consequence, autonomy grade, model passport — "independently verifiable by `fa-verify`, which shares no code with the broker" [Maintainer claim, Medium]) is specified but G1+; franken_term's attestation bundles are a *shipped* precedent for content-addressed, third-party-verifiable provenance artifacts. The packet's next step 5 already proposes prototyping this in a sibling repo.
   - *Expected payoff:* the first DecisionClosure-shaped capsule can be emitted and independently verified without waiting for G6 — proves the "verifiability by outsiders" pitch against a real artifact instead of a registry entry.

## 7. Cross-pollination OUT (franken_alignment → other projects)

1. **Receipt-bound qualification batch format → franken_ocr, franken_sympy, franken_node.**
   - *Concept:* per-batch JSON receipts binding source hashes, job id, failed attempts (retained), and raw logs; `IMPLEMENTATION_STATUS.md` narrating each batch with explicit non-claims.

   - *Expected payoff:* stale CI stops being an evidence vacuum — the batch ledger records *what ran, on what, and what failed*, which is strictly more honest than a deleted workflow.

2. **"Unqualified source addition" standing disclosure → franken_redis, franken_networkx, franken_search.**
   - *Concept:* any code landing after the last executed gate must open the status ledger with a self-disqualification until the gate re-runs.
   - *Targets & fit:* franken_redis (conformance red at pin, and "v0.1.0's 24 signed assets target an earlier commit, not the pin" — green-looking artifacts on unexecuted code); franken_networkx ("The README is a drift source" with four counted divergences [Counted, High]); franken_search (real releases while "relevance quality is unproven" by its own findings doc). All three have green/older evidence adjacent to newer code — the exact rot this rule kills.
   - *Expected payoff:* the suite's most common evidence-rot pattern (old green badges on new code) becomes a caught violation instead of a drift footnote.

3. **Concordance-checked documentation (`concordance-check` / `system-map-check` / `prose-check`) → franken_jax, franken_pandas, franken_node.**
   - *Concept:* xtask subcommands that machine-check docs↔code mappings and prose claims against the tree.
   - *Targets & fit:* franken_jax (README "contradicts itself and the code on the most basic facts (118 vs 162 primitives, 15 vs 17 crates, 162,733 vs 459,703 lines) [Counted, High]" — a concordance gate would have failed every one); franken_pandas (README is "2,976 lines: drift, disclaimers, heat map" — scale makes manual sync hopeless); franken_node (already has `check_claims_manifest.py --check-honesty`; concordance is the stricter superset covering prose↔source).
   - *Expected payoff:* the drift pattern in §2 Pattern A gets a mechanical gate instead of analyst recounts.

4. **Planted-mutation negative-evidence standard → franken_ocr, frankengraphdb, franken_search.**
