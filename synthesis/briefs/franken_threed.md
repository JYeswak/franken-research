Paired with the most self-disavowing documentation in the suite — the maintainer's own README states "**zero speedup has been measured**" and the specialization doc states "a compiled addon is not a measured acceleration" [Maintainer claim, High].

**Strongest ceiling — the thesis is a speedup claim with zero measured speedups, on the wrong side of an optimizer's baseline.** The 2×/3× headline gates are "targets, not results" [Maintainer claim, High]; the unspoken competitor is V8's own JIT ("a closed numeric loop is exactly what modern JITs already handle well, which compresses the headroom the 2×/3× gates need") [Inference, Medium]; 7 of 11 planned crates are unwritten (the contract doc confirms they are load-bearing, not optional) [Code-verified + Counted, High]; bus factor 1 with opaque agent provenance [Git-observed, High]; and the MIT+OpenAI/Anthropic rider excludes the likeliest validators [Code-verified, High]. **The 3 most important pieces of evidence:**

## 3. CI/EVIDENCE BAR — what franken_threed demonstrates that others lack

Specific mechanisms, what each does, and who lacks them:

1. **Exhaustive full-input-class differential gate with live-oracle instantiation.** Mechanism: the closed numeric body is compiled to an import-free Wasm module, then executed across the *complete* input class (all 256 cube topologies × 8 flag combos = 2,048 kernel invocations, plus animated metaball sequences, 80 seeded random fields, NaN/empty edge cases), asserted bit-comparable (`sameEffect`, `sameArrays`) against a *live instantiation of the actual upstream r186 `MarchingCubes` class*, with diagnostic counters requiring exactly 256 Wasm calls and **zero fallback calls**. Lacked by: **frankenredis** (5,041 differential probes vs vendored Redis 7.2.4 oracle — sampled `argv` cases, not an exhaustive input class; no zero-fallback counter); **franken_numpy** (differential conformance vs live NumPy oracle, but its `fnp-conformance` crate is the *only* workspace crate not published — 404 on crates.io [External, High] — and it is not a compiler's-output gate); **franken_ocr** (bit-identical scalar oracles for int8 kernels — closest analog, but kernel-level oracles, not full-input-class sweeps of compiled artifacts vs a live oracle, and no fallback-exclusion counters); **franken_nlp** (fidelity-oracle profiles `hf_bf16_eager`/`diagnostic_f32`, but profile-level, not a compile-and-prove gate).
2. **Oracle integrity verification before use.** Mechanism: the upstream oracle checkout is verified by blob SHA-1 (`29a405be…`) before the differential suite runs. Lacked by: all oracle-using packets observed — none report a hash-check-before-use step on the oracle itself (frankenredis vendors Redis 7.2.4; franken_numpy uses live NumPy; franken_networkx pins NetworkX 3.6.1 with ELF-hash pinning of the *timing* denominator, not an oracle-integrity check).
3. **Independent assessor re-execution of the CI-gated suite.** The 61/61 pass was re-run locally by the assessor with the oracle integrity step included [Verified — executed by analyst, High]. No other packet reports a full independent re-execution of its CI-gated differential suite with oracle verification (beads-for-frankentui reports an analyst re-verification of SHA-256 chunk hashes [Verified, High], but for a static-site manifest, not a differential suite; frankentui_website reports live-route HTTP 200s [Verified, High]).
4. **Demonstrated dependency admission ledger with dated remote-compile evidence.** Mechanism: DEPENDENCY_ADMISSION.md with dated RCH compile logs, exact version pins, and per-crate consumption against the 245k-line budget [Code-verified, High]. The only other packet in the suite touching the concept is **franken_nlp**, and only as a *proposed next step* ("prototype the admission ledger against synthetic 44-deep KV shapes" [Inference, Medium]) — not a demonstrated artifact.
5. **The pinned parser discipline.** Mechanism: acorn pinned to exactly 8.14.0 in `tools/package.json`+lockfile — "a pinned parser is load-bearing for reproducible compilation" [Code-verified, High]. No other packet identifies a parser/compiler-input pin as a reproducibility-critical dependency (franken_threed is also the only packet with a compiler input to pin).

**Honesty note (where franken_threed lags, not leads):** the *machine-checked honesty* discipline franken_threed only *proposes* (next-step 3: machine-check the honest-status table) is already *implemented* by **franken_engine** (binding claim-to-proof matrix — 28 claims: 13 OBSERVED / 8 TARGETED / 7 HYPOTHESIS, each with owning bead, artifact path, verification command — that "gates README wording in CI" [Counted, High]) and by **franken_networkx** ("five auto-generated ledgers… that fail CI on drift" [Code-verified, High]). franken_threed's README drift (§4.7.2) is the finding those two mechanisms would have prevented — this is the single highest-value import (§6, item 1).

## 5. GENUINE UNIQUENESS

Only items verified to have no counterpart in any of the other 43 packets (checked by targeted text search across all packets):

1. **A hand-rolled JS→Wasm numeric-kernel compiler.** Zero hits for `acorn`, `rollup`, or `JavaScript→Wasm` in any other packet. `numeric_kernel.mjs` (779 lines: Acorn parse → import-free Wasm emit, f64 arithmetic/comparison opcodes, bitwise lowering, counted loops, typed arrays) is the only compiler in the suite, and the only suite member whose primary artifact is *compiled from* the upstream library rather than *replacing* it.
2. **An application specializer, not a clean-room reimplementation.** All 43 others reimplement their target in Rust (or build adjacent tooling); franken_threed is the only one that specializes *around* an untouched upstream JS library. Its governing constraint — the **no-cut rule** (full r186 surface, permanent omission forbidden; compatibility tracked as four separately-measured promises: API compatibility, application equivalence, accelerated coverage, measured performance) — appears in no other packet. The packet's §4.6 verdict: "nobody ships build-time specialization with differential oracle parity as the admission ticket" for a retained-mode JS 3D API [Inference, Medium]. *(Closest approaches, still distinct: **franken_nlp**'s "stated bet is specialization — one fixed model means every weight-side dimension is a compile-time constant," but that is compile-time-constant specialization of one model, not hot-loop extraction from an upstream library; **franken_ocr** compiles model-specific int8 kernels with bit-identical scalar oracles, but the kernels are hand-written for fixed models, not compiled out of an upstream codebase.)*
3. **Kill gates as first-class decision records.** Zero mentions of "kill gate(s)" in any other packet. franken_threed: "first-class beads with explicit PASS/FAIL decision records (`f3d-gate-1-foundation-tzn`, `f3d-gate-2-bridge-apz` whose criterion is literally 'the selected Wasm/host bridge shows an advantage'…) — but all 12 kill-gate beads are still **open** [Counted, High], so the gates have never been exercised."
4. **The exhaustive-sweep + zero-fallback-counter admission criterion.** §3 item 1 above. No other packet combines an exhaustive (not sampled) input class, live-oracle instantiation, bit-comparable assertions, *and* a counter asserting the fast path was actually exercised (wasmCalls == 256, fallbackCalls == 0). This is the mechanism that would falsify a "proved correct by testing the cases the kernel handles" tautology.
5. **A persistent render-schedule / guard-fallback execution model for specialized kernels.** `numeric_kernel_runtime.mjs` (536 lines): ownership/shape guards verified on every kernel entry, fallback to original JS on aliases/accessors/unsupported shapes, with the "once the numerical outputs have been published, there is no fallback replay" commit semantics [Code-verified, Medium]. No other packet has a guard-gated specialization runtime (franken_nlp's `strict-quantized` profiles have "preregistered logit/argmax/token/task budgets" — a cousin, but a quantization contract, not an entry-guard fallback runtime).

*Deliberately excluded from this list:* the honest-status table (franken_engine's claim matrix and franken_networkx's drift-failing ledgers are strictly stronger implementations of the same idea); the differential-oracle pattern in general (shared with frankenredis/franken_numpy/franken_nlp/franken_ocr — see §2A context and §3); the evidence-schema discipline (frankenfs has a 23-event-type evidence schema [Verified schema exists, High]; frankensim has a fuller evidence algebra).
