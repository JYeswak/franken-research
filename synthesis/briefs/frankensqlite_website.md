All evidence-tier labels below are the packets' own (`[Verified]` / `[Counted]` / `[Code-verified]` / `[Git-observed]` / `[External]` / `[Maintainer claim]` / `[Inference]`, High/Medium/Low confidence). Every claim cites the packet it came from. Nothing below is invented.

## 1. OWN-PACKET DISTILLATION

- **Verdict:** "a genuinely well-crafted interactive docs site whose engine-facing claims have drifted past the engine's own honesty line — the site is worth studying as a frontend artifact and as a cautionary tale about marketing outrunning a carefully hedged README" [Inference, High].
- **TRL:** 8 (live production website, all five routes HTTP 200; docked one level because the analyst never built it and no CI gates it) [Verified, High].
- **NODUS ring:** Monitor — Rulebook §4.9: *"Monitor is for websites, retired artifacts, and plan-stage work"*; "a website does not become Pilot by being well-built; there is no bounded workload to pilot *on*" [Inference, High].
- **Strongest strength:** The spec-evolution viewer — "a real 137-revision, integrity-hashed SQLite database of the engine's spec history, reconstructed in-browser via a custom diff patch engine with its own unit tests" [Verified, High]; plus unusual marketing candor ("Production Maturity: Early" vs C SQLite's "20+ years" in the site's own comparison table [Code-verified, High]).
- **Strongest ceiling:** Four site claims are contradicted by the engine it markets at same-day currency, and "the site's value is as the engine's communication surface… its claims about the engine should not be cited without the engine's own README, which is the more honest document" [Inference, High].
- **Three most important pieces of evidence (with tiers):**
  1. `"0 unsafe blocks / pure safe Rust throughout"` is **disproven as stated**: sibling-packet census (re-grep-confirmed) finds 41 `unsafe` blocks in `fsqlite-vfs` plus the `fsqlite-c-api` FFI boundary and 2 local `allow` overrides, vs the site's hero-stat "zero" [Verified, High].
  2. The drift is **test-enforced**: `tests/unit/content.test.ts` asserts `expect(crates).toHaveLength(26)` — "so correcting the stale '26-crate' claim to the engine's actual 28 would **fail the website's own tests**" [Code-verified, High].
  3. Two flagship features are **aspirational presented as shipped**: self-healing ("No external backups needed") and page-level encryption (with copy-paste `PRAGMA fsqlite.key` / `PRAGMA fsqlite.repair_ratio` examples) vs the engine README's own line that "page encryption plus RaptorQ self-healing are not yet reachable from the public API" — and the three APIs have zero engine-wide occurrences [Counted + Maintainer claim, High]. The site's PRAGMA example is worse than wrong: unrecognized PRAGMAs are silently ignored, so `PRAGMA key` *returns success while leaving the database unencrypted* [Verified, High].

## 2. SHARED NEGATIVE PATTERNS

**Pattern 1 — Site re-publishes engine numbers it cannot re-prove.** frankensqlite_website: "every number it publishes about engine performance is an engine number repeated without the engine's methodology docs" (§4.5, Inference, Medium); its "up to 8x" claim "traces to a benchmark family the engine's own methodology doc says 'Do not cite… for concurrent-writer speed claims'" [Maintainer claim, High]. **franken_markdown_website shares it verbatim:** "the site's headline engine numbers are re-published from the engine repo — this site cannot re-prove them" [Inference, High], and its kill test fired: "`verify:live` run against production reports 8 stale assets with the wasm glue matching no committed tree, exit nonzero" [Verified, High].

**Pattern 2 — Hero stats are a drift inventory (stale counts, testably stale).** frankensqlite_website's "26-crate workspace" vs 28 counted crates [Counted, High]. **frankentui_website shares it:** "The hero stats are a drift inventory. '12 Workspace Crates' contradicts the kernel's own workspace manifest, which lists 20 members at its HEAD [Verified stale, High]; 'V0.1.1 Alive on Crates.io' is wrong twice over" [External + Code-verified, High]. Both are the same failure: a hand-written hero-stat number that no machinery re-derives.

**Pattern 3 — Aspirational claims presented as demonstrated.** frankensqlite_website: "100% SQLite-compatible" as hero stat while the engine's 100% is an explicit *target*/release gate [Maintainer claim, High]; encryption/self-healing marketed with runnable examples while the engine README disavows reachability [Maintainer claim, High]. The same *demonstrated vs aspirational* taxonomy is used by the sibling engine packets — e.g. **frankensqlite**: "the 100% target is aspirational, not operational"; **franken_engine**'s claim matrix marks end-to-end constructs "aspirational" where only selected edges are "observed" — but the engine's README *labels* them; the website's sin is not having aspirational claims, it is *removing the labels* the engine kept. Its own packet says it directly: "the site systematically un-hedges" the engine README (deepening Q7, Inference).

**Pattern 4 — README deploy docs that describe machinery the repo doesn't have.** frankensqlite_website's README lists `bun tsc --noEmit`, `bun lint`, `bun run build`, `bun test`, `bun run test:e2e` as pre-push checks, "but the repo has no `.github/workflows` — deployment is push-to-Vercel with no gates" [Code-verified, High]. **franken_ocr is the decay-stage version of the same pattern:** "the CI workflows were deleted from the tree at HEAD and the last runs (2026-09-03) failed, while the docs still describe CI as the release gate" [Inference-ish verdict text, High evidence]. The website isn't at the deletion stage — it never had CI — but the class (docs describe a gate that doesn't exist) is identical.

**Pattern 5 — Stale CHANGELOG / stale metadata.** frankensqlite_website's CHANGELOG "documents only the first 17 (through 2026-03-16) — the 12 commits of the 2026-09-21 refresh are undocumented" [Code-verified, High]; flywheel star counts stale +30–40% on both spot-checks (1,654→2,152; 1,211→1,691) [External, High]. **frankensim_website:** "the CHANGELOG is a fossil from the sibling `asupersync_website` project" [Code-verified, High]. **frankentui_website:** the spec-evolution dataset (2026-02-08) and beads snapshot (2026-02-04) are "both February, both unlabeled as historical on the site" [Verified, High]. **beads-for-frankentui / beads_for_franken_engine:** dashboards frozen at a 2026-03-08 snapshot, "197 days (~6.5 months) before the pin" [Verified/Code-verified, High].

## 3. CI/EVIDENCE BAR

Honest headline first: **frankensqlite_website demonstrates almost no CI/evidence practice that other packets lack — it has no CI at all** (no `.github/workflows`, push-to-Vercel, honor-system pre-push checks [Code-verified, High]), so on CI machinery it sits *behind* the suite, not ahead. What's notable is what exists in lieu of CI:

1. **Integrity-hashed data artifact.** The spec-evolution SQLite DB's `meta` table carries `dataset_hash`, `classification_hash`, `db_hash`, `base_commit`, and a 137-commit manifest — "the one provenance-strong artifact… content-addressed history for the *spec*" (deepening Q1) [Verified, High]. **Who lacks it:** the four other marketing sites — frankensim_website, franken_markdown_website, frankentui_website ship stale versions of *their own* engines' artifacts without in-artifact integrity metadata on the site payload itself (franken_markdown_website's 404 `verify:live`, frankensim_website's un-hashed vendored WASM: "no hash linkage between the vendored `.wasm` and the parent repo's `fs-wasm` crate source" [Code-verified, High]). Caveat: frankentui_website has the *pattern's cousin* — `export_meta` provenance row + per-file sha256 manifest + `evidence.jsonl` for its demo payload [Code-verified, High] — so hashed provenance is shared with frankentui_website, not unique.
2. **A single-file, typed, unit-tested marketing-claim registry** (`lib/content.tsx`, 1,144 lines: "every marketing claim lives here" [Code-verified, High]) — auditable in one file read. No other website packet describes such a registry; the engine-side analogs are frankensqlite's `parity_score_contract.toml` / `supported_surface_matrix.toml` and franken_engine's FE-CLAIM matrix. The irony, documented in the packet itself: the registry is also what makes the drift *grep-able and test-enforced* — the registry's tests defend the stale constants.
3. **Test footprint without a gate.** 158 counted `test()`/`it()` call sites across 4 unit files + 5 Playwright specs [Counted, High] — bigger than sibling sites' suites, but "never executed" by the analyst and executed by nothing: "No CI executes any of this" [Code-verified, High]. This is a practice in the *weakest* sense: the suite is an artifact of intent, not evidence.

The site is the packet-suite's clearest demonstration that **tests ≠ CI**: the suite exists, covers the drifted constants, and protects them.

## 4. SHARED HURDLES

- **Bus factor 1.** "All 12 commits in the 2026-09-21 refresh authored by Jeff Emanuel / Dicklesworthstone (same person)" [External (GitHub API), High]; "No second committer, no foundation, no succession plan" [Inference, Medium]. Shared with ~40 of the 43 other packets (grep hits: asupersync, beads-for-frankentui, beads_for_franken_engine, franken_agent_detection, franken_alignment, franken_engine, frankensqlite, frankentui, frankensim, frankenredis, frankenlibc, frankenmermaid, frankensim_website, frankentui_website, and 26 more). This is the suite's universal hurdle, not this repo's.
- **License gap (distinctive variant).** The website has **no LICENSE file — default all-rights-reserved**, "more restrictive than the engine's MIT+AI-lab rider" [Code-verified, High]. Shared in kind with **beads_for_franken_engine** ("none — no LICENSE file in the tree; GitHub reports `license: null`" [Code-verified + External, High]) and **frankensim_website** ("no LICENSE file… the GitHub API `license` field is null, so the site's legal state is default copyright, not MIT" [Code-verified + External, High]). Notably, the website lacks even the suite's standard MIT+OpenAI/Anthropic rider — it has neither the rider nor a grant, which the packet flags as likely "inadvertence rather than posture" [Inference, Medium].
- **README/contribution ceiling.** Contribution policy quoted verbatim: "I do not accept outside contributions for any of my projects… know I won't merge them directly" [Maintainer claim, High]; 0 open issues, 4 stars / 3 forks. Same ceiling appears in the sibling websites: frankentui_website ("single maintainer, no contributions accepted, custom non-OSI rider" [Code-verified]).
- **Velocity vs review depth / burst maintenance.** 17 commits in the Feb–Mar 2026 launch burst, six months of silence, then 12 commits on a single day (2026-09-21) [External (GitHub API), High] — "burst maintenance, not continuous maintenance: the site is updated when the maintainer needs a public face for an engine milestone, not as the engine moves" [Inference, Medium]. The engine's two new crates (`fsqlite-wasm` 2026-06-19, `beads-doctor` 2026-08-27 [External (crates.io API), High]) were both born during the site's silent six months. Shared in shape with **frankensim_website** ("untouched for 32 days… pin 2026-08-21" [Git-observed, High]) and **franken_markdown_website** ("production lags the pin (manual deploys)" [Verified, High]). The packet's structural conclusion: "Any fix that relies on the maintainer remembering to update the site will fail the same way; only generated claims survive this maintenance pattern" [Inference, Medium].
- **No independent validation.** Like the whole suite, there is no external user in evidence; the site's honesty exhibits are the maintainer auditing himself (the comparison table's losing rows).

## 5. GENUINE UNIQUENESS

Strict standard: only things no other packet does. "Merely also does X" is called out.

1. **The SQLite-backed spec-archaeology viewer with a custom patch engine and in-artifact integrity hashes.** The dataset is a real 2.6 MB SQLite database (tables `base_doc/change_groups/commits/meta/patches`, 137 commits + 137 patches, integrity hashes in `meta`) reconstructed in-browser via sql.js with a *custom* unified-diff `patch-engine.ts` that has its own unit tests [Verified/Code-verified, High]. Cousin, not twin: **frankentui_website** has a spec-evolution lab too, but it is "versioned JSON (31 commits, 11 buckets)" with no patch engine and no hashes, "presented ahistorically" [Code-verified, High]. The *SQLite + custom diff engine + content hashes* combination is unique to this packet.
2. **A centralized, typed, unit-tested marketing-claim registry as repo architecture.** `lib/content.tsx` — every hero stat, feature card, comparison row, code example, FAQ, and flywheel entry lives in one typed file that unit tests assert against [Code-verified, High]. Grep of the other five website packets found no such registry; engine-side analogs exist (frankensqlite's contract TOMLs, franken_engine's claim matrix) but none are *marketing*-claim registries wired to unit tests. (The packet notes this is also the mechanism of the failure — the registry is "the site's most auditable decision," and auditable drift is still drift [Inference, High].)
3. **Test-enforced drift as a documented anti-pattern.** The site's own test suite *defends* two stale claims (`expect(crates).toHaveLength(26)`, `expect(crateStat?.value).toBe("26")` [Code-verified, High]) — "Drift with a regression test defending it… the canary: automation currently *protects* the drift." No other packet in the 44 documents a test suite failing on the *true* value. Unique in the dark sense, but unique.
4. **The site-vs-README honesty inversion documented at same-day currency.** This is the only packet whose central finding is that the artifact *un-hedges* its sibling: "the engine's README is a model of adversarial self-scrutiny… and the website systematically un-hedges it" (deepening Q7) — with four concrete engine-facing claims checked against the engine pin from five minutes earlier. Other websites drift (frankentui_website, franken_markdown_website), but none of their packets ran the *sibling-engine cross-check* this packet did; none have a "marketing outrunning a carefully hedged README" thesis grounded in a same-day, grep-level audit [Counted/Verified, High].

Not unique, merely also: the 36-component viz suite (frankensim_website has 43 demo components + 20 concept-viz components [Counted, High]); the in-browser sql.js SQLite pattern (**frankentui_website**'s 6.1 MB `beads.sqlite3` queried via sql.js [Code-verified, High]); the candid-losing-rows comparison table (frankensim_website's Limitations section "admits the deployed stats can go stale" [Maintainer claim, High]).

## 6. CROSS-POLLINATION IN (concepts from other packets → frankensqlite_website)

**Concept → origin → why it fits frankensqlite_website → expected payoff**

1. **Machine-checkable claim schema (claim text → code artifact → status row, verified in CI)** → **asupersync** — its "claim-discipline, CI-blocking baseline gates, honest-status tables" is called "the exportable artifact even if the runtime itself is never adopted" [Inference, Medium]; the asupersync packet proposes exactly the schema: "claim text → code artifact → status row, machine-verified in CI." → The website's `content.tsx` registry is the *shape* of this schema already — it just needs the artifact column. Generate the crate list, unsafe posture, and feature flags from the engine pin and make the 26-count test read the manifest. → Expected payoff: the next engine release breaks the website *build*, not the website's *honesty* — drift becomes a compile error. This is the packet's own next-step 1, and asupersync is the in-suite proof the machinery is exportable.
2. **Concordance-checked docs** → **franken_alignment** — its methodology ("receipt-bound qualification, planted-mutation testing, concordance-checked docs, unqualified-addition disclosure") is called "the most exportable artifact in the FrankenSuite" [Inference, Medium]. → Run a concordance check between `lib/content.tsx` claims and the engine README's disclaimers; every site claim that contradicts an engine `not yet reachable` line fails. → Expected payoff: the un-hedging class of drift (encryption, self-healing, 100%) is caught automatically at site-refresh time.
3. **Negative-evidence ledger + published self-retractions** → **frankenlibc** ("41,205-line negative-evidence ledger… including retractions of the project's own stale wins" — "the strongest measurement discipline observed in the program" [Inference, High]) and **frankenredis** (26,485-line negative-evidence log, "every benchmark loss recorded with a verdict and artifact" [Counted, High]). → The site should publish a self-retraction table for its four drifted claims (26→28, 0→41 unsafe, 8x lineage, 100% target) instead of silently fixing them. → Expected payoff: converts the credibility liability into the same honesty signal the engine already monetizes — the engine's disavowals are its most-cited packet feature.
4. **Claim-coverage audit** → **frankenmermaid** — ships a claim-coverage audit that self-reports "225 KEEP claims, 8 with a live incumbent ratio — 96.4% without" [Inference on the audit; claim-counts Code-verified]. → Audit the site's hero stats the same way: each of the ~6 hero stats names its artifact (crate count ← engine Cargo.toml; 0 unsafe ← unsafe census; 8x ← nothing). → Expected payoff: forces the un-provable stats to be reworded or removed rather than re-asserted; the 96.4%-without number becomes the site's honesty KPI.
5. **Demo-payload provenance manifest (`version.json` pinning the upstream SHA + per-file sha256 + evidence log)** → **frankentui_website** — ships `version.json` pinning `frankentui_git_sha` `20d095200584f0f5d3d3679e95f76087ca1730c8` (synced 2026-09-18) plus per-file sha256 and a 209-line `evidence.jsonl` [Code-verified, High]. → The website's claims should name the engine commit they were checked against (e.g. "verified against fsqlite@`315bc0f1`") with a per-claim provenance row, like the spec DB's `base_commit` field already does. → Expected payoff: drift becomes *legible* to visitors — "this number is 6 months old" is honest; an un-dated stale number is a lie.

## 7. CROSS-POLLINATION OUT (concepts from frankensqlite_website → named other projects)

**Concept → target(s) → why it fits them → expected payoff**

1. **Centralized claim registry (single typed file, unit-tested constants)** → **frankentui_website, franken_markdown_website, frankensim_website.** frankentui_website's hero stats drifted across multiple files ("12 Workspace Crates" vs 20-manifest reality, no CI to gate them [Verified stale, High]); franken_markdown_website's Lab Notes strip is "two engine versions stale" (0.3.5 claimed vs 0.4.2 shipped vs 0.4.1 live, *on the same page*) [Verified, High]; frankensim_website's own Limitations section "admits the deployed stats can go stale" [Maintainer claim, High]. → Put every version number and hero stat in one typed, tested registry. → Expected payoff: the three sites' drift surfaces collapse to a single file; the next version bump is one edit, not a scavenger hunt.
2. **SQLite-backed spec-archaeology viewer (dataset + custom diff patch engine + integrity hashes)** → **frankentui_website** (its JSON-based 31-commit spec lab gets the hash-verified, queryable upgrade path), **frankenredis** (deep docs culture, beads issue-tracker discipline — a 137-revision-style spec history would fit its honesty-machinery brand), **frankensim_website.** The packet's done-when is concrete: "a second FrankenSuite repo's spec document renders in it unmodified" [Inference, Medium]. → Expected payoff: turns one site's novelty into the program's reusable spec-archaeology component; the Wardley mover from genesis to custom-built is observable.
3. **Comparison table with deliberate losing rows** → **franken_markdown_website** (its site "cannot re-prove" the engine numbers it republishes [Inference, High] — it should say so in a row), **frankensim_website**, **frankentui_website** (hero stats with "no measurement methodology" [Maintainer claim, Low] need the "Early / unverified" row treatment). → frankensqlite_website grades itself "Production Maturity: Early" against C SQLite's "20+ years" [Code-verified, High]. → Expected payoff: the honesty that the engine packets get praised for (frankenredis's disavowed benchmark table, frankensqlite's L2800 disclaimer) becomes a website-side convention.
4. **Deferred heavy-viz loading (IntersectionObserver + skeleton placeholders, 600px rootMargin)** → **frankensim_website** (43 demo components + Three.js frontier demos — the heaviest frontend payload in the program [Counted, High]), **franken_markdown_website** (two-pane WASM playground). → The website's 2026-02-27/28 perf pass already built this [Maintainer claim, High]. → Expected payoff: interactive-demo sites stay fast without dropping their demos; the pattern is copy-pasteable.
5. **Same-day-currency sibling audit (site claims grep-checked against the engine pin from five minutes earlier)** → **franken_markdown_website** (its own `verify:live` already sha256-compares production assets [Code-verified, High] — extend it to version-string concordance), **frankentui_website** (its "12 crates" drift would have failed this check on day one). → Expected payoff: every marketing site in the suite gets a falsifiable claim-sync ritual; the audit is cheap (grep + curl) and the packets show no site does it yet.

## Caveats

- The other 43 packets were skimmed (TL;DR, claim inventory, verdict/TRL/ring, benchmark, limitations, license/governance), not read in full; quoted material above was located with targeted extraction and may miss nuance in the packets' full bodies.
- The frankensqlite_website packet inherits engine-side facts (41 unsafe blocks, 28 crates, README disclaimers) from the sibling frankensqlite packet's verified counts plus direct re-greps — a cross-check, not independent validation (packet §4.12).
- The website was never built or test-executed by the analyst (`bun install`/`next build`/vitest/Playwright all unrun), so TRL 8 rates the *deployed* site, and any of section 6's proposals assume the build is green — an unverified premise the packet's own §4.12 flags as the single most verdict-changing open question.
