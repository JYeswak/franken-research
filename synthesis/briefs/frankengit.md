## 1. OWN-PACKET DISTILLATION

- **Verdict:** FrankenGit is a "genuinely substantive, unusually self-critical clean-room pure-Rust Git-compatible forge effort" [Inference, High] — 49 first-party `fgit-*` crates, 589,340 lines of Rust, "not vaporware," but "a pre-release" whose "most durable contribution today is the verification and claim-governance methodology, not a usable forge" [Inference, Medium].
- **TRL: 4.** "Bounded one-node server interop validated in lab against real `git` client; TRL 5 requires validation of *integrated* components in a relevant environment — the forge, transports, and product stack are not integrated, so 4 is the ceiling."
- **NODUS ring: Explore.** "*Pilot* requires a release artifact plus a bounded real-workload fit (no release exists); *Invest* requires independent validation plus governance (neither exists)."
- **Strongest strength:** Claim-governance and evidence discipline — "the auto-demoting claims registry, the 34-row negative-evidence registry, the checked-claims block the checker refuses to leave stale, and verification lanes that fail-closed with exit 3 instead of returning a false green" — "a methodology that treats its own marketing as a demotable claim" [Verified, High].
- **Strongest ceiling:** "a pre-release, bus-factor-1 project with zero tagged releases, zero independent validation found, no smart-HTTP/SSH-as-production-transport, no forge product, and a non-OSI `LicenseRef-MIT-OpenAI-Anthropic-Rider` license that withholds all rights from OpenAI and Anthropic — against an incumbent (GitHub/git) whose moat is ecosystem, trust, and network effects, not code."

**3 most important pieces of evidence (packet's own tiers):**

1. **Zero first-party `unsafe`, exhaustively confirmed** — "a grep over all 1,434 first-party files finds 49 `unsafe`-keyword hits, and every one is in a comment, doc string, assertion message … identifier … or CSP assertion — there is not a single `unsafe fn`, `unsafe impl`, or `unsafe {` block in first-party code" [Verified by exhaustive pattern grep, High]; NEG-008 "rejected the hypothesis that 'unsafe or FFI shortcuts are required for world-class Git performance' — as a *constitutional* matter."
2. **Revision-bound reality check of real-`git` interop** — "178 acceptance IDs across five E2E suites exercising nonempty clone, raw push, historical state, incremental fetch, and SHA-256 repository behavior against a real `git` client" [Maintainer claim, Medium-High — revision-bound with artifact locations] — with the packet's own caveat that the snapshot (2026-09-07) "is now 15 days stale" at a tree moving ~25–40 commits/day [Verified, High].
3. **The auto-demoting claims registry as a mechanism** — "SHA-256-bound artifacts, automatic demotion on change"; the registry header rule is quoted verbatim: "any mismatch is an automatic demotion, not a reviewer-overridable status transition"; claim 12 is rated **Partially demonstrated** [Verified, High] — "mechanism exists and is wired into the README block generator; the enforcement loop runs in the maintainer's process, not observed by the analyst."

## 3. CI/EVIDENCE BAR — what frankengit demonstrates that others lack

1. **Digest-bound auto-demoting claims registry.** Frankengit's claims registry binds each claim to an exact SHA-256 artifact digest and its header rule is quoted verbatim: "any mismatch is an automatic demotion, not a reviewer-overridable status transition"; `tools/registry-check` "refuses a stale block" per README [Verified, High]. Who lacks it: frankenredis (whose README "currently carries stale '15 crates'/'every component forbids unsafe' sentences" — a stale claim that would have auto-demoted); frankensqlite_website (site contradicts the engine — 26 vs 28 crates, "zero unsafe" vs 41 counted unsafe blocks); franken_manim (has a 2,483-row Parity Ledger with a "fail-closed runtime self-audit" [Verified, High] but no digest-bound auto-demotion of prose claims). frankengit's own packet sets the falsification test for portability: "integrate it into FrankenRedis … if the mechanism cannot be decoupled from FrankenGit's registry schema … it is product scaffolding, not a method."
2. **Negative-evidence registry with required entry classes and prose/TSV correspondence rules.** Frankengit has 34 rows with "13 required entry classes (including `overclaim_correction` and `non_reproducible_result`)" and "one-to-one prose/TSV correspondence rules" [Verified, High]; NEG-029/NEG-030 record the maintainer killing its own latency and capacity findings with A/A-floor methodology. Many packets have NEGATIVE_EVIDENCE.md (frankenredis: 26,485 lines; frankenpandas: 44,086; frankentorch: 42,708; frankenscipy: 44,078; frankenlibc: 41,205; frankenmermaid: 726 rows with mandatory A/A nulls; franken_networkx: a 37,116-line ledger with an "INCUMBENT-vs-SELF-SPEEDUP verdict contract"), so the *ledger* is shared culture — but frankengit's *typed schema + correspondence rules* (required classes, machine-checkable killing of findings) is not attested for any other packet. Who most lacks the schema discipline: franken_nlp (NEGATIVE_EVIDENCE "seeded with one pre-registered reserved entry" — schema without content); franken_surveillance_system ("NEGATIVE_EVIDENCE.md (48 lines)").
3. **Fail-closed dormant verification lanes.** Frankengit's `full`/`release` lanes "fail-closed with exit 3" — they "refuse with exit 3 instead of returning a false green" [Verified, High]; NEG-017 records the rejection of "green CI = safe." Who lacks it: franken_overlap ("GitHub Actions is deliberately disabled, so no third party can observe test greenness; validation is owner-local"); franken_whisper ("no CI config in the tree"); franken_code_browser ("no CI workflows … `.github` contains only issue templates [Verified, High]"); franken_drone (sole CI workflow is self-hosted). Others fail *open* on red: frankenredis (CI red at the pin — conformance run #7679 "failed at the `cargo fmt` gate"), franken_node ("CI is red at the pin — all 8 push-triggered runs"), franken_numpy ("red at the pin … at the G1 `cargo clippy -- -D warnings` gate"), franken_sympy ("786 consecutive CI runs" failing), frankenlibc, frankenfs, frankenpandas (live-oracle + lint jobs red).
4. **Machine-checked Lean proof lane inside an application repo.** Frankengit has a Lean 4.32.0 proof lane with four theorems "under three named boundary assumptions," registry-bound, with registry wording that explicitly disclaims "not-a-proof-that-the-rust-implementation-refines-the-model" [Verified registry + Maintainer claim, Medium]. franken_lean is the Lean-reimplementation project itself (bounded slices, K2/NbE disclaimed, CI red at pin); no other application packet binds Lean theorems to a claims registry. franken_alignment is the closest conceptual relative (a "binding claim-to-proof matrix" is franken_engine's; franken_alignment has 40 registered invariants and 21 falsifiable hypotheses but "all `not_implemented` at the pin" for production lanes).
5. **Revision-bound reality check against a real incumbent client.** Frankengit's 2026-09-07 snapshot documents "178 acceptance IDs across five E2E suites … against a real `git` client … revision-bound with exact commands and artifact locations" [Maintainer claim, Medium-High]. Comparator: frankenredis has "5,041 counted differential probes against a vendored Redis 7.2.4 oracle" and "284 observed runs of the upstream Tcl suite"; franken_whisper measures against the actual whisper.cpp binary side-by-side with A/A nulls; frankenmermaid keeps a "structural-equivalence oracle (not pixel diffs)" against pinned mermaid-js — but those are benchmark oracles; frankengit's *real-client acceptance-ID registry, revision-pinned* is the interop-conformance variant, and its own packet honestly reports it "15 days stale" — which is itself evidence-bar behavior (frankenredis's disavowed headline table is the same honesty pattern).

## 5. GENUINE UNIQUENESS

Things no other packet does (with "also does X" caveats where the surrounding field is shared):

1. **A clean-room Git-protocol forge in Rust.** No other packet implements git-daemon/upload-pack/receive-pack/pkt-line/packs/delta with SHA-256 repositories and 178 acceptance IDs of real-`git`-client interop [Maintainer claim, Medium-High]. Entirely standalone in the program.
2. **The auto-demoting claims registry as a working mechanism.** The closest relatives are franken_markdown's `claims.tsv` + `check-claim-discipline.sh` ("fails when README marketing drifts from `capabilities --json`" — CI-gated, not digest-bound), franken_engine's "binding claim-to-proof matrix" that "gates README wording in CI" [Counted, High], and franken_node's `check_claims_manifest.py --check-honesty` (which the analyst executed — 9 checks ok, 0 drifted [Verified, High]). None has digest-mismatch auto-demotion with a "not reviewer-overridable" rule. **Merely "also does X"**: claim-registry culture itself is program-wide.
3. **Immutable decision stream + tiny conditional authority head** ("authority-from-database": the decision stream replaces the mutable bare repo + product DB as the single source of truth [Verified design, High]) with exact-predecessor CAS as the *only* commit point ("a failed CAS publishes nothing"). No other packet has this architecture. franken_engine has a "signed evidence ledger with transparency log + Merkle Mountain Range (MMR)" — an evidence ledger, not an authority model; frankengraphdb has "One Version Universe" fountain-coded commit streams — a storage design, not a forge-authority decoupling.
4. **Machine-checked Lean proofs of authority theorems within a non-prover project.** Unique among application packets (see §3 item 4).
5. **The receive-session envelope as fail-closed transport design**: "operator-selected size ceilings, a work-proportional session budget (`base + admitted bytes × rate`, hard-clamped), over-budget verdicts delivered through report-status rather than silent hangups, and a receive-pack lane disabled by default until bound to a principal." Protocol-specific; no other packet has an adversarial-transport envelope of this form. (franken_node has a 22-row threat model; franken_snowflake has a write-safety ladder — different mechanisms.)
6. **A machine-enforced license-disclosure apparatus**: D14 owner-resolved licensing decision with OSI marker `no`, `AGENTS.md` §10 mandating "No document may claim open source," and `scripts/license_gate.sh` consuming the decision's HTML markers [Verified, High]. Every other rider-bearing packet has the rider text but no machine gate; franken_engine even mis-discloses (README badge "License: MIT" linking to a rider-bearing LICENSE); franken_native_capsule has no LICENSE file at all.
7. **Agent-native authority plane inside a forge substrate** (intent runs, context packets, effect authorization, cancellation lineage; "agent text is explicitly 'not interpreted as capabilities'"). Caveat: franken_alignment pursues agent control more deeply as *research* (40 registered invariants, 21 falsifiable hypotheses) but with production lanes `not_implemented`; franken_node's threat model is "already written for agent operators" [Inference, Medium]. FrankenGit's is the only one embedded in an authority-store design with an immutable decision stream.

**"Also does X" — explicitly not unique:** the negative-evidence ledger (program-wide culture; frankenredis/frankenpandas/frankentorch/frankenscipy/frankenlibc/frankenmermaid/franken_networkx all have large ones); zero-unsafe posture (shared with franken_manim, franken_markdown, franken_agent_detection, franken_overlap, franken_threed, frankenmermaid's zero-token census, franken_drone, franken_snowflake, franken_engine, franken_lean); 78 CI workflows and 54 E2E suites (volume is common; CI greenness at the pin is not even established for frankengit — "CI per-run pass/fail not legible from text scraping").

3. **Preregistered paired-bootstrap claim verdicts for benchmarks** → from **franken_overlap** (`fo-claim-gate`: "preregistered paired-bootstrap claim verdicts of `supported`/`inconclusive`/`unsupported`" [Code-verified + Maintainer claim, High]) → why it fits: frankengit's FG-036c multicell benchmark honesty (NEG-029 latency-ordering kill, NEG-030 capacity-model kill) was *post-hoc* self-scrutiny; preregistered verdicts make the killing a gate instead of a confession, matching the ledger's own doctrine. → **Payoff:** future benchmark claims carry a preregistered verdict before measurement, hardening the "killing its own findings" discipline into a check the tree enforces.

4. **Registry-invariant tests that fail the build on drift** → from **franken_agent_detection** ("registry-invariant tests that fail the build on slug drift" [Counted/Code-verified, High]; next-step 1: "export the registry-invariant test pattern program-wide") → why it fits: frankengit maintains multiple registries (claims TSV, negative-evidence ledger with "one-to-one prose/TSV correspondence rules," the unsafe-boundary situation) whose correspondence is currently enforced by a checker in the maintainer's process; build-failing invariant tests move it into CI. → **Payoff:** the prose/TSV correspondence rules and registry invariants become compile-time rather than process-time guarantees.

5. **Formal result-class doctrine for performance claims** → from **franken_whisper** (PERF_LEDGER result-class doctrine: "self-speedups are *maintenance*, not wins; a campaign win requires the actual incumbent binary running side-by-side in the same invocation with A/A nulls in [0.98, 1.02]" — "the most explicit honesty apparatus observed in this program" [Inference, Medium]) → why it fits: frankengit's multicell SLO benchmark already lives this discipline informally (counts asserted with equality; timings "not latched as gates"; NEG-029's A/A-floor rejection); adopting a named result-class doctrine (self-speedup vs incumbent-campaign) would standardize what the packet calls "the number that survives, as a *non-result*." → **Payoff:** FG-036c-style numbers get a program-compatible verdict vocabulary, making cross-run and cross-project comparability honest.
