## 1. OWN-PACKET DISTILLATION

**Verdict.** FrankenSQLite is a **genuinely substantive, unusually self-critical clean-room Rust reimplementation of SQLite 3.52.0** [Inference, High] — not vaporware: a fresh-clone census confirms 28 crates and 1,784,743 lines of first-party Rust [Verified, High], a real SQL parser → VDBE pipeline, pager/WAL/B-tree storage, page-level MVCC with `BEGIN CONCURRENT` and conservative page-granularity SSI by default, seven extension crates, a SQLite-compatible C ABI shim, and 25,684 counted `#[test]` annotations [Verified, High].

**TRL: 6. NODUS ring: Explore.** Real releases ship (v0.4.4, crates.io, signed CLI) and the engine runs — demonstrated in a relevant environment; the 5/6 boundary is honest either way (no operational deployment or independent validation keeps it from 7), and 6 is carried by the release artifacts. Pilot fails on "no bounded real workload fit demonstrated"; Invest fails on zero independent validation plus bus-factor-1 governance.

**Strongest strength — the evidence discipline** [Verified, High]: a performance *negative-results* ledger, a strict signed parity-release threshold policy (100% declared-surface parity required), machine-readable contracts, a differential oracle against bundled rusqlite, crash-recovery fault matrices, and a README that publishes the sentence "No numeric performance result is claimed for current `main`." The packet's judgment: "The methodology-export lens fires hard here."

**Strongest ceiling — the governance compound** [Verified, High]: bus factor 1 with an explicit no-outside-contributions policy, zero independent benchmarks/reviews/deployments found, a pinned dated-nightly toolchain (`nightly-2026-08-31`), and the non-OSI MIT+OpenAI/Anthropic-rider license that withholds *all* rights — including benchmarking, testing, and analyzing — from the two leading AI labs.

**The 3 most important pieces of evidence (with tiers):**

1. **Scale and memory-safety posture are real and audited at the lint level.** 28 workspace crates; 1,784,743 Rust lines / 1,598 files; 25,684 counted `#[test]` annotations; 5 fuzz targets [Verified, High]. 26 of 28 crates inherit workspace `unsafe_code = "forbid"`; the two exceptions declare local overrides with explanatory comments; real `unsafe` blocks found only in vfs (41 blocks: mmap/shm/uring/atomics) and the c-api FFI boundary [Verified, High].
2. **Release engineering is further along the product axis than most of the 44.** v0.4.4 on GitHub (2026-09-17) with all 28 crates at 0.4.4 in their `Cargo.toml` files [Verified, High]; 31 release assets including per-platform tarballs, per-artifact `.sha256` files, and `SHA256SUMS.minisig` [Verified asset existence, High; signature validity not checked].
3. **The honesty exhibits are verified, not asserted.** "No numeric performance result is claimed for current `main`" [Verified, High] — the packet calls this "the strongest benchmark-honesty posture in the program." The `PRAGMA key` silent-success foot-gun is documented in the README's own FAQ and troubleshooting table: the command "returns success while leaving the database completely unencrypted" [Verified in README FAQ + troubleshooting, High]. The asupersync 0.5.0 runtime dependency is genuine — registry source, pinned checksum, 3,005 references across 17 files in `fsqlite-core/src`, zero tokio matches in `Cargo.lock` [Verified, High]. The differential oracle diffs against bundled `rusqlite` 0.40.1 [Verified dependency, High].

## 3. CI/EVIDENCE BAR

Practices frankensqlite demonstrates that named other packets lack — with the mechanism named and the lacking parties named:

**E1 — A formal, maintainer-curated performance negative-results ledger.** Mechanism: `docs/progress/perf-negative-results.md` — ideas *measured and rejected*, with retry conditions; old benchmark matrices kept in `baselines/` but explicitly labeled "not release evidence" ("the one detailed benchmark artifact in the tree disqualifies itself"). **Who lacks it (21 of 43):** asupersync, beads-for-frankentui, beads_for_franken_engine, franken_agent_detection, franken_alignment, franken_drone_geometry_reconstruction, franken_engine, franken_lean, franken_manim, franken_markdown, franken_markdown_website, franken_native_capsule, franken_node, franken_snowflake, frankensim, frankensim_website, frankensqlite_website, franken_threed, frankentui, frankentui_website, franken_overlap (has claim gates but no negative-evidence ledger file per the census). The gap bites hardest where the packets themselves admit unmeasured superlatives: franken_markdown — "'ultra-fast' is an unmeasured word — zero published head-to-head numbers vs pulldown-cmark/comrak"; franken_engine — "the runtime is candidly ~1,000× slower than Node on the only measured bundle"; franken_snowflake — "no performance or correctness comparison has ever been published" for its asupersync HTTP stack; franken_node — "the L1 product oracle sits at 69.82% (391/560) against the charter's ≥95% ship floor". **E2 — A strict, signed parity-release threshold policy.** Mechanism: `parity_release_threshold_policy.toml` — **100% declared-surface parity required** before release, no threshold downgrades, no waived obligations, evidence fresh within 24h, **signed policy payload** [Verified, High]. The policy is a gate design, not a current scorecard (no published parity score was found — the packet is explicit about this). **Who lacks it:** no other packet shows this exact gate. The closest analogs are frankenterm's `skipped_not_proven` qualification ladder ("refusal-to-claim as a machine-readable state") plus its content-addressed, sigstore-signed release attestation bundles, and franken_lean's CI-enforced claim matrix — but none binds a *declared-surface parity percentage* to a *signed release payload* with a *freshness window*. frankenfs's parity report is the anti-example: it "explicitly disavows its own 97/97 number as 'not an executed-test result or a readiness score'" — frankensqlite's policy is the mechanism that would prevent such a number from ever being release-load-bearing.

**E3 — Power-loss crash-recovery fault matrices with committed-row visibility as the asserted bar.** Mechanism: the harness's power-loss fault matrix (whole/half/third-frame WAL cuts, checksum flips, tail zeroing), SIGKILL-at-chosen-commit-states tests, and bit-flip testing — where the asserted bar is *committed-row visibility*, not `PRAGMA integrity_check` [Maintainer claim, Medium]. **Who lacks it:** 42 of 43. The only comparable practice is frankengraphdb's `fgdb-sim` — "virtual time, fault-injecting virtual disk (torn writes, bit flips, ENOSPC, fsync lies), DPOR schedule exploration, crashpacks with replay commands" [Maintainer claim, Medium] — and frankenfs's "in-tree crash/replay artifact gates." No other packet runs a power-loss matrix against a durability bar. frankensqlite's own next step 5 proposes freezing this as a versioned, machine-readable corpus run against stock SQLite — the bar item is as much the *bar definition* as the matrix.

**E4 — Deterministic-concurrency machinery in the verification harness (DPOR + lab reactor).** Mechanism: asupersync's deterministic lab reactor for concurrency tests plus the harness's DPOR schedule explorer (`dpor_enumerate_trace_classes` in `crates/fsqlite-harness/src/tla.rs`, verified in tree). **Sharing, stated honestly:** this is shared with frankengraphdb ("DPOR schedule exploration" in `fgdb-sim`) and franken_snowflake ("DPOR race suite" — `race.rs`, "420 passed, 0 failed across 32 targets" [figure stale per that packet]), and the lab runtime itself is asupersync's export (frankengraphdb, franken_snowflake, franken_remote all consume it). It is a bar only over the ~40 packets without deterministic-concurrency testing. frankensqlite's distinctive sub-piece is the *falsification experiment it enables* (next step 1: run the dormant merge ladder under a same-page write-conflict storm, comparing merged results byte-for-byte against serial execution) — no other packet proposes a merge-correctness experiment with a serial oracle.

## 5. GENUINE UNIQUENESS

Only things no other packet does. Where the *primitive* is shared, that is stated ("also does X") and only the distinct *application* is claimed.

**U1 — Serializable page-level MVCC concurrent writers inside the SQLite file-format envelope.** `BEGIN CONCURRENT`, conservative page-granularity SSI (Cahill/Fekete) by default, first-committer-wins base-drift detection, `commit_seq` from a global `AtomicU64` with `Release`-ordering stores [Verified code presence, High; isolation behavior Maintainer claim, Medium]. MVCC-the-primitive is shared — frankenfs has "block-level MVCC with a 5-variant merge-proof taxonomy" (filesystems), frankengraphdb unifies "MVCC/time-travel/git-style branches" (graph DB) — but **no other packet reimplements SQLite, and none attempts serializable concurrent writers inside the SQLite file-format envelope**. The packet's lane analysis: "a *SQLite-file-compatible, serializable-concurrent-writer* embedded engine … Nobody owns it: SQLite and Limbo serialize writers by design; libsql extends WAL but doesn't do MVCC SSI; rqlite/dqlite distribute the single-writer model instead of parallelizing it" [Inference, Medium]. This is the packet's one architectural bet and it is genuinely unoccupied in the suite.

**U2 — The documented silent-success encryption foot-gun.** The README's own FAQ + troubleshooting table warn that `PRAGMA key = 'secret'` "returns success while leaving the database completely unencrypted" — the XChaCha20-Poly1305 DEK/KEK design lives in `fsqlite-pager` (`encrypt.rs` verified in tree) but no `PRAGMA key`/`rekey` dispatch is wired into `Connection`, and unrecognized PRAGMAs are silently ignored [Verified in README FAQ + troubleshooting, High]. The honesty *culture* is shared suite-wide (P-sections above), but **no other packet documents its own live security foot-gun in its own README**. (franken_sympy's Sept-8 reality-check audit "reads like a red-team report against its own author" and frankenfs published its own "silent-data-loss facade" — those are the nearest relatives, and both are historical findings, not a currently-shipping silent-success behavior the docs warn you about.)

**U3 — RaptorQ fountain-coded durability applied to the SQLite WAL pipeline.** Native file-backed connections generate `.wal-fec` repair symbols asynchronously; the compatibility WAL reader never calls the decoder (bd-1hi.11); "gated on end-to-end recovery evidence" [Verified code presence, High + Maintainer claim, Medium]. The *primitive* is shared: frankenfs has a "hand-rolled RFC 6330 fountain-code self-healing subsystem (`ffs-repair`, 31,572 lines)" and frankensearch has "RaptorQ sidecars … in code." **The application — fountain-coded repair symbols for a SQLite WAL — appears in no other packet.** (Both frankensqlite and frankensearch share the *unwired* state: symbols generated, recovery not wired — the honesty about the gap is the shared part.)

**U4 — A dormant-by-design write-merge ladder with an explicit safety ladder.** The safe write-merge ladder (intent replay + structured page patches) exists as "dormant, test-exercised code in `fsqlite-mvcc` with a documented safety ladder (`PRAGMA fsqlite.write_merge = SAFE | LAB_UNSAFE`; raw byte-range XOR merge explicitly forbidden)" — "design plus dormant implementation, not live commit behavior," wiring tracked in bd-3d5y3 / bd-p4dcv [Verified disclaimers, High]. No other packet names a merge ladder at all (the phrase appears only here and in frankensqlite_website). frankenfs's `MergeProofMechanism` taxonomy is the nearest relative and it is *live*, not dormant — the dormant-with-safety-ladder *discipline* is frankensqlite's own.

**Not unique (explicitly "also does X"):** the differential oracle (frankenredis has "5,041 counted differential probes against a vendored Redis 7.2.4 oracle"; franken_networkx, franken_numpy, frankenpandas, frankenscipy, franken_sympy, franken_threed, frankenmermaid all run differential-vs-incumbent harnesses); the C ABI shim (frankenlibc's whole product is "C ABI entrypoints"; franken_tts has an audited `ftts-ffi` C ABI island; franken_whisper has an iOS C ABI); the WASM target (franken_markdown's byte-parity-gated WASM package, frankenmermaid's WASM demo); machine-readable contracts (frankengraphdb's `invariants.toml`/`laws.toml`/`claims_lint.toml` enforced by `tools/registry-check`; franken_lean's machine-checked claim matrix; franken_node's claims manifest; frankenmermaid's claim-coverage audit); signed release artifacts (franken_ocr, franken_whisper, franken_tts, franken_snowflake all ship signed/checksummed artifacts); the asupersync runtime coupling (frankenterm, franken_snowflake, franken_remote, franken_tts); the DPOR/lab-runtime deterministic concurrency practice (frankengraphdb, franken_snowflake via asupersync's lab runtime); the negative-results ledger (22 other packets — see E1).

## 6. CROSS-POLLINATION IN

Concepts from other packets that should be applied to frankensqlite:

**IN-1. CI-enforced claim gating → from franken_markdown.** The concept: `claims.tsv` + `check-claim-discipline.sh` "wire each README claim to a `capabilities --json` key and a proof script — marketing hygiene as CI, a discipline no incumbent practices." franken_engine has the sibling variant: "a binding claim-to-proof matrix (28 claims: 13 OBSERVED / 8 TARGETED / 7 HYPOTHESIS …) that gates README wording in CI." Why it fits frankensqlite: it already owns the machine-readable contracts (`sqlite_version_contract.toml`, `supported_surface_matrix.toml`, `parity_release_threshold_policy.toml`) but they are gate *designs* — its public CI is a `disabled_manually` workflow and its README drifts by an order of magnitude on crate sizes. Expected payoff: wiring README/CHANGELOG numerals to contract keys in CI mechanically catches the drift class the packet documents (fsqlite-types "2,800+ LOC" vs 28,471 actual) and turns the 100%-parity policy from a TOML file into an enforced gate.

**IN-2. Refuse-loudly for unimplemented surface → from frankengit (+ franken_snowflake).** The concept: frankengit's "dormant verification lanes that refuse with exit 3 instead of returning a false green" — refusal as a machine-readable state. franken_snowflake's sibling: the typed-skip live-proof contract where "a credential-less run emits a *structured skip event* … instead of silently passing, so 'no credentials' is never confused with 'green.'" Why it fits frankensqlite: the `PRAGMA key` silent-success foot-gun is exactly the false-green pattern — an unimplemented command returning success. Expected payoff: making unwired PRAGMAs return a typed no-op/refusal (rather than silent success) kills the single most dangerous honesty exhibit in the packet, with two named suite precedents for the mechanism.

**IN-3. Campaign-win measurement doctrine → from franken_whisper.** The concept: a formal result-class doctrine — "a campaign win requires the actual incumbent binary running side-by-side in the same invocation with A/A nulls in [0.98, 1.02]" — with self-speedups classified as *maintenance*, not wins (shared in variant form by frankenmermaid: "mandatory A/A nulls and ELF-SHA-256 provenance"; franken_networkx: the "INCUMBENT-vs-SELF-SPEEDUP verdict contract"). Why it fits frankensqlite: its release gate is "single-writer benchmarks within 3× of C SQLite" — currently a *target* — and the citation-grade performance matrix is deferred; the tree already contains a self-disqualifying benchmark artifact. Expected payoff: when the matrix lands it is incumbent-gated and quotable by construction, and the "within 3×" target becomes a falsifiable gate instead of an aspiration.

**IN-4. A named merge-conflict taxonomy for the dormant write-merge ladder → from frankenfs.** The concept: the `MergeProofMechanism` taxonomy (AppendOnly, RangeOverlay, BitmapOr, BitmapDelta, NoSameBlockMerge) with expected-loss policy selection — "mergeable same-block writes are resolved without aborting." Why it fits frankensqlite: its next step 1 is waking the dormant write-merge ladder under a red-team flag; the ladder has intent replay + structured page patches but no named conflict-resolution algebra, and same-page conflicts currently abort-and-retry. Expected payoff: the ladder gets a falsifiable merge taxonomy to test against the DPOR harness + serial oracle, converting "dormant implementation" into an experiment with named merge variants.
