## 2. SHARED NEGATIVE PATTERNS

**Pattern B — Bus factor 1, owner-directed, single maintainer.** fmd: "Single: Dicklesworthstone (Jeffrey Emanuel, per LICENSE copyright) — bus factor 1; no second maintainer visible in repo docs" [Inference, High]; "Governance: owner-directed single maintainer; no visible external contributors." Shared with all 43 others, but with a nuance: fmd's packet does *not* document the explicit contribution-refusal policy found verbatim in asupersync (README L2620: "I do not accept outside contributions for any of my projects" [Code-verified]), frankenterm ("bus factor 1 is an explicit, deliberate policy — 'I do not accept outside contributions for any of my projects'" [Verified verbatim]), franken_manim, franken_node, franken_code_browser, and franken_markdown_website ("I do not accept outside contributions for any of my projects…" [Code-verified]). So the *bus factor* is universal; the *declared refusal* is not documented in fmd.

**Pattern C — Docs/claims drift against a fast-moving tree.** fmd: line counts moved "146,322 `src/` lines at this HEAD vs ~138,500 at the v1 draft's HEAD (days apart) — the tree grows ~thousands of lines per day"; test count 136 vs 123 at the v1 draft; README says "CI fails if it drops" while the only Actions workflow is disabled [all Verified, High]. Shared with: frankenscipy ("the pattern is docs lagging a fast tree, the exact signal the Rulebook asks for" — test counts, parity figures, crates.io contradiction all drifted [Verified, High]); frankenmermaid ("the README is internally inconsistent and chronically stale (15 vs 18+Auto algorithms … ~114k vs 258k lines)" [Verified, High]); asupersync ("the honest README is itself a drift vector: 2,626 lines of carefully scoped claims that rot fast at this velocity" [Inference, Medium]); franken_markdown_website ("the Lab Notes strip says the page runs engine **0.3.5** while the pinned tree wires in **0.4.2** and production serves **0.4.1**" [all Verified, High]).

**Pattern D — "CI" that means the maintainer's machine (DSR-only enforcement, unobservable externally).** fmd: "the *only* GitHub Actions workflow is named 'DISABLED — releases use DSR exclusively' with `if: ${{ false }}`" and AGENTS.md states "'Never use GitHub Actions for any reason'"; "Enforcement runs through DSR … on the maintainer's own hosts: unobservable externally. README's 'CI' means 'the maintainer's machine,' not CI" [Verified, High]. Shared with: frankengraphdb ("GitHub Actions was de-automated by owner ruling on 2026-09-03 ('we do not use gh actions for any reason, ONLY /dsr'), so the pin has no CI verdict" [CI-observed + Maintainer claim, High]; "the evidence pipeline is currently trust-me" [Inference, Medium]); asupersync ("every behavioral claim about the assessed tree rests on maintainer-run DSR gates, unobservable externally" [CI-observed, High]); frankenmermaid (11 declared quality gates in `.ci/quality-gates.toml` but "no test workflows exist … the 11 declared quality gates … have no visible enforcement point" [Verified, High]); frankenterm ("no public CI … verification runs on maintainer-controlled RCH hosts that are not independently inspectable" [Verified]); franken_tts ("no workflow configuration exists in the tree").

**Pattern E — Zero independent validation.** fmd: "**Independent validation: zero** [External, High within recall caveats]"; "104 stars, 151 crates.io downloads … no evidence of production adoption outside the author's suite"; and the rider "chills the independent validation the project most needs." Shared with: frankenmermaid ("zero independent validation of any kind was found"), franken_tts ("zero independent validation of any kind"), frankenredis ("zero independent benchmarks, reviews, or production deployments found"), frankengit ("zero independent validation found"), franken_node, frankenscipy, and ~35 more. **Pattern F — Performance evidence is maintainer-generated, with no incumbent head-to-head.** fmd is the extreme case: "`'ultra-fast'` appears in the crate/GitHub description with zero published head-to-head numbers against pulldown-cmark or comrak anywhere in the repo" [Verified absence, High]. ## 3. CI/EVIDENCE BAR (what fmd demonstrates that other packets lack)

1. **The claim-discipline gate: `claims.tsv` + `check-claim-discipline.sh` wiring README claim patterns → `capabilities --json` keys → proof scripts, failing when marketing drifts** [Verified exists, High]. What it does: each README claim pattern must resolve to a machine-readable capability key emitted by the binary itself plus a proof file; drift fails the gate. Who lacks it: everyone else. The closest analogs are different designs, not the same mechanism: frankengit has its own `registries/claims.tsv` ("6 claim rows in `registries/claims.tsv` with exact SHA-256 artifact bindings" [Verified, High]) — an artifact-binding registry, not a README→capabilities wiring; franken_node has an Ed25519-signed honesty manifest (whose own `generated_at` reads `1970-01-01T00:00:00Z` [Code-verified, High]); frankenterm has sigstore-signed attestation bundles with `skipped_not_proven` gates; frankenmermaid has KEEP/REJECT ledgers + a claim-coverage audit but its README is *still* chronically stale — the exact failure class fmd's gate mechanizes against. Only fmd and frankengit even have a `claims.tsv` file; only fmd ties it to a live capability manifest.
2. **The byte-stability stack: `check-determinism.sh` (byte-repeat renders) + `SOURCE_DATE_EPOCH` + staged writes + `check-wasm-package.sh` byte-parity gate** [Verified mechanism, High; behavioral claims Maintainer claim, Medium]. No other packet mentions `SOURCE_DATE_EPOCH` (grep: only fmd). Others do determinism differently and weaker in this dimension: frankenmermaid's "same input + config → byte-identical SVG" rests on "FNV-1a golden checksums" [Verified mechanism, High] but its own packet found the README's "zero HashMap/HashSet usage" sentence **disproven** (one `std::collections::HashSet` with RandomState sits in the layout path); franken_drone_geometry has "staged writes with object-first/manifest-root-last visibility" plus readback verification (a stronger custody story, but no epoch-pinned render determinism); frankentorch has a "Deterministic Autograd Contract." None combines epoch-pinned timestamps, staged writes, repeat-render byte equality, and a cross-target (native↔WASM) parity gate.
3. **Ratcheted conformance with a floor file that matches the README** — "ratcheted CommonMark floor of 578/652 … floor file matches README — consistent" [Verified consistency, High; behavioral results Maintainer claim, Medium]. Peers have conformance machinery (frankenscipy "CI Gates G1–G9 green at the pinned commit," franken_numpy "differential conformance against a live NumPy oracle," frankengit "54 E2E suites," franken_manim's "2,483-row machine-readable Parity Ledger with a fail-closed runtime self-audit") but fmd's two-way README↔floor-file consistency check is the cleanest closed loop between marketed and measured.
4. **Perf-honesty commit convention: `perf-gauntlet.sh` (host/build fingerprint, hyperfine baselines, golden checksums, hypothesis ledger) + `perf-compare.sh` variance-envelope classification (noise / improvement / regression) + commit messages recording p50/p95 over 100+ iterations, byte-identical goldens, "SIMD not claimed until proven," and rejected trials.** The packet calls it "the *strongest internal perf discipline* seen in the program." Peers have pieces — frankenmermaid's mandatory A/A nulls, franken_tts's CV≤5% admission gate, frankenredis's negative-evidence ledger — but none shows the full before/after-classified, golden-gated, rejected-trials-recorded commit convention. (Caveat: "strongest … seen in the program" is one analyst's [Inference, Medium], and sibling analysts made competing superlative claims — see §5.)

## 4. SHARED HURDLES (structural)

- **Bus factor 1 with hand-rolled subsystems.** fmd: "Every subsystem (Brotli, PDF writer, shaper, 41K-line pdf.rs monolith) is hand-rolled and must be maintained against the upstream projects' collective engineering" [Verified, High]. Same shape: franken_engine (3.5M lines, ~20 commits/day, bus factor 1); franken_code_browser (147,429 lines, "206 commits across 2026-09-17→22, peaking at 101 commits on 2026-09-17"); frankenmermaid (258,093 lines, "~3,282 commits in ~7 months … if the maintainer stops, the 258,093-line tree rots within quarters"); frankenscipy (613,565 lines, "bit-rot sets in within quarters" without a successor).
- **Velocity vs review depth.** fmd's tree grows "thousands of lines per day" (138.5K → 146.3K between drafts). fmd's packet: "What breaks first if velocity decays is the thing velocity currently papers over … a slowdown without a successor doesn't stabilize the project, it strands the tree" [Inference, High]. Shared with frankenscipy ("the maintainer's own docs already lag reality by weeks … strands 613,565 agent-authored lines on a pinned nightly"), frankenterm (3.4M lines, 16,269 commits), franken_node (~20 commits/day).
- **Release artifacts lag or mismatch the tree.** fmd: npm latest 0.4.4 vs engine 0.4.5 [External, High]; demo site serving engine 0.3.5 while engine is 0.4.5 ("the live demo site serves engine **0.3.5** … the shipping automation lags the code by two minor versions on its own flagship demo"). Shared with: frankenredis (v0.1.0 release "targets the earlier tag commit, not the pin"); franken_markdown_website (page simultaneously claims 0.4.1 and 0.3.5; "production lags the pin (manual deploys) while npm already installs 0.4.4 — the 'try it here, install it there' coherence is broken" [Verified, High]); frankenmermaid ("the 'release' is a source-only tag" — no crates.io/npm artifact at all).
- **The rider poisons the exact audience.** fmd's sharpest formulation of a suite-wide fact: the MCP server / agent ergonomics are "built for an agent-infrastructure ecosystem whose two largest builders are legally excluded" [Inference, Medium]. Same structural ceiling named in franken_tts ("bars exactly the two AI labs building agent-voice infrastructure from even benchmarking it"), franken_node ("the rider is an advancement blocker (Explore-with-a-ceiling), not a ring qualifier"), franken_snowflake ("a license that legally bars the exact labs that would validate it"), frankenterm ("denies all rights (including benchmarking and analysis) to the two leading AI labs — the precise demographic an agent-orchestration tool needs").
- **The honesty apparatus is unobservable from outside.** fmd: "the gates are real scripts run on the maintainer's DSR hosts — unobservable externally." Shared with frankengraphdb ("the evidence pipeline is currently trust-me"), frankenterm (RCH hosts), asupersync (DSR gates), frankenmermaid (gates with "no visible enforcement point"). Consequence named by fmd's packet and applicable suite-wide: the license "withholds even *benchmarking* rights," so independent replication — the one thing that would make the gates trustworthy — is the one thing the license forbids.

## 5. GENUINE UNIQUENESS (standalone vs the other 43)

**Genuinely standalone (no other packet does these):**

1. **`SOURCE_DATE_EPOCH`-pinned, staged-write, byte-parity determinism across HTML+PDF+WASM.** Only fmd's packet mentions `SOURCE_DATE_EPOCH`; only fmd has a WASM *byte-parity gate* (`check-wasm-package.sh` gating parity, manifest, size budgets); only fmd matched "deterministic receipts." Peers do determinism in other domains (frankenmermaid's byte-identical SVG via FNV-1a goldens; franken_drone_geometry's exact-byte media custody with readback verification; frankentorch's deterministic autograd; franken_engine's deterministic replay with sealed witnesses) — but none has the epoch-timestamp + staged-write + repeat-render + cross-target-parity stack for *rendered documents*.
2. **EPUB 3 output.** Only fmd's packet matched "epub" (`src/epub.rs`, 941 lines) — "capability exceeds marketing here" since it's un-marketed in the "HTML & PDF" headline.
3. **Clean-room Brotli/WOFF1/WOFF2 + hand-rolled DEFLATE** (`compress.rs` 2,338 lines, `brotli.rs` 1,151, `woff2.rs` 427). No other packet claims a clean-room Brotli or font-container stack.
4. **fmd-font / fmd-math: the zero-dependency typesetting substrate factored out for suite reuse — and actually consumed.** fmd's Cargo.toml comments say fmd-font was split "so the wider Franken suite can consume it directly — franken_manim's fm-ydw is the factoring bead"; franken_manim's packet verifies consumption (fmd-math pinned as git dep, "the largest upstream contribution in suite history" [Verified upstream ledger + pin, High]) with a "99.797% occurrence-weighted parse+layout on 17,711 frozen occurrences" coverage ratchet. Other suites share crates too (franken_numpy's PCG64DXSM core, franken_manim→frankentorch kernels), but the zero-dep *typesetting* substrate as a suite public good is uniquely fmd's.
5. **The README→`capabilities --json` wiring inside the claim gate.** Only fmd ties claim patterns to a live machine-readable capability manifest emitted by the binary itself. (frankengit has claims.tsv with SHA-256 artifact bindings — a registry of claims; franken_node has a signed manifest — a census of claims. fmd's is a *live wiring* between marketing text and binary capability.)
6. **The 330x Knuth-Plass narrative as content** (13.5s → 0.04s via true TeX active-node deactivation, render-tree and PDF/HTML goldens byte-identical) — no other packet has a comparable single algorithmic-fix story with byte-identical goldens.

**Merely "also does X" (do not cite as unique):** `#![forbid(unsafe_code)]` (33 of 44 packets, incl. frankenmermaid, franken_lean, franken_drone_geometry, frankensqlite); zero-third-party-dependency library posture (franken_drone_geometry: "30 workspace members, ~57.2k first-party lines, zero external crates"; franken_surveillance_system: "zero external crates … all building on `std` alone"; franken_lean: "zero-external-dependency 731k-line workspace"); claim-governance in general (frankengit, frankenterm, franken_node, frankenmermaid, frankengraphdb, frankenredis, frankenscipy, franken_lean — a suite signature, not an fmd invention); the agent surface (`capabilities --json`/`doctor --json`/MCP — franken_code_browser has `fcb doctor --json` + a Capabilities subcommand; frankenterm has a 586-line MCP crate; franken_snowflake and franken_node have MCP servers); WASM distribution (frankenmermaid, franken_tts, franken_whisper, frankensqlite, franken_ocr, and others); fuzz targets with checked-in corpora (24 packets).

**Honesty caveat:** the fmd packet calls the claim-discipline gate "the most rigorous marketing-hygiene mechanism observed in this program" [Inference, Medium] — but sibling analysts made mutually exclusive superlative claims for their own subjects on the same day: franken_lean ("the most self-auditing repo in this assessment program"), frankenredis ("the most rigorously self-audited codebase assessed in this program to date" [Inference, Medium]), franken_node ("the most self-scrutinizing pre-1.0 codebase assessed in this program to date" [Inference, Medium]), frankenterm ("Claim-governance machinery without peer in this program"), frankenmermaid ("Evidence discipline without peer in this program"), frankenlibc ("the strongest measurement discipline observed in the program so far" [Inference, High]), franken_tts ("the most honest evidence machinery found in this program's model-runtime family"). No analyst read another's packet; treat all seven superlatives as uncalibrated. The *mechanisms* are real; the rankings are not evidence.

## 6. CROSS-POLLINATION IN (other packets → franken_markdown)

1. **frankenmermaid's incumbent-arm contract + CLAIM_COVERAGE_AUDIT → fmd.** Concept: a machine-readable `**Legacy incumbent arm (same invocation):**` marker that a performance claim must carry to count as a vs-incumbent claim, plus an audit that counts KEEP claims and publishes the share lacking a live incumbent ratio (frankenmermaid self-reported "225 KEEP claims, 8 with a live incumbent ratio — 96.4% without" [Verified, High]). Why it fits: fmd's exact gap is the unmeasured "ultra-fast" — the marker contract would force every perf sentence to either carry the marker or be demoted, and the audit protocol is already designed to be run "against a sibling FrankenSuite repo" (frankenmermaid's packet, next step 5). Expected payoff: converts "ultra-fast" from an unmeasured word [Verified absence, High] into a counted, audited claim — the packet's own "single most fixable gap."
2. **frankenredis's NEGATIVE_EVIDENCE.md ledger → fmd.** Concept: a standing, counted ledger where "every benchmark loss [is] recorded with a verdict and artifact" (26,485 lines at the pin [Counted, High]). Why it fits: fmd's perf loop already "records rejected trials" and publishes noisy means honestly, but has no durable ledger file (grep: fmd's packet never names a negative-evidence ledger). Expected payoff: gives the existing perf-honesty culture a first-class artifact, and gives the trajectory's "independent benchmark" revisit trigger a place to land losses.
3. **frankensearch's committed machine-readable latency receipts + SELF-SPEEDUP/INCUMBENT comparison-class policy → fmd.** Concept: `docs/evidence/perf/*.json` receipts carrying "git revision, hostname, load average, model identities, percentiles" [Verified, High], plus an explicit policy separating SELF-SPEEDUP claims from INCUMBENT claims (19,201-line ledger [Counted + Code-verified, High]). Why it fits: fmd's packet notes "The one place 'MB/s' appears is a *metric column* in `docs/planning/PERFORMANCE_OPTIMIZATION_PLAN.md`, not a result" — the receipts would turn `parser-perf.sh` output into citable numbers. Expected payoff: the missing benchmark table becomes receipts anyone can re-run and diff, without waiting for a full incumbent campaign.
4. **frankenterm's `skipped_not_proven` refusal-to-claim gate → fmd.** Concept: "machine-readable refusal-to-claim (`skipped_not_proven`)" — the maintainer "refuses to sign off prematurely," and the CHANGELOG "publishes failed held-out runs (RC53)" [Verified, High]. Why it fits: fmd's two live overclaims — "ultra-fast" and the stale "CI fails if it drops" README language — would both sit behind a `skipped_not_proven` gate until measured, which is exactly what the claim-discipline gate's falsification story needs. Expected payoff: the claim-discipline machinery covers *absence* of proof, not just drift of proof — closing the "ultra-fast" hole by construction.
5. **franken_snowflake's dependency-admissibility gate → fmd.** Concept: `scripts/check-dependency-admissibility.py` "runs `cargo tree` across every feature lane (default, no-default, each production feature, all combined, *and* dev/test lanes) and fails on any forbidden crate" (franken_snowflake's packet, next step 3), which "produced the verified zero-Tokio lock file" [Verified, High]. Why it fits: fmd's zero-dep claim is verified in manifests and `scripts/check-policy.sh` exists, but its optional features (`batch`→asupersync, `cli`→clap, wasm-bindgen) are lane-sensitive — the admissibility gate proves the diet per-lane rather than per-default-build. Expected payoff: hardens fmd's core differentiator (zero-dep library) against feature-flag drift as the tree grows thousands of lines per day.

## 7. CROSS-POLLINATION OUT (franken_markdown → others)

Expected payoff: determinism moves from single-host maintainer claim toward the cross-host byte-stability fmd's own next step 3 demands.

Expected payoff: turns the argued-but-unevidenced CI-snapshot fit into an adoptable machine contract, testable without a human in the loop.
