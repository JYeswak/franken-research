## 1. OWN-PACKET DISTILLATION

**Verdict:** franken_lean is "the most self-auditing repo in this assessment program — an attempt to rebuild Lean 4's whole substrate natively in Rust with a methodology export (machine-checked claim matrix, anchor-bound kernel contracts, a CI-enforced unsafe-site ledger) that is arguably more valuable than the prover itself."

**TRL: 4** — "bounded slices execute in a lab environment (relevant-environment validation), short of TRL 5 (no integration in a relevant environment)."
**NODUS ring: Explore** — "Substantive but unproven… zero release artifacts, zero independent validation, red CI. Pilot requires a release artifact plus a bounded real workload fit — neither exists."

**Strongest strength:** the evidence-governance machinery (B8) — "a claim matrix with evidence states and documentation CI that rejects wording stronger than the matrix permits — is a genuine methodological contribution, and it is partly *already enforced* (the bidirectional unsafe-ledger census passed CI at the pin [CI-observed, High])."

**Strongest ceiling:** "institutional un-adoptability — one maintainer who refuses outside contributions, a license rider that bars the AI labs most able to validate it from even benchmarking it, and CI red at the pin, so the project's own gates cannot currently certify its own claims. These three are one mechanism, not three problems."

**The 3 most important pieces of evidence (with tiers):**

1. **CI at the pin is red on the main gate — 11 of 30 steps failing** [External, High]. The `ci` workflow run `35746280136` (head = pin `e91da199`) concluded failure: `quality gate (scripts/check.sh)`, `ownership evidence — clean source-bound matrix`, `tribunal epoch-lab nested workspace`, `gate self-test`, and six e2e smoke steps all failed. Two other pin-headed runs (`fln-lsp-jsonrpc-lifecycle-landing`, `windows-functional`) also failed. The gates that enforce honesty passed while the gates that assert capability failed — "the project's own verification apparatus does not currently certify the project's own code."
2. **Zero-external-dependency 731k-line workspace** [Counted, High; Verified, High]: 731,657 lines / 839 `.rs` files / 32 crates, and "`Cargo.lock` contains zero `source =` entries — every dependency, including dev-dependencies, is a workspace path crate" [Verified, High]. Kernel posture: `#![forbid(unsafe_code)]` at the `fln-kernel` root with zero actual unsafe blocks [Code-verified, High]; 697-row `ci/UNSAFE_LEDGER.txt` with a bidirectional CI census that **passed at the pin** [CI-observed, High].
3. **Upstream-handcuffed kernel spec** [Code-verified, High]: 731-line `KERNEL_CONTRACT.md` gives each judgment rule an `anchor:` line naming the exact upstream file and line at the pin — e.g. `anchor: vendor/lean4-src/src/kernel/type_checker.cpp:289 (infer_type_core) expect="infer_type_core"` — and the `kernel_contract.rs` conformance test's anchor-resolution mechanism is code-verified. ## 3. CI/EVIDENCE BAR

What franken_lean demonstrates that other packets' projects lack — specific mechanisms, with who lacks them:

1. **Upstream-anchored specifications with drift-failing CI (`anchor:`/`expect=`).** Mechanism: each rule in `KERNEL_CONTRACT.md` carries an `anchor:` line naming the exact upstream file/line at the pin plus an `expect=` token; the `crates/fln-conformance/tests/kernel_contract.rs` test resolves every anchor against the pinned Reference source tree and fails CI if the token on that line ever changes [Code-verified, High]. **No other packet has this.** The nearest neighbors bind their *own* surfaces, not upstream's: franken_networkx has "five auto-generated ledgers… that fail CI on drift" [Code-verified, High] — but they drift-check its own API surface, never the pinned incumbent's source lines; frankenredis vendors Redis 7.2.4 as an oracle and runs its Tcl suite, but no conformance claim is bound to a Redis source line with a machine check; franken_tts pins truth-pack commits (HF weights `5d83992`, upstream source `022e286`) [Verified, High] — commit-level pins, not line-level anchors with CI enforcement. The epoch-ratchet problem (upstream Lean releases monthly) is lean's alone to have mechanized a detector for.

2. **A bidirectional unsafe-site census with CI enforcement that passes even when the main gate is red.** Mechanism: 697-row `ci/UNSAFE_LEDGER.txt`, `// UNSAFE-LEDGER:` markers at each narrowly-scoped `#[allow]` site, and a bidirectional census (ledger ↔ code, both directions) that "passed at the pin" [CI-observed, High] inside a gate that was otherwise failing. **No other packet has this.** Others do unsafe posture differently and weaker: frankentorch documents 116 unsafe sites under deny-gates [Counted, High] but its own docs claim "unsafe forbidden" — ledgerless tension; franken_snowflake has a compile-time secret-leak build script and a cargo-tree admissibility gate [Verified, High] (different axis: dependency hygiene, not unsafe inventory); franken_node's `#![forbid(unsafe_code)]` census is a one-way recount; frankengraphdb has a `unsafe_boundary_ledger.toml` + std-only `tools/registry-check` [Code-verified, High] — the closest in form, but with exactly 6 sites and no reported bidirectional CI census at a red pin. Lean is the only one to have a *machine-checked ledger + CI census that is currently green*.

3. **A one-ceremony multi-artifact pin file + an explicit Oracle-Only Law (SUITE.lock).** Mechanism: one lockfile pins the Reference (lean4 v4.32.0), the Corpus (mathlib4 v4.32.0), the toolchain (`nightly-2026-08-31`), and the suite commits, while the doctrine states upstream "never executes as a component" [Verified, High]. **Partially shared, not matched:** franken_tts has a "pinned truth pack (HF weights @ `5d83992`, upstream source @ `022e286`)" [Verified, High]; frankenredis vendors Redis 7.2.4 as a differential oracle (5,041 probes [Counted, High]); franken_whisper vendor-pins whisper.cpp; franken_networkx vendors NetworkX. None of them unify Reference + Corpus + toolchain + suite-substrate pins in a single ceremony file, and none states the oracle law as explicit doctrine. Lean's is the most complete pinning ceremony in the 44.

4. **An anti-hollow-green regression design.** Mechanism: the pinned-Nat-council regression's runner script (`scripts/check_pinned_nat_council.py`) is written so it "cannot produce a hollow green when the artifact is absent" [Maintainer claim, Medium] — the absence case is a failure, not a vacuous pass. **Others approximate it but not as a design rule:** franken_whisper's AGENTS.md names 12 forbidden reward-hacking patterns ("gate self-weakening, golden regeneration, tautological tests, bench-path hardcoding" [Maintainer claim, High]); frankengit has "dormant verification lanes that refuse with exit 3 instead of returning a false green" [Verified, High]; franken_overlap has fail-closed `.foidx` v2 parsing with a corruption-rejection test [Code-verified, High]. Lean's is the only one to state the anti-vacuity property as the artifact's acceptance criterion.

5. **A per-commit {1, 8, 32}-thread schedule-independence harness.** Mechanism: `thread_matrix_determinism.rs` exists [Code-verified, High]; per-commit thread-matrix testing of the Prelude. **Partially shared:** franken_manim's PG-5 is "bit-identical raw frames at {1,4,16} threads per commit" [Maintainer claim, Medium] — same shape, one fewer tier; franken_snowflake has a "DPOR race suite" (different axis: race detection, not schedule-independence). Lean's is the only per-commit *schedule-independence* gate.
