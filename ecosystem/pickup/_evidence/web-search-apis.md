# Web search API layers - evidence

All repos below verified via the GitHub REST API (`GET /repos/<owner>/<repo>`) or a returned web-search result. Star counts and push dates are live as of 2026-09-23. Default branches were used (tavily/serpapi use `master`; file fetches went through the contents API which resolves the default branch).

## Trend (owner/repo | stars | last push | why it evidences the trend)

- `firecrawl/firecrawl` | 183,735 | 2026-09-23 | The web data API to search, scrape, and interact at scale; fully open-source monorepo with self-host path. Proves the category has an open-source incumbent at massive adoption. `SELF_HOST.md`, `skills/`, and 30+ CI workflows.
- `searxng/searxng` | 37,549 | 2026-09-23 | Free metasearch engine; the open aggregation layer underneath agent search stacks (Firecrawl's server test matrix uses `search: ['searxng']` as its CI search backend). Proves an open, maintained index-aggregation primitive exists.
- `jina-ai/reader` | 12,036 | 2026-05-22 | URL→LLM-friendly-markdown endpoint (`https://r.jina.ai/<url>`), keyless; Jina Search (`s.jina.ai`) pairs for a keyless agent research loop. Proves the "extraction as an API" half of the Tavily/Exa value prop is real and maintained (TS monorepo, active CI).
- `tavily-ai/tavily-python` | 1,406 | 2026-09-18 | Official Tavily Python SDK. Commercial vendor with open SDK; pushed within days. Proves the commercial, agent-built API product (search/extract/map) with a maintained client.
- `exa-labs/exa-py` | 234 | 2026-09-22 | Official Exa Python package (neural search API). Pushed yesterday. Proves the neural/semantic-search-API-for-agents product line is active; examples cover websets, livecrawl, structured answers.
- `serpapi/serpapi-python` | 173 | 2026-09-15 | Official SerpApi Python wrapper. The old-guard SERP-data vendor still shipping; 7-version Python matrix in CI.
- `exa-labs/exa-js` | 130 | 2026-09-22 | Official Exa JS SDK, pushed yesterday alongside exa-py. Proves multi-language SDK parity is the norm for these vendors.
- `tavily-ai/tavily-js` | 95 | 2026-09-18 | Official Tavily TypeScript SDK, pushed same day as the Python SDK. Same story: commercial vendor maintaining parity clients.
- `serpapi/google-search-results-nodejs` | 95 | 2025-12-03 | SerpApi Node.js client. Older, slower cadence — evidences that these SDKs are thin wrappers maintained on a "good enough" schedule.
- `VanessaCorentin/WebSearchFree` | 0 | 2026-08-17 | New MIT-licensed keyless web search + extract API for agents (DDG/Brave HTML, Wikipedia, optional SearXNG backends; Tavily-style JSON). Thin evidence, but proves open-source clones of the category keep appearing.

Honest trend read: the category is real and commercially hot (per press: Tavily acquired by Nebius; Exa raised $85M per Medium 2026-03-12 — press claims, not repo-verified), but the *open* surface is mostly thin SDK wrappers plus Firecrawl. Brave Search API and Perplexity Sonar are API-key-only products with no official open SDK repo found — genuinely closed.

## Process practices worth copying (practice | repos exhibiting it | file pointers)

- **Post-deploy quality-eval benchmark against production, labeled per commit**: `firecrawl/firecrawl` — `.github/workflows/eval-prod.yml` (triggers on completed GHCR deploy to `main`; runs `.github/scripts/eval_run.py --label prod.<sha> --api-url --api-key --experiment-id` against the live prod API with secrets). A clean-room project should copy this: every merge to main gets an automatic quality benchmark run on the shipped artifact, not just the branch build.
- **Comment-triggered on-demand eval for PRs**: `firecrawl/firecrawl` — `.github/workflows/scrape-evals.yml` (any maintainer comment/PR body containing `#scrape-quality-eval` dispatches a scrape-quality eval; gated by org membership check). Copy this to make quality checks explicit and cheap to invoke during review.
- **Full-stack self-hosted integration matrix across providers**: `firecrawl/firecrawl` — `.github/workflows/test-server.yml` (matrix over engine `playwright|fetch` × proxy `proxy|no-proxy` × search backend `searxng` (google disabled) × `redis`/`rabbitmq` service containers, with `TEST_SUITE_SELF_HOSTED=true`). Copy the pattern: parameterize the search backend as a matrix axis so a clean-room implementation proves provider-swap correctness in CI.
- **Live-API integration tests wired to CI secrets**: `tavily-ai/tavily-python`, `exa-labs/exa-py`, `serpapi/serpapi-python` — `tavily-ai/tavily-python/.github/workflows/tests.yml` (env `TAVILY_API_KEY: ${{ secrets.TAVILY_API_KEY }}`, pytest over Python 3.9–3.11); `exa-labs/exa-py/.github/workflows/run_tests.yml` (`EXA_API_KEY` secret, `pytest tests/ --cov=exa_py`); `serpapi/serpapi-python/.github/workflows/ci.yml` (`API_KEY` secret, `pytest tests -k "not example"`). For an agent-facing API this is the right default: test against the real endpoint in CI, with unit-only separation for the rest.
- **Unit/integration directory split in SDKs**: `exa-labs/exa-py` — `tests/unit/` vs `tests/integration/`, plus `--cov=exa_py` and Codecov upload in `run_tests.yml`. `tavily-ai/tavily-python` similarly has `tests/request_intercept.py` (request interception for offline-safe tests) alongside `tests/test_search.py`, `test_crawl.py`, `test_map.py`, `test_research.py`, `test_errors.py`. Copy the split and the interceptor: new project should mock transport at the HTTP layer for unit tests.
- **Docs-as-tests: every example executes in CI**: `exa-labs/exa-py` — `.github/workflows/run_examples.yml` (`find examples -name "*.py"` split into 3 batches, run with `EXA_API_KEY`/`OPENAI_API_KEY` secrets against live APIs). `exa-labs/exa-py/examples/` has 13+ examples (websets, livecrawl, pydantic answers, subpages). Copy this ruthlessly: example code rots unless CI runs it.
- **Unit + e2e test tiers with a booted-server e2e harness**: `jina-ai/reader` — `tests/run-unit.ts` vs `tests/run.ts` (boots `build/stand-alone/crawl.js`, runs ~28 e2e files via node:test with 10s timeouts), `package.json` scripts `test:unit`, `test:e2e`, `test:coverage` (c8, Codecov upload with `fail_ci_if_error: true`). `tests/e2e/` covers per-option behavior worth copying wholesale: `content-fidelity`, `markdown-chunking`, `token-budget`, `summaries`, `error-handling`, `cache-control`, `option-interactions`. For any extraction endpoint, this is the file-level template.
- **Automated changelog/release on merge**: `exa-labs/exa-py` — `.github/workflows/release-please.yml` with `.release-please-manifest.json` and `release-please-config.json`. Low effort, keeps provenance of what shipped when.
- **Polyglot SDK parity tested per language**: `firecrawl/firecrawl` — `test-{js,py,go,rust,java,php,ruby,dotnet}-sdk.yml` + matching `publish-*-sdk.yml` workflows. Only worth copying once a second SDK exists, but it sets the bar: one test workflow per client.
- **Coverage reporting to Codecov with failure policy**: `jina-ai/reader/.github/workflows/_test.yml` (`fail_ci_if_error: true`) and `exa-labs/exa-py/.github/workflows/run_tests.yml` (`fail_ci_if_error: false`). Pick the Jina strictness for a new project.
- **Reusable workflow composition**: `jina-ai/reader/.github/workflows/ci.yml` (calls `_test.yml` via `workflow_call` with pinned Node `24.14.1`), `ci.yml` skips docs-only PRs via `paths-ignore: ['**.md']`. Copy both the reusable-workflow shape and the docs-skip.

## Notes / caveats (be honest about thin evidence)

- **This category is mostly closed-source.** The actual search-quality machinery — index, ranking, relevance evals, latency SLOs — lives inside Tavily/Exa/SerpApi/Brave/Perplexity and is not open. What *is* open are thin SDK wrappers (tavily, exa, serpapi: 100–1,400 stars each) whose CI only integration-tests the HTTP surface against live APIs. No public relevance benchmark (e.g., vendor-side FreshQA-style evals, NDCG@k dashboards) was found in any repo — press mentions benchmarks (Valyu claims 79% on FreshQA per Medium), but those claims are vendor marketing, not repo-verifiable.
- **Firecrawl is the exception** and the only repo in this set with a real quality-eval pipeline (`scrape-evals.yml`, `eval-prod.yml`, `.github/scripts/eval_run.py`). But its eval scripts run against *its own* prod with secrets; the scoring methodology is not publicly documented in the repo. A clean-room project can copy the *plumbing* (trigger shape, per-SHA labels, experiment IDs) but must invent its own ground-truth dataset and scoring.
- **SearXNG is infrastructure, not an agent API.** Included because it's the open search backend Firecrawl's CI actually uses, but its API returns SERP-style JSON for humans — not LLM-optimized answers, extraction, or structured output. Don't mistake it for a Tavily equivalent.
- **`VanessaCorentin/WebSearchFree` (0 stars, pushed 2026-08-17)** is a one-person OSS clone; verify its claims before citing it as evidence of anything beyond "clones keep appearing."
- **Jina Reader's last push (2026-05-22)** is ~4 months old; still the keyless standard reference, but freshness is weaker than the vendor SDKs.
- **`serpapi/google-search-results-nodejs`** (last push 2025-12-03) shows these vendor SDK repos get maintained only when the API changes — thin commit history is normal here, not a red flag.
- **No latency-SLO evidence found in any repo.** No workflow or doc in this set asserts p50/p99 query latency budgets or tracks them in CI. A clean-room project would be *ahead* of the open evidence by adding a latency-regression check (e.g., fail CI if p95 search latency regresses >x%) — that is a gap to fill, not a practice to copy.
- **Linkup has no discoverable open SDK repo** (`linkupapi/linkup` 404s) — another data point for "commercial, closed."
- **Adopter evidence is thin at repo level.** Vendor repos show stars, not customers. The strongest adoption signal found was structural: `firecrawl-skills/`, `skills/`, and per-language SDK test matrices (vendors ship SDKs *because* agents embed them), plus Firecrawl's 183k stars. Named-adopter lists, if needed, would require reading marketing pages (out of scope for repo evidence).
