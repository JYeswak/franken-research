## Process practices worth copying (practice | repos exhibiting it | file pointers)

1. **Kernel-level benchmark scripts next to the kernels, timing real GEMM shapes (not toy shapes).** AutoGPTQ (`tests/bench_autoawq_autogptq.py` — benchmarks Yi-34B down_proj K=20480/N=7168 shapes, GPTQ vs AWQ GEMM/GEMV side by side), bitsandbytes (`benchmarking/matmul_benchmark.py`, `benchmarking/inference_benchmark.py`, `benchmarking/int8/`), llama.cpp (`tools/llama-bench/`, `benches/`). New project should keep one benchmark per kernel family, with shape configs taken from real model layers.
2. **Numerical-correctness regression tests pinned to golden reference outputs.** AutoGPTQ `tests/test_q4.py` hard-codes `CUDA_OLD_REFERENCE` tensors and asserts max-diff/mean-relative-diff per backend kernel (ExLlama/Marlin/Triton) — the pattern for "does kernel X produce the same numbers as reference": per-kernel golden-output tests with a diff tolerance, not just "runs without crashing".
3. **Perplexity as the canonical quality-degradation metric, shipped as a first-class tool.** llama.cpp `tools/perplexity/` (runs WikiText against a quantized GGUF); AWQ/GPTQ papers standardize on WikiText2/PTB/C4 perplexity; lm-evaluation-harness (`lm_eval/tasks/`) supplies downstream tasks (MMLU, ARC, HellaSwag). Copy: repo-local perplexity tool + lm-eval-harness adapter for downstream zero-shot tasks; report both.
4. **Multi-backend CI matrix: one workflow per hardware backend.** llama.cpp: 58 workflows (build-cuda-ubuntu/windows, build-vulkan, build-opencl, build-apple, ci-self-hosted-metal...) via `.github/workflows/`; bitsandbytes: `tests-pr.yml`, `tests-nightly.yml`, `test-runner.yml` split by GPU availability; pytorch/ao: `1xH100_tests.yml`, `4xH100_tests.yml`, `regression_test_rocm.yml`, `metal_test.yml`. Copy: smoke tests on every backend per PR; heavy numeric/correctness tests nightly on self-hosted GPUs; explicitly separate "builds" from "GPU-correctness" workflows.
5. **Framework-embedded quantization as a config, with a runnable quantization-eval script per method.** pytorch/ao `benchmarks/benchmark_gptq.py` (times GPTQ quantize + profiles, `fire`-CLI callable), `benchmarks/benchmark_hqq.py`; TensorRT-LLM `examples/` quantization scripts. Copy: each method = script that (a) quantizes, (b) reports perplexity delta, (c) reports kernel speedup, all one command.
6. **lint/format gates independent of GPU CI.** bitsandbytes `.github/workflows/lint.yml` + `.clang-format`; llama.cpp `.clang-format`, `.clang-tidy`, `.flake8`, pre-commit. Copy: ruff/clang-format + pre-commit so PRs are reviewable without a GPU runner.
7. **Documented end-to-end flow from full-precision model to quantized artifact in examples.** llm-awq `examples/convert_to_hf.py` (quantize → save HF-ready); AutoGPTQ `examples/` + `docs/`; bitsandbytes `examples/`. Copy: one "golden path" example per supported format, run by CI as smoke (llm-awq's notebooks/examples pattern).

## Notes / caveats (be honest about thin evidence)

- **llm-awq's repo itself is thin on process:** the canonical AWQ repo has no `.github/workflows` (API 404), no `tests/` dir — quality evidence lives in the MLSys paper (WikiText2/PTB/C4 perplexity tables), not in repo CI. The *method* is well-evidenced; the *engineering process* of that repo is not a model to copy (stale push: 2025-07-17). Copy AutoGPTQ/pytorch-ao process instead.
- **Perplexity/accuracy numbers were sampled, not exhaustively verified:** I confirmed the existence of the eval tooling (`tools/perplexity/`, lm-eval task YAMLs, golden-reference test asserts) and the AutoGPTQ kernel comparison benchmark, but did not run any eval or read specific perplexity result tables. Treat "which eval set, which tolerance" guidance as structural (the pattern) rather than numerically grounded.
- **AutoGPTQ's last push (2025-04-11) suggests the standalone GPTQ packaging is in maintenance mode** — its kernel ideas live on inside vLLM/TensorRT-LLM/pytorch-ao. Trend evidence is solid but the momentum has moved downstream.
- **Star counts for ggml-org/llama.cpp, vllm, onnxruntime, transformers inflate "quantization" trend evidence** — they are broader projects where quantization is a feature, not the core. The category-specific trend rests more on awq/GPTQ/bitsandbytes/torchao, with the flagships showing normalization.
- **Repo tree listings via the GitHub contents API are default-branch snapshots** (branch verified where relevant: llama.cpp `master`, others `main`); workflow file names are real, but I did not read full workflow bodies beyond `test_quality.yml` (AutoGPTQ, which turned out to be a code-quality/format check, not accuracy tests — a reminder to read before citing CI as "eval CI").
