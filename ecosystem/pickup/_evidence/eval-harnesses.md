## Process practices worth copying (practice | repos exhibiting it | file pointers)

1. **Ship a mock/dummy model provider for offline harness testing** | inspect_ai, lm-evaluation-harness | inspect_ai: `src/inspect_ai/model/_providers/mockllm.py` — docstring: "A mock implementation of the ModelAPI class for testing purposes"; supports scripted outputs via `custom_outputs` (iterable, generator, or callable of `(input, tools, tool_choice, config) -> ModelOutput`). lm-evaluation-harness: `lm_eval/models/dummy.py` (`DummyLM`, registered as `"dummy"`) — lets the full eval pipeline run with zero API cost/credentials.
2. **Unit-test scorers and metrics like library code, with fixture/golden data** | inspect_ai, lm-evaluation-harness | inspect_ai: `tests/scorer/` (~30 files: `test_match.py`, `test_math.py`, `test_metric.py`, `test_krippendorff.py`, plus `tests/scorer/logs/` golden logs). lm-eval: `tests/test_metrics.py`, `tests/test_aggregation_pipeline.py`.
3. **Version task/dataset configs explicitly** | lm-evaluation-harness, terminal-bench | lm-eval task YAMLs carry `metadata: version:` — verified `lm_eval/tasks/hellaswag/hellaswag.yaml` has `metadata: version: 1.0` with `metric_list` declaring aggregation and `higher_is_better`. Terminal-Bench pins datasets (`tb run --dataset-version 0.1.1`, separate `terminal-bench-datasets` repo). Copy: never silently mutate a benchmark; bump a version.
4. **CI validates only the benchmarks that changed** | lm-evaluation-harness | `.github/workflows/new_tasks.yml` + `tests/utils.py`: `parser()` maps changed `lm_eval/tasks/*.yaml` files to task names, and the workflow runs those tasks (with the dummy model) against changed API code; `tests/testdata/`, `tests/testyamls/`, `tests/test_configs/` provide fixed fixtures. This is the pattern for keeping a 300+ benchmark suite's CI affordable.
5. **Tiered CI: lint, typecheck, fast unit tests on every PR; slow/docker tests behind markers** | inspect_ai, lm-evaluation-harness | inspect_ai `.github/workflows/build.yml`: ruff lint+format, mypy (py3.10/3.11 matrix), then `pytest -ra --doctest-modules -n logical` with separate slow jobs (`pytest --runslow -m slow tests/${{ matrix.area }}/`); separate `docker.yml` for sandbox workflows. lm-eval `.github/workflows/unit_tests.yml`: pre-commit + CPU test matrix. Copy the marker discipline: cheap tests gate merges, expensive tests run explicitly.
6. **Grading as deterministic, containerized test execution with per-language log parsers** | SWE-bench | `swebench/harness/run_evaluation.py`, `swebench/harness/grading.py`, `swebench/harness/log_parsers/` (per-language regex parsers), `swebench/harness/constants/`. Copy: scoring = run pinned tests in pinned containers, then parse logs with deterministic regexes — not LLM judgment where avoidable.
7. **Golden-log tests for the graders themselves + anti-cheat tests** | SWE-bench | `tests/test_log_parsers_python.py`, `test_log_parsers_java.py`, `test_log_parsers_javascript.py`, `test_log_parsers_pytest_v2.py` (parser correctness); `tests/test_grading_spoofed_output.py`, `test_grading_truncated_ids.py` (grader must not be fooled by model-printed fake PASS lines); `tests/test_grading_skipped.py`, `tests/test_infra_failure.py`. This is the single most copy-worthy practice: adversarial tests of your own scoring.
8. **Separate benchmark data from harness code** | inspect_ai/inspect_evals, terminal-bench, lm-evaluation-harness | inspect_ai (harness) vs inspect_evals (eval implementations) are distinct repos; terminal-bench harness vs `terminal-bench-datasets`; lm-eval `lm_eval/tasks/` YAMLs reference external HF datasets (`dataset_path: Rowan/hellaswag`) rather than vendoring data. Copy: harness repo stays code; datasets live in their own versioned home.
9. **Eval registry with per-eval packages** | openai/evals | `evals/registry.py`, `evals/elsuite/`, per-eval modules with colocated `*_test.py` (`evals/data_test.py`, `evals/record_test.py`, `tests/unit/evals/`). Copy: one directory per benchmark, registry entry per eval, tests colocated with the eval code they cover.
10. **Keep model-response handling and checking code in separate modules** | gorilla (BFCL) | `berkeley-function-call-leaderboard/bfcl_eval/`: `eval_checker/` (deterministic checkers) vs `model_handler/` (LLM response generation) vs `constants/`; `TEST_CATEGORIES.md` documents the checker taxonomy. Copy: the part that decides PASS/FAIL should be importable and testable without any model.
11. **Golden/regression suites for the runner itself** | harbor | `tests/golden/terminus_2/`, `tests/unit/`, `tests/integration/`, `tests/runtime/`, `tests/conftest.py` — end-to-end golden runs pinned per agent/environment. Copy: snapshot a full run's verdict and diff against it.
12. **Contribution policy gates for benchmark submissions** | inspect_ai, inspect_evals | inspect_ai `.github/workflows/pr-gate.yml` (contribution-policy gate script) and `suppressions.yml`; inspect_evals `AUTOMATED_CHECKS.md`, `BEST_PRACTICES.md`, `APPROVED_CONTRIBUTORS.md` at repo root. Copy: a new benchmark must pass documented automated checks before merge.

- I verified `mockllm.py` exists and is documented "for testing purposes", and that inspect_ai has `tests/model/` + `tests/scorer/` suites; I did not verify a specific test file invoking `mockllm` (conftest grep only surfaced an unrelated S3 mock). The practice claim rests on the provider's stated purpose.
- lm-eval adopter claims (Open LLM Leaderboard backend; NVIDIA, Cohere, etc.) were verified firsthand in the canonical repo's README (line 57), not only via fork mirrors.
- lm-eval's `lm_eval/api/sampler.py` grep for "seed" returned nothing in this pass; determinism evidence from lm-eval rests on `tests/test_samplers.py` (seeded few-shot sampling tests) and `metadata.version` in task YAMLs — adequate but I would not claim a specific seed API without a follow-up check.
- Star counts and push dates are point-in-time (2026-09-23); treat as trend evidence, not exact rankings.
